# 13 · 办公工作台与本地文档编辑

> **状态：首个可用版本已实现。** 状态快照：2026-08-18。
> 本能力服务于单用户、owner-only 的本地办公场景，不把 WorkPilot 扩展成通用 Office 套件或多人协同编辑器。

---

## 1. 当前交付

用户可以在前端 `/workspace` 选择已登记本地目录中的文件，输入自然语言指令并直接修改原文件。

| 格式 | 状态 | 当前编辑方式 |
|---|---|---|
| Markdown（`.md` / `.markdown`） | ✅ | 整篇或选区改写，写回后重新入库 |
| Word（`.docx`） | ✅ | 段落、表格单元格替换，以及追加段落 |
| Excel（`.xlsx`） | ✅ | 修改或清空单元格值，支持本工作簿内公式 |
| 旧版 Word / Excel（`.doc` / `.xls`） | ❌ | 不支持，需先转换为 Open XML 格式 |
| 含宏工作簿（`.xlsm`） | ❌ | 暂不支持，避免宏与签名被破坏 |
| PowerPoint（`.pptx`） | ⏳ | 本阶段未实现 |
| PDF | 只读 | 不修改原 PDF |

Word 与 Excel 文件当前只进入办公工作台，不进入 RAG 检索索引；Markdown 写回成功后会复用既有入库链路生成新版本。

## 2. 权限模型

本能力采用“**先申请一次权限，权限期内直接操作**”，而不是每条指令都要求用户确认：

1. 只有登录 owner 可以看到本地工作台与文件列表。
2. owner 在工作台授予 `local_office_write` 限时权限；授权与当前 owner 会话绑定，默认有效 1 小时，状态保存在**进程内**（`rag/editor_permissions.py`：sha256(token) → 单调到期时刻）。
3. 权限有效期内，用户点击“执行并直接写入”后，后端完成规划、校验和写回，不再弹出逐操作确认框。
4. 用户可以随时撤销权限；会话退出、授权过期或**进程重启**后，写接口立即拒绝请求。进程重启即失效是刻意的：一个限时授权在重启后还活着，那才是意外。
5. 权限只覆盖数据库中启用的 `local_dir` source，且文件仍必须位于 `LOCAL_LIBRARY_PATH` 内。前端提交的任意系统路径不会获得写权限。

这是能力授权，不是任意文件系统授权：后端始终重新解析文件标识、校验 source 根目录、拒绝符号链接和越界路径。

Cowork 工作流已增加正式的会话级权限路径：用户为 conversation 授予 `read_only` 或
`read_write` root；读写 root 一次性获得 `filesystem.read/write`、`office.word.edit` 和
`office.excel.edit`。Cowork runner 调用 Word/Excel 时，tool registry 和格式执行器入口会
分别校验 capability，授权有效时直接执行且不产生逐操作确认。Shell 与外部操作不会继承
目录权限。现有 `/workspace` 的 `local_office_write` 仅作为旧界面兼容层保留。

## 3. 直接写入的保护措施

无需逐次确认不等于静默覆盖。每次执行都经过以下保护：

- **乐观并发控制**：打开文件时记录 SHA-256；真正写入前再次校验。文件若已被 Word、Excel、Obsidian 等外部程序修改，返回 `409 document_conflict`，停止覆盖。
- **恢复副本**：修改前把原文件复制到同一 source 下隐藏目录 `.workpilot-backups/<时间>-<摘要>/`。
- **原子替换**：先在同目录生成临时文件，再替换原文件，避免只写入一半。
- **格式验证**：Word 和 Excel 临时文件必须能分别被 `python-docx`、`openpyxl` 重新打开后才允许替换。
- **操作白名单**：模型只产生受限 JSON 操作，不接触路径或执行 shell；Word 不删除结构，Excel 不修改样式、合并关系和工作表结构。
- **Excel 公式约束**：拒绝外部工作簿引用、网络函数和 HTTP/file 公式，降低数据外传与意外联动风险。
- **资源上限**：限制文件大小、扫描单元格数、模型操作数与生成 token，避免超大文件拖垮服务。

如果 Markdown 已写回但重新入库失败，原文件保持新内容、恢复副本仍可用，当前活动索引继续指向旧版本，后续由目录同步重试。把索引失败状态直接展示到工作台是下一阶段要补齐的可观测性项。

## 4. 工作台交互

工作台采用三栏结构：左侧为本地文件与格式筛选，中间为结构化预览，右侧为权限状态与自然语言指令。

- Markdown 支持在预览区选择文本；未选择时默认对全文执行。
- Word 预览给段落和表格单元格稳定编号，便于模型生成最小修改。
- Excel 预览以 `Sheet!A1` 展示工作表与单元格。
- 执行完成后展示修改摘要、变更数、模型与恢复副本路径。
- 冲突、过期权限、格式不支持、文件过大和模型操作非法都有独立错误状态。

工作台刻意不实现 WYSIWYG、多人协同、多光标、任意宏执行或完整 Office 功能。复杂版式调整仍应在 Word/Excel 内完成。

## 5. API 与实现边界

主要 API：

| 接口 | 作用 |
|---|---|
| `GET/POST/DELETE /api/v1/editor/permission` | 查看、授予或撤销会话级写权限 |
| `GET /api/v1/editor/files` | 扫描授权 source 中的可编辑文件 |
| `GET /api/v1/editor/files/{file_id}` | 读取结构化预览与基线摘要 |
| `POST /api/v1/editor/files/{file_id}/execute` | 权限有效时按指令直接写入 |

格式执行器彼此隔离：Markdown 走文本替换与重新入库；Word 走 `python-docx`；Excel 走 `openpyxl`。后续增加 PowerPoint 时应新增独立执行器和操作 schema，不把二进制 Office 文件降级成纯文本覆盖。

具体取舍见 [ADR-0008](adr/0008-限时授权后直接编辑本地办公文件.md)。

## 6. 多 Agent 的关系

办公工作台和 Cowork runner 目前调用统一模型网关和格式执行器，**不是多 Agent 系统**。
仓库已有固定 `literature_review` 图和动态 `cowork.v1` 单 Agent 工具循环；后者提供工具注册、
checkpoint、预算、事件和 Artifact，但没有 supervisor 或并发 specialist。

未来若引入多 Agent，可以把 Markdown、Word、Excel 执行器注册成不同 specialist 的工具，但仍需补齐 supervisor/任务委派协议、agent 间消息与上下文隔离、每个 agent 的预算和权限、结果合并与冲突策略、全链路来源记录及相应评测。在这些机制落地前，不把“多个格式执行器”描述为“多 Agent 协作”。
