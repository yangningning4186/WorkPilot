# ADR-0013 沉浸阅读作为工作模式，而非第二条产品线

**状态**：已采纳
**日期**：2026-08-22

## 背景与约束

WorkPilot 的两个参照物做的是同一件事的两半：

- **OpenWorker** —— 本机 Agent 工作台。一个能跑工具的循环，加上让它敢在你自己的硬盘上
  动手的那一整套东西：目录授权、逐次审批、幂等、Scheduler、Inbox、Skills、MCP。
  它的强项是**做事**，弱项是它对"依据"没有承诺——工具返回什么，模型就说什么。
- **DeepTutor** —— 可溯源的文档阅读。侧边一个阅读器，模型每下一个论断就把页面滚到依据
  那一页并高亮。它的强项是**接地**，弱项是读完之后什么也做不了。

原来的架构把这两半做成了两条产品线：`app/rag/` 是问答流水线（检索 → 生成 → 引用），
`app/cowork/` 是工具循环，`rag ⊥ cowork` 由 import-linter 强制。于是出现了一个荒谬的
边界：用户在 Cowork 里问"这篇论文第三节在论证什么"，Cowork 只能把整个文件读成一大段
文本塞进上下文，因为**带页码的那条路在另一个产品里**。

## 决策

**阅读不是第二条产品线，是同一个 run 的一档工作模式。**

用户在开场界面选 `office` 还是 `reading`（`CoworkWorkMode`）。两档共用同一个工具循环、
同一套审批与预算、同一份 checkpoint；差别只有两处：

1. `WorkCapability(name="reading")` 在 run 起始通过 `system_block` 往 system prompt 里写一段
   playbook，并通过 `pre_loop` 做确定性 locate 预检索——先看大纲、读过再引、一处一跳、
   `[p.N]` 标注。
2. 阅读器面板打开与否。

阅读工具仍注册在统一 registry；reading Capability 把 `material_outline` / `search_material` /
`read_material` / `reader_goto` / `reader_annotate` 声明为 `owned_tools`，保证阅读档首轮就能看到。
office 档需要时仍可通过动态工具目录发现它们，所以没有复制执行器。只有**玩法和首轮工具面**
是分档的。

接地由两条独立的路径提供，各自解决不同的问题：

| | 沉浸阅读（`cowork/reading/`） | 知识库检索（`rag/kb/`） |
|---|---|---|
| 面对 | 用户此刻打开的**这一份**文件 | 跨文档的资料库 |
| 寻址 | **locator**：1-based 的页 / 节序号 | chunk + 页码 |
| 存储 | 不入库。读工作区原始文件，进程内解析缓存 | `~/.workpilot/kb/<slug>/` 的 FAISS + BM25 |
| 引用编号 | `[p.12]`，阅读器渲染成可点链接 | `[K1]`（预检索）/ `[S1]`（`search_knowledge`） |
| 校验 | `verify_quote` 逐字回原文 | 命中的 block 原样透传 `locations[]` |

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **保留两条产品线，Cowork 通过窄接口调 RAG 的问答流水线** | 各自的边界清楚，改动最小 | 那条流水线的产物是**一段最终答案**，不是可以继续加工的证据。模型拿到一段别的模型写好的话，既没法追问也没法接着调工具——等于在工具循环里嵌了一个不能交互的黑盒 |
| **把阅读做成第三档产品（`app/reading/`），与 rag、cowork 并列** | 层次干净 | 它需要工具注册表、需要 capability 校验、需要审批——那些全在 cowork 里。搬过去等于把 cowork 复制一份 |
| **不分模式，靠工具描述让模型自己判断该不该按阅读的玩法来** | 少一个概念 | 试过。工具描述里写"读过再引"，模型在非阅读任务里也开始给每句话标页码；而在真的阅读任务里，因为那段话混在二十个工具描述中间，命中率反而更低。**模式是用户已经告诉你的信息，让模型再猜一遍是浪费** |
| **让阅读工具收服务端注入的 `material_id`（DeepTutor 的做法）** | 模型不能乱指文件 | 这里每只工具都收 `path` + 声明 `filesystem.read`，于是注册表在**每一次**调用上重跑目录授权。模型既读不到未授权目录的文件，也不会因为会话中途撤销授权而继续拿着一个仍然有效的句柄——比注入 id 更严 |

## 接受的代价

1. **两套引用编号。** 预检索发 `K1…Kn`，`search_knowledge` 发 `S1…Sn`，阅读发 `[p.N]`。
   模型要认三个前缀。合并成一套的代价更大：两边都从 1 开始且内容不同，共用前缀会让
   `[S2]` 在同一段回答里指向两段不同的原文。
2. **引文校验的强度刻意不对称。** `reader_goto` 在引文对不上时**照样翻页、只是不高亮**。
   用中文问一篇英文论文时，模型给的"引文"是它自己的翻译，永远不可能逐字命中；为此拒绝
   跳转会让阅读器看起来是坏的。落到正确的页而不画高亮，远比原地不动有用。
   `reader_annotate` 是更强的承诺，所以引文对不上直接拒绝；批注锚在内容哈希上持久化，
   阅读器面板负责展示备注与删除，模型没有删除工具。
3. **`rag ⊥ cowork` 仍然成立，但代价转移了。** `cowork/reading/` 不 import `app.rag`，
   它走 `app/ingest/` 的共享解析器。于是同一份 PDF 可能被解析两次：一次进 KB 索引，一次
   进阅读缓存。个人规模上这是秒级的重复，换来的是两条路径可以各自演进。

## 后续影响

- `app/rag/` 收缩成 `kb/`（本地知识库）+ `editor_permissions.py`。原来的 `retrieval/`、
  `review/`、`grounded_answer.py` 那一整套 PostgreSQL 问答流水线随
  [ADR-0012](0012-退役postgres与redis改用本机文件.md) 一起退役。
- `knowledge_contracts.py` 仍是两个产品包之间唯一的契约面，`RagService` 的实现从
  `PgRagService` 换成了 `LocalKbService`，调用方不感知。
- 溯源精度从 bbox 降到**页**（KB 路径）。阅读路径仍然是 bbox：unit 由 `ParsedBlock`
  组成，`verify_quote` 命中哪个 block 就把那个 block 的 `locations[]` 原样交出去，
  约束 3 在这条路径上完整保留。
