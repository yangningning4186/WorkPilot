# ADR-0006 解析块作为标注锚点，与分块策略解耦

**状态**：已采纳
**日期**：2026-08-13
**取代**：[03 数据模型](../03-数据模型.md) 初版中 `gold_chunks` 直接绑定 `chunk_id` 的设计

## 背景：初版设计有两处独立的致命缺陷

初版把四种分块策略的产物存在同一张 `chunks` 表（用 `strategy` 字段区分），
同时把评测的 gold 标注直接写成 `chunk_id` 列表。这个组合坏了两次：

### 缺陷一：标注与策略耦合，E1 实验根本不成立

四种策略切出来的 chunk 边界不同、ID 不同。
标注绑在 `heading` 策略的 chunk 上，就无法给 `semantic` 策略打分——
**分块策略对照实验（E1）从设计上就无法公平比较**。

而 E1 是排期里第一个产出简历数字的实验。

更糟的是：任何一次重新分块（改参数、修分块 bug）都会生成新的 chunk ID，
**全部人工标注作废**。换解析器还会改变文本坐标，需要单独迁移。
而人工标注是这个项目最贵的资产。

### 缺陷二：四策略共用一个 HNSW，过滤导致召回退化

pgvector 的属性过滤发生在**候选扫描阶段**：
HNSW 遍历图结构取出候选后再按 `WHERE strategy = 'x'` 过滤，
四策略混存意味着约 75% 的候选被丢弃，很可能凑不满 top-k。

这不只是性能问题——**E1 测出来的策略差异会混进索引退化噪声，结论是错的**。
而且退化程度与各策略的 chunk 数量相关，等于给不同策略施加了不同的惩罚。

## 决策

### 1. 引入四层结构，标注锚定在解析层

```
documents                逻辑文档（身份跨版本稳定）
  └─ document_versions       内容版本，持有归一化 full_text 作为字符偏移基准
       └─ parsed_blocks         ★ 解析产出的稳定最小单元 —— 标注锚点
            └─ chunks              某策略下的产物，可多套并存
```

- `parsed_blocks` 记录 `char_start` / `char_end`（相对 `full_text`）
- `chunks` 记录它覆盖的 `block` 区间与 `char` 区间
- `eval_items.gold_spans` 存 `[{version_id, char_start, char_end}]`

### 2. 评测时做区间映射

```
chunk c 命中 gold span g  ⟺  overlap(c, g) / len(g) ≥ 0.5

span-level Recall@k = |{g : ∃c ∈ top-k, c 命中 g}| / |gold_spans|
```

同一份标注可以给**同一解析版本下的任意分块策略**打分，
重新分块不失效。换解析器会生成新 `version_id`，需要 quote/context 对齐加人工确认，
不宣称旧 span 能自动迁移。

### 3. 每策略一个部分向量索引

```sql
CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)
WHERE strategy = 'heading' AND is_searchable;
```

查询走各自的索引，无索引内过滤损失。
剩余过滤（`doc_type` / `tags`）用 pgvector 的 `hnsw.iterative_scan` 兜底。
历史版本按有效区间先缩小 `version_id` 集合，再做精确扫描，不污染当前问答索引。

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **每次只保留一种策略，跑实验时重灌库** | 表结构最简单 | 每次切换要重新 embedding 全量语料（小时级）；且无法同时对比，实验周期被拖垮 |
| **每策略一张独立表** | 索引干净 | 检索代码要按策略分支，融合层和引用解析都要改；表数量随策略数增长 |
| **标注保留 chunk_id，每策略各标一份** | 不改结构 | 人工标注成本 ×4，且改一次分块参数就全部重来。**这是用最贵的资源换最省的设计** |
| **PARTITION BY LIST (strategy)** | 分区裁剪最彻底 | 分区表主键必须包含分区键，牵动所有引用 chunk_id 的地方。当前规模下部分索引已够，简单优先。留作规模增长后的升级路径 |

## 接受的代价

1. **表多了两张**，入库流水线多一层写入
2. **`full_text` 字段较大**（整篇文档的归一化文本）
   → Postgres TOAST 自动处理；换来的是 span 解析零成本
3. **区间映射有阈值参数 θ=0.5**，本身是个可调项
   → 在 dev 集上做敏感性检查，并在实验台账中记录取值
4. **char offset 依赖解析器稳定性**：换解析器或升版本会产生新 version，
   老 version 的标注不会自动迁移
   → 这是**正确行为**而非缺陷：不同解析结果本就该分开评测。
   已在 `document_versions` 记录 `parser` + `parser_version`

## 额外收获

span-level recall 比 chunk-id recall 更稳定，但不是完整的公平性保证：

- 更贴近用户感知（"关键段落有没有被找到"，而不是"某个 ID 在不在列表里"）
- 一个过大 chunk 仍可能完整包住 span 并获得命中，因此 E1 必须以固定 token budget 为主口径，
  同时报 context precision、冗余率和端到端质量

所以这次修复不只是补漏，是把评测口径改对了。

## 后续影响

- `messages.citations` 同步改为锚定 `block_id`：换分块策略后历史引用依然可定位
- `relations.source_block` 引用 `parsed_blocks`，知识图谱的溯源也跨策略稳定
- E1 实验设计需要在报告中声明各策略用的是**同一份 gold_spans**
- 入库流水线的顺序变为：解析 → 写 blocks → 按策略切 chunks → embedding
