# ADR-0014 知识库索引版本化与显式激活

**状态**：已采纳
**日期**：2026-08-22

## 背景与约束

ADR-0012 把资料库从 PostgreSQL/pgvector 收到本机目录后，最初每个 KB 只有一份 `index/`。
embedding 签名不一致会拒绝检索，避免旧向量和新查询安静错配，但它仍有三个缺口：

1. baseline 与 candidate 不能在同一份文档集合上并存。跑 A/B 要复制整个 KB，语料是否真的
   相同只能靠人保证。
2. 重建会覆盖唯一索引。候选构建失败会影响当前可用版本，也无法在确认效果后再切换。
3. 一份评测报告只写“用了某个 KB”不能自证检索配置；embedding、引擎、切分和融合常数可能
   已经变化。

索引是可重建的派生数据，但**一次评测引用过的索引配置不是可以被静默改写的临时状态**。
单用户、本机文件系统的产品形态仍然不需要恢复 PostgreSQL；需要的是一个适合目录事实源的
发布协议。

## 决策

**同一 KB 的同一份文档清单上允许并存多版索引，并用 manifest 中的显式指针选择 active。**

磁盘布局为：

```text
<kb-root>/<slug>/
├── manifest.json
└── versions/<version_id>/
```

`KbIndexVersion` 固化以下事实：

- embedding 的 model、dimensions、revision；
- retrieval engine（hybrid / dense / bm25）；
- chunk size、chunk overlap、RRF 常数；
- 建版时的文档内容哈希集合、节点数、标签与创建时间。

版本生命周期遵循这些规则：

1. `create_version` 在新目录完整构建，成功后才原子写 manifest。构建失败的目录不在版本清单中，
   因而对检索不可见；已有版本不会被覆盖。
2. 创建时可选择是否激活。评测通常用 `activate=false`，产品交互默认激活。
3. 默认检索只认 `active_version`；`RagSearchRequest.kb_version_id` 可以显式选择某版。
   active 缺失或指向不存在的版本时拒绝检索，不回落到“最新一版”。
4. 删除最后一版被拒。删除 active 时明确选择最新创建的剩余版本，并把新指针写回 manifest。
5. 加文档只刷新 active 版，其他版保留并按文档哈希标成 stale；已经引用旧版的报告因此仍可复现。
6. 旧 `index/` 没有足够信息还原检索配置，不做静默认领；提示用户运行 `rebuild` 生成 v1。

管理能力同时暴露给 service、HTTP、`app.cli.kb version` 和知识库页。版本构建仍走进程内索引
作业；激活和删除在构建期间拒绝并发修改。`EvidenceBundle.backend` 写入 KB、版本和引擎，评测
报告可以从自身回答“证据来自哪一版”。

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **继续单索引，就地覆盖** | 实现最少、磁盘只占一份 | 无法 A/B；候选失败影响当前版本；报告引用的配置会被下一次重建改写 |
| **复制整个 KB 做 baseline/candidate** | 不改 manifest 结构 | 文档清单也被复制，之后很容易漂移；版本身份散落在目录名和跑批参数中，报告不能自证 |
| **恢复 PostgreSQL 版本表与事务激活** | 关系约束与跨表事务完整 | 为单机派生索引重新引入服务依赖，与 ADR-0012 的桌面前提相冲突；文件先写、manifest 后发布已能提供所需边界 |
| **active 损坏时自动取最新版本** | 表面可用性更高 | 会静默改变检索配置。用户以为仍在搜原版，实际证据已经换源，违反显式失败原则 |
| **新文档自动重建所有版本** | 每一版永远覆盖完整语料 | 一次导入膨胀成 N 次全量构建，并会修改评测已经引用的历史版本；stale 可见比自动改写更诚实 |

## 接受的代价

1. 多版会重复保存 FAISS、BM25 和 docstore，磁盘占用近似随版本数线性增长；当前不做自动清理，
   由用户显式删除。
2. 版本目录与 manifest 不是一个事务。崩溃可能留下不在清单里的孤儿目录，但不会发布半成品；
   后续可增加只清理“manifest 未引用目录”的维护动作。
3. `rebuild` 仍是刷新 active 版的维护动作，会改写该版本；要保留原结果时必须使用
   `version create`。CLI 与界面需要把这两个动作明确区分。
4. 加文档后旧版可能 stale。显式版本检索仍允许使用它，因为评测可能正需要旧语料快照；界面和
   API 必须持续展示 stale，不能假装它覆盖当前文档集合。

## 重新审视的触发条件

- 需要跨机器共享 KB，或多个进程同时创建/激活版本；
- 孤儿目录与版本磁盘占用需要自动回收；
- 版本数量或单版索引规模使本机列表、加载或存储成本不可接受；
- 需要让切分器、embedding 和检索参数在 UI 中全部自由配置，而不只是当前的引擎选择。

## 后续影响

- 约束 10 在本地 KB 路径上的实现从“事务切换数据库投影”变成“独立目录先构建、manifest 后
  发布”；ADR-0012 与 [04 §3](../04-知识与阅读设计.md) 按此修订。
- 评测 baseline/candidate 应指向同一个 `kb_slug` 的两个 `kb_version_id`，不再复制语料库。
- API 返回 `active_version`、完整 `versions` 与 `needs_migration`；旧客户端不能再只看库级
  `embedding` 判断全部索引状态。
- active 指针失效、最后一版删除、历史版本被覆盖都必须有专属回归测试，不能只依赖普通检索
  用例间接覆盖。
