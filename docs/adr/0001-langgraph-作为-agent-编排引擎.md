# ADR-0001 LangGraph 作为 Agent 编排引擎

**状态**：已采纳
**日期**：2026-08-13

## 背景与约束

场景 B（多步任务执行）有三条硬需求，任何一条做不到，Agent 就只是个演示玩具：

1. **断点续跑**：综述整理这类任务要跑几分钟、十几步，中途失败不能从头再来
2. **人工中断**（HITL）：写回笔记库是不可逆操作，必须能暂停等用户确认
3. **过程可见**：前端要渲染实时进度时间线，需要能拿到结构化的执行状态

这三条的共同前提是：**Agent 的执行状态必须是显式的、可序列化的、可从外部读取的**。

约束：单人 6 周，不能自研编排引擎。

## 决策

采用 LangGraph，并强制以下实现方式：

- `AgentState` 是可 JSON 序列化的 `TypedDict`
- 每个节点是 `state → state` 的纯函数
- checkpointer 落本机 SQLite（原为 PostgreSQL，见 [ADR-0012](0012-退役postgres与redis改用本机文件.md)），不用内存
- 禁止把连接、客户端、闭包塞进 state

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **AutoGen** | 多智能体对话范式成熟，社区大 | 控制流隐式地藏在 agent 之间的对话里，无法可靠地拿到"当前执行到第几步"。中断与恢复要靠 hack 消息历史实现。调试时无法定位状态 |
| **CrewAI** | 上手最快，角色/任务抽象直观 | 抽象层级过高，出问题时定位不到底层发生了什么。checkpoint 和细粒度中断能力不足，为了满足三条硬需求需要绕开它的抽象——那还不如不用 |
| **MetaGPT** | SOP 驱动，适合固定流程 | 强绑定预设的软件开发 SOP，与本项目场景不匹配 |
| **自研状态机** | 完全可控 | 6 周排期内，把 checkpoint、中断恢复、并发控制、错误传播做扎实的成本太高，且没有额外的简历价值 |

## 接受的代价

- **学习曲线**：LangGraph 的 API 变动较频繁，需要锁版本
- **抽象泄漏**：复杂控制流（动态分支、并行子图）的表达不够直观
- **调试**：图执行的错误栈比线性代码难读；原计划靠 Langfuse trace 补齐，Langfuse 退役后只剩结构化日志的 `trace_id` 与 `llm_calls` 表
- **性能开销**：每步都写 checkpoint，增加 IO。已评估：单用户场景下可忽略，
  但如果扩到多用户高并发，需要改为异步批量写或分级 checkpoint（只在关键节点写）

## 后续影响

- 强约束了 [03 数据模型](../03-数据模型.md) 中 `agent_checkpoints` 表的设计
- `AgentState` 的可序列化要求成为 [CLAUDE.md](../../CLAUDE.md) 的第 2 条不可违背约束
- 大产物（综述正文）必须走 `artifacts` 引用而非内联进 state，否则 checkpoint 会膨胀
- 前端 Agent 时间线消费 `run_events` 表（初版设计为 `agent_steps`，
  已被 [ADR-0007](0007-agent幂等与事件溯源.md) 修正）
- **重要补充**：LangGraph 从 interrupt 恢复会**从节点开头重新执行**，
  checkpoint 恢复的是状态而非副作用。幂等必须另行落在 `tool_invocations`（ADR-0007）
