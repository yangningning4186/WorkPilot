# ADR-0005 记忆采用时序有效性建模而非覆盖式更新

**状态**：已采纳
**日期**：2026-08-13

## 背景与约束

个人助手的核心价值是"它了解我"。但"了解"有一个绕不开的问题：**人是会变的。**

三个月前用户说"我在做多模态检索"，现在说"我转做 Agent 评测了"。
系统需要同时满足两个看似矛盾的要求：

1. 当前对话中，注入的必须是**最新**的研究方向
2. 用户问"我三个月前在关注什么"时，能答出**历史**状态

同样的问题出现在文档上：笔记被反复修改，用户既要问"我最新版笔记怎么写的"，
也可能要问"我上个版本是怎么想的"。

## 决策

记忆**不覆盖，只失效**。借鉴 Graphiti（Zep）的时序知识图谱思想：

```sql
memories(
    fact, valid_from, invalid_at, superseded_by, pinned, ...
)
```

- 新事实与旧事实冲突时：给旧记录写 `invalid_at = now()` 和 `superseded_by = 新记录id`，
  再插入新记录
- 当前检索只取 `invalid_at IS NULL`
- 时间点检索：`valid_from <= T AND (invalid_at IS NULL OR invalid_at > T)`

同一模式应用于 `documents` 和 `relations`。

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **覆盖式更新**（UPDATE 同一行） | 最简单，表最小 | 丢失历史，答不了时效性问题。而 `temporal` 正是评测集的七类之一，占 10% |
| **仅追加不标记失效** | 实现最简单 | 检索时新旧事实同时命中，模型会看到矛盾信息并随机选一个——比没有记忆更糟 |
| **版本号方案**（每条记忆带 version） | 能追溯历史 | 无法表达"这条事实在某个时间区间有效"，回答"三个月前"需要额外推算 |
| **直接用 Zep/Graphiti** | 现成 | 引入外部服务；且这块是面试深挖点，自己实现才讲得透（同 [ADR-0003](0003-自建评测框架.md) 的逻辑） |

## 接受的代价

1. **表会持续增长**，失效记录永不删除
   → 缓解：`access_count` + `last_used_at` 支持后续做归档策略。个人产品数据量小，暂不处理
2. **查询变复杂**：每处检索都要带 `invalid_at IS NULL` 条件
   → 缓解：建部分索引 `WHERE invalid_at IS NULL`，并在 repository 层封装默认过滤
3. **判定"矛盾"本身是个难题**：什么算冲突、什么算补充？
   → 由 light 档模型做 ADD/UPDATE/DELETE/NOOP 四分类，**这个分类器的准确率需要单独评测**。
   分错的后果：该 UPDATE 的判成 ADD → 新旧并存产生矛盾；该 ADD 的判成 UPDATE → 丢失信息
4. **误失效不可逆感知**：模型错误地让一条正确记忆失效，用户很难发现
   → 缓解：`pinned` 字段，用户手动确认的记忆不允许被模型自动失效；
   `/memory` 页提供历史视图，可以看到并恢复已失效的记忆

## 后续影响

- 直接支撑评测集的 `temporal` 类别（占 10%），这类题目在覆盖式方案下根本无法出题
- 前端 `/memory` 页需要设计"当前记忆"与"历史记忆"两个视图，
  时序建模因此变成用户可见的产品特性，而不只是内部实现
- 四操作分类器成为一个独立的被测组件，需要自己的评测样本
