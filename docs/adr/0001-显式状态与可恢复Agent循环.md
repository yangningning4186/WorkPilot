# ADR-0001 显式状态与可恢复 Agent 循环

**状态**：已采纳

**日期**：2026-08-13

**最近修订**：2026-08-24

## 背景与约束

多步任务执行有三条硬需求：

1. 长任务失败后能从持久状态继续；
2. 高风险动作能暂停并等待人工确认；
3. 前端能用结构化事件还原实时进度。

三者共同要求 Agent 状态显式、可 JSON 序列化、可从外部读取，且运行时行为不能依赖
进程内调用栈或不可恢复对象。

## 决策

采用自研确定性“决策—工具—观察”循环，并强制以下协议：

- 状态使用可 JSON 序列化的 `TypedDict`；
- 模型决策与工具执行都接收当前状态并返回新状态；
- checkpoint 持久化到本机 SQLite；
- 审批、预算、重复调用熔断、事件和恢复由产品层显式控制；
- 外部连接、客户端和闭包不得进入 checkpoint；
- 副作用幂等必须落在工具调用边界，不能由 checkpoint 代替。

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| 通用 Agent 编排框架 | 预置图、节点和路由抽象 | 当前产品只有清晰的决策—工具循环；额外抽象不能替代审批、预算、事件、持久化和幂等协议，反而增加恢复语义与依赖复杂度 |
| 多智能体对话框架 | 角色与协作范式成熟 | 控制流隐藏在消息对话中，不利于精确判断执行位置、权限和副作用边界 |
| 固定 SOP 工作流 | 路径稳定、容易演示 | 真实办公与论文阅读任务分支动态，固定步骤表无法覆盖模型根据观察结果调整下一步的需求 |

## 接受的代价

- 循环路由、状态迁移和恢复协议需要自行维护；
- 分支图高度复杂时，线性循环的可读性会下降；
- checkpoint 只恢复状态，尚未确认完成的执行片段仍可能重放；
- 每个完整工具轮保存 checkpoint 会增加少量本地 IO。
