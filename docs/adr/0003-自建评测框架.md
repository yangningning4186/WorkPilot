# ADR-0003 自建评测框架而非直接使用 Ragas / DeepEval

**状态**：已采纳
**日期**：2026-08-13

## 背景与约束

评测体系是本项目的**核心差异化**，不是配套设施。

三份目标 JD 都点名"效果评估与反馈优化闭环""系统性评估 Agent 效果""质量保障体系"，
而这恰恰是候选人项目里最稀缺的部分。项目的价值主张就建立在
"能拿出逐条记录的实验台账"这件事上。

## 决策

自建评测框架（`eval/`），借鉴成熟项目的**思想**而不引入它们的抽象：

- **Ragas** → 指标分解到组件的思想（context_precision / faithfulness 等）
- **DeepEval** → pytest 集成与 CI 门禁的工程范式
- **promptfoo** → "评测即代码 + 快照 diff"
- **Langfuse** → 复用它的 trace 与 dataset 存储，不复用它的评测逻辑

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **直接用 Ragas** | 开箱即用，指标现成 | ①面试时讲不透——"faithfulness 怎么算的"答不上来就等于没做评测；②reference-free 设计与本项目"人工标注 gold_spans 字符区间"的路线不匹配；③Agent 类指标（step_efficiency、recovery_rate）覆盖不到 |
| **直接用 DeepEval** | 指标最全，CI 集成最好 | 同上第①条。且它的抽象较重，塞进自定义的七类分层评测集和双轨判分需要大量适配，省不下多少工 |
| **Langfuse 内置评测** | 与 trace 天然打通 | 评测能力偏轻，不支持复杂的规则轨判分与门禁逻辑 |
| **不做评测，靠人工体感** | 零成本 | 直接放弃项目的核心价值主张 |

## 接受的代价

- **开发成本**：约 3–4 个人日，占 6 周排期的可观比例
- **指标实现可能有 bug**：自己实现 nDCG、Kappa 这类指标有算错的风险
  → 缓解：用 Ragas 在同一批数据上交叉验证若干指标，确认口径一致
- **不如成熟库全面**：只实现本项目真正用得上的指标，不追求覆盖度

## 为什么代价可接受

这些指标本身不复杂（nDCG、Cohen's Kappa、RRF 都是几十行代码），
真正的难点在**评测集设计、Judge 校准、门禁阈值设定**——
而这三件事无论用哪个框架都得自己做。

换句话说：用现成框架省下的是最容易的部分，付出的是最有价值的部分。

## 后续影响

- `eval/` 成为与 `backend/` 平级的一等模块，不是测试目录的附属
- 评测集用 YAML 存在 git 里（可 review、可 diff），而非只存数据库
- CI 门禁直接依赖 `eval/gate.py`，评测框架的稳定性变成合入流程的依赖
