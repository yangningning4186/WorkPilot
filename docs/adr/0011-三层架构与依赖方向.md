# ADR-0011 三层架构与依赖方向

**状态**：已采纳（Step 0–4 全部落地）
**日期**：2026-08-20
**相关**：[ADR-0007](0007-agent幂等与事件溯源.md)、[ADR-0010](0010-cowork本地存储与rag数据面分离.md)、[02 架构设计](../02-架构设计.md)

## 背景与约束

代码长到 195 个文件、约 4 万行之后，`backend/app/` 的目录名不再表达职责：

- `app/services/` 15k 行、44 个文件，同时住着 run 生命周期（内核）、
  Office 执行器（能力）和 `grounded_answer`（产品）。它不是一层，是"其它"。
- `app/agent/` 7366 行里 5900 行文件名以 `cowork_` 开头。包名叫"Agent 层"，
  内容是"Cowork 产品 + 一点综述"。
- `agent → services` 21 条边、`services → agent` 11 条边，**互为依赖**。

后果不是"不好看"，是**同一个框架能力长出了两份实现**。最典型的是 run 预算：

| | Cowork / review | RAG answer |
|---|---|---|
| 入口 | `BudgetedGateway` | `build_model_gateway(budget_guard=...)` |
| per-run token | ✅ | ❌ |
| 调用次数 | ✅ | ❌ |
| 墙钟 | ✅ | ✅ |
| 日成本 | — | ✅ |

CLAUDE.md 约束 5 要求"token / 调用次数 / 墙钟任一超限即熔断"。
Cowork 三维齐全，RAG 侧只有墙钟。没人写错，是**没有框架层时的必然结果**：
`agent_core/budget.py` 没有任何机制规定 RAG 必须用它。

## 决策

采用 [earendil-works/pi](https://github.com/earendil-works/pi) 的三层划法，
**每层是一个独立可发布的包，依赖表本身就是层次约束**。

| PI 包 | 职责 | WorkPilot 对应 |
|---|---|---|
| `pi-ai` | 只懂模型 | `packages/workpilot-ai/` |
| `pi-agent-core` | 只懂框架：循环、状态、事件、压缩 | `app/agent_core/` |
| `pi-coding-agent` | 最懂业务 | `app/rag/` + `app/cowork/` |
| `pi-tui` | 只管显示 | `frontend/` |
| `pi-telemetry` | 旁挂横切 | `packages/workpilot-telemetry/` |

**与 PI 的唯一实质差异**：PI 只有一个业务 agent（coding），本项目有两个
（RAG、Cowork）。因此第三层是两个平行包，**且它们之间禁止直接 import**——
要共享就下沉到 agent-core，不许横向搭桥。

依赖方向单向：`entry → {rag, cowork} → agent-core → ai`，`rag ⊥ cowork`。

### 为什么用包边界而不是目录约定

目录约定挡不住任何人。`app/agent_core/contracts.py` 的模块 docstring 从一开始就写着
"本模块禁止依赖 `app.agent`、`app.services`、数据库或具体 Provider"——它管住了
那 799 行，管不住其余 4 万行。

包边界是**构建期**强制的：`workpilot-ai` 的 pyproject 里没有 `sqlalchemy`，
它就永远拿不到 `AsyncSession`；没有 `pydantic-settings`，它就永远读不到 `.env`。
约束从"文档里写了"变成"import 不进来"。

配套 `import-linter`（`[tool.importlinter]`，CI 里 `uv run lint-imports`）
覆盖包内部还没拆开的层次，随每一步收紧。

### Step 1 的三处切分

搬 `app/llm/` 时发现的层次泄漏，全部按"纯逻辑留包里、依赖外部世界的留应用层"处理：

1. **`gateway.py` 的四个 `*_from_settings` 构造器**（165 行）→ `app/llm_bootstrap.py`。
   `ModelGateway` 类本身接受显式 kwargs，本来就是 Settings-free 的；
   把 `Settings` 翻译成构造参数是**部署配置的事**，不是模型的事。

2. **`audit.py` 整个文件**（32 行，写 `llm_calls` 表）→ `app/telemetry/llm_calls.py`。
   `AuditSink` Protocol 留在 `workpilot_ai.types`，SQL 实现留应用层。

3. **`batch.py` 拆两半**：`BatchSpec` / `current_batch_id` / `batch_scope` 是纯口径，
   留包里；`gpu_batch()`（建表写表）与 `batch_spec_from_settings()` →
   `app/telemetry/gpu_batches.py`。
   顺带把 contextvar 的 set/reset 收口成公开的 `batch_scope()`，
   落库适配器不再去碰模块私有变量。

结果：`workpilot-ai` 的运行期依赖只剩 `httpx` / `structlog` / `uuid6` / `pyyaml`。

> **2026-08-22 更新**：原文这里论证的是 `RedisCompletionCache` 为什么可以留在包里——
> 它只接受**注入的**客户端、不自己读连接串，所以它知道的仍然只有「缓存」。
> [ADR-0012](0012-退役postgres与redis改用本机文件.md) 之后它换成了 `InProcessCompletionCache`，
> 连注入都不需要了，`redis` 从依赖表里消失。**论证方式仍然值得留着**：判断一个东西该不该
> 待在下层包里，看的是它知道多少，不是它叫什么名字。

### Step 2 第一块：压缩上移到框架层

`app/agent/cowork_compaction.py`（436 行）→ `app/agent_core/compaction.py`。

**判断依据一开始是错的**：这个文件的 import 只有 `agent_core.budget` 与 `workpilot_ai`，
看上去"零业务依赖、改个名就完事"。但**import 干净不等于文件干净**——真正搬的时候
撞出四处硬编码的 Cowork 语义：

| 硬编码 | 处理 |
|---|---|
| `SUMMARY_SYSTEM_PROMPT`（"你负责压缩 WorkPilot Cowork 的…"） | → `CompactionPrompts.system_prompt` |
| `<cowork_history_summary>` 包裹标签 | → `outbound_prefix` / `outbound_suffix` |
| `task_type="cowork_compaction"` | → `summary_task_type` |
| `prompt_budget("cowork_decision")` | → `decision_task_type` |

结论是同一个（这块逻辑属于框架层），但代价从"改个名"变成"抽一个 5 字段的注入契约"。
分界线：**框架层管"什么时候压、压到哪个边界、失败怎么退化"，产品层管"用什么话去压"**。
Cowork 的那一份是 `cowork_runtime.py` 里的 `COWORK_COMPACTION_PROMPTS`。

`_parse_summary` 仍然要求模型返回 `{"summary": "..."}`，这是框架层定义的输出契约，
产品换措辞可以、换格式不行——写在 `CompactionPrompts` 的 docstring 里。

回归网：`test_compaction_is_product_neutral` 用一套虚构的 digest agent 措辞跑通压缩，
并断言渲染结果里不含 `cowork`。谁把 prompt 硬编码回去，这条就挂。

**这一步也是"import 图不是层次真相"的教训**：后面几步不能只看 import 边，
要打开文件看常量和字符串。

### Step 2 第二块：state 拆框架与产品

`app/agent/state.py` 里住着两类东西，靠名字完全看不出来：

| 原符号 | 去向 | 判断 |
|---|---|---|
| `PlanStepState` / `InterruptState` | `app/agent_core/state.py` | 任何 Agent 都有计划步骤与人工中断 |
| `json_state` / `normalize_budget` | 同上，改为泛型 | 约束 2 的运行时执行者，与状态内容无关 |
| `ReviewDocument` / `ReviewCard` / `ReviewGroup` | `app/agent/review_state.py` | 综述业务类型 |
| **`AgentState` → `ReviewState`** | 同上 | 见下 |

`AgentState` 这个名字是错的：它的 `schema_version` 字面量就是 `"literature-review.v1"`，
字段是 `documents` / `cards` / `groups` / `comparison` / `draft`——**它从来只是综述工作流
的状态**，却因为叫"Agent 状态"而被当成通用类型，把三个综述业务类型一起拖进了共享层。
改名之后 Cowork 侧对它的唯一引用（`BudgetState`）自然回落到 `agent_core.contracts`。

### Step 2 第三块：事件与持久化 → `app/runstore/`

原计划是"把 `services/runs.py` 的 run 生命周期下沉到 agent-core"。**逐行读完之后改了**：
那 1123 行里几乎没有可移植的框架逻辑，每个函数都是

```python
store = configured_cowork_store()
if store is not None and await store.get_run(run_id) is not None:
    return await store.append_events(...)      # 桌面 SQLite 旁路
... 一段 Postgres SQL ...
```

**它是一个双后端存储适配器，不是框架代码。** seq 必须连续、租约语义、终态集合这些
不变量是用 SQL 表达的，搬进 `agent_core` 只会把建表语句带进框架层。

而事件的**形状**其实早就在框架层了——`agent_core/contracts.py` 里的 `RunEvent`、
`RunRecord`、`WorkflowType`、`TERMINAL_RUN_STATUSES`，`runs.py` 只是把它们再导出一遍。

这也正是 pi 的划法：`pi-agent-core` 管"事件是什么形状"，"会话持久化"归 `pi-coding-agent`。
本项目的差别是**两个产品共用同一份持久化**，所以它既不能留在 `services/`（那是 RAG 侧），
也不能留在 `agent/`（Step 3 要拆成两个包）。于是新开一层：

```
app/runstore/
├── runs.py         ← app/services/runs.py（run 生命周期 + 事件发号 + 租约）
└── checkpoints.py  ← app/agent/persistence.py（计划、尝试、checkpoint）
```

`checkpoints.py` 顺手对状态类型泛型化（`AgentCheckpoint[StateT]`），
不再 import `ReviewState`——存储层本来就不该认识任何一个工作流的字段。

依赖方向：`{rag, cowork} → runstore → agent_core → workpilot_ai`，
由契约 3b「runstore 不依赖产品层」守住。

### 一处**没有**修的泄漏

`WorkflowType = Literal["answer", "literature_review", "cowork"]` 仍留在
`agent_core/contracts.py`——框架层枚举了产品名。

不修的理由是挪不动：`runstore` 与 `cowork_store` 都要用它，而 `runstore → cowork_store`
已经存在，放进任何一边都会成环。它本质是 `agent_runs.workflow_type` 这一列的取值域，
跟着 store 走才对。Step 3 拆产品包时一并解决，或者放宽成 `str`。

`test_agent_core_carries_no_product_vocabulary` 显式豁免了它并写明理由——
**允许的例外要写在断言里，不能靠没人去测**。

### Step 3：劈开两个产品包

`app/agent/`（12 文件）与 `app/services/`（46 文件）整体消失，落到：

```
app/
├── rag/          40 文件  9769 行   问答 · 综述 · 资料库 · 检索 · 记忆 · 编辑器
├── cowork/       35 文件 13377 行   工作台 · 文件/Office/Shell/Web · 连接器 · Skill/MCP
├── agent_core/   11 文件  1309 行   框架层
├── runstore/      6 文件  2234 行   run · 事件 · checkpoint · 幂等租约 · 会话
├── telemetry/     7 文件  1066 行   成本与预算（Step 4 升包）
├── platform/      5 文件   280 行   鉴权会话 · 请求身份 · 限流
├── ingest/       10 文件  1873 行   文档解析（两个产品共用）
├── knowledge_contracts.py           RAG ↔ Cowork 的证据与检索契约
└── docedit.py                       两个产品共用的文档编辑原语
```

契约 6「rag 与 cowork 互不依赖」用 import-linter 的 `independence` 类型守住。

**按名字分类会错，逐个查了引用方**：

| 模块 | 名字像 | 实际是 |
|---|---|---|
| `local_dir.py` | Cowork 本地目录 | **RAG**：`sources` 表的入库同步，Cowork 不 import 它 |
| `editor.py` | Cowork 编辑器 | **RAG**：编辑的是资料库文档，带 `source_id` 与回灌 |
| `conversations.py` | RAG 会话 | **共用**：与 `runs.py` 同款双后端分派 → `runstore/` |
| `ingest/` | RAG 入库 | **共用**：Cowork 的 `read_local_pdf` 直接调 `parse_pdf` |

`editor.py` 与 `office_workspace.py` 都直接查 `sources WHERE kind='local_dir'`——
它们共享的是**表**不是模块，所以没有 import 环，但这层数据耦合值得记一笔。

**又一次"import 图不是层次真相"**：`app/cowork/tools.py` 从
`app/rag/review/write_note.py` import `acquire_invocation` / `complete_invocation` /
`fail_invocation`——**约束 9 的 `tool_invocations` 幂等租约协议，整个住在综述工作流的
写笔记模块里**，Cowork 反过来依赖它。已抽到 `app/runstore/invocations.py`。
`agent_core/idempotency.py` 里原本只有纯身份计算函数，看上去"约束 9 已经在框架层了"。

### Step 3 之后**仍然存在**的一条产品间边

```
app.cowork.office_workspace -> app.rag.markdown_ingestion
```

Cowork 在授权目录里改完 Markdown 之后要回灌资料库索引。**这不是层次错误**——
Cowork 编辑的正是 RAG 的语料，两者本来就该在这里相遇。硬拆成注入或全局钩子只会
把一个真实耦合藏进间接层，而且钩子没注册时会静默停止索引。

已在契约 6 的 `ignore_imports` 里显式登记并写明理由。收口方式是翻成事件
（Cowork 只发"文件已改"，RAG 自己订阅），留到 Step 4。

### Step 4：telemetry 成包

原计划是"把 `cost_*` 四个模块收进一个包"。**又是逐行读完之后改了**——那四个模块
每一个都拿着 `AsyncSession`，整体搬进 `packages/` 只会得到一个 import `app` 的假包。

真正的分界线和 Step 1 同形：**口径与 schema 进包，落库留应用层**。

```
packages/workpilot-telemetry/    依赖表为空，连 httpx 都不需要
├── records.py      AuditRecord + AuditSink        ← 原在 workpilot_ai/types.py
├── budget.py       BudgetGuard + CostReservation + 三个错误
├── cost.py         BatchCost 的 10 个摊销口径属性（纯 Decimal）
└── conformance.py  BudgetGuard / AuditSink 的语义一致性检查

app/telemetry/                   只剩"写进哪张表"
├── llm_calls.py cost_budget.py cost_report.py cost_overview.py
├── gpu_batches.py model_budget.py
```

**依赖方向是 `workpilot_ai → workpilot_telemetry`**，不是反过来：网关产出度量，
度量不知道谁在产出。`AuditRecord` / `AuditSink` / `BudgetGuard` 因此从
`workpilot_ai/types.py` 迁到了 telemetry 包——它们是被测量的东西的 schema，
不是模型调用的一部分。契约 2b 守住这个方向。

**为什么依赖表必须是空的**：成本口径是本项目最需要"说得清、算得准、换个存储也不变"
的东西（docs/07 §7.1 那个错误算法就是因为口径跟着实现走才会出现）。
一旦包里出现 SQLAlchemy，`BatchCost` 的公式就会开始迁就表结构。

### conformance：Protocol 管不住的那一半

pi-telemetry 的三件套是 typed schemas + reference adapters + **conformance tests**，
第三件才是关键。`BudgetGuard` 的方法签名管不住这类语义：

- 同一 `idempotency_key` 重复预留只能扣一次（网关重试、worker 复活都会撞上）
- 预留后没发出调用，释放必须还额度
- 结算按实际值**覆盖**预估，不是再加一笔
- 已结算的预留再释放不得退款

`workpilot_telemetry.conformance` 把这四条写成可复用的断言函数（不是 pytest 用例），
`tests/test_telemetry_conformance.py` 把 SQLite 实现接上去跑（原为 PostgreSQL 实现）。出第二个
实现时复制一份换 fixture 即可，断言一行不用重写。

验证过它会咬：一个不按 key 去重的假实现立刻报
`重复预留被计了 0.20，应为 0.10`。

## 接受的代价

- **零用户可见收益**。检索不会变准，Agent 不会变聪明，评测指标一分不涨。
- **`AsyncSession` 的透传链是 Step 2/3 的主要工作量**，比搬文件大得多。
  agent-core 一旦独立成包却还要 import SQLAlchemy，它就不是"只懂框架"。
  届时的解法是 agent-core 定义 `RunStore` Protocol，实现留业务层注入。
- **跨文件拆分保不住 git blame**（`services/runs.py` 拆三份时会丢）。
  纯搬迁一律用 `git mv`。
- Step 3 会改动工具目录，**属于影响输出的改动**，按 CLAUDE.md 约束 6
  必须前后跑同一份 agent-task 评测集对照。Step 1/2 不改输出，免评测。

## 考虑过的替代方案

| 方案 | 放弃理由 |
|---|---|
| 只按目录分层，不拆包 | 就是现状。`agent_core/contracts.py` 的 docstring 已经试过了，管住 799 行 |
| 只上 import-linter，不拆包 | 能挡住新增违规，但挡不住"框架层偷偷 import sqlalchemy"这类**依赖**问题；且规则写在一个文件里，容易被一行 `ignore_imports` 绕过 |
| 按认知维度分层（感知/规划/执行） | RAG 与 Cowork 会各自竖着穿过三层，切不出可复用的包，也和 PI 的划法不一致 |
| 一次性重构到位 | 195 个文件同时动，review 不可能做，回归网也失效。分四步、每步一个 PR |
