# ADR-0002 PostgreSQL + pgvector 而非专用向量库

## 背景与约束

- 单用户个人产品，语料规模预期 500–2000 篇文档 / 5–20 万 chunk
- 需要**混合检索**：向量 + 词法检索 + 元数据前置过滤
- 需要 chunk 与业务数据（documents / memories / eval_results）联表查询
- 单人 6 周，运维面越小越好
- 本机连容器运行时都要现装，基础设施每多一个组件都是净成本

## 决策

用 PostgreSQL 17 + pgvector 承担向量存储，同库承担全部业务数据与词法全文索引。
HNSW 索引起始参数 `m=16, ef_construction=64`，M2 做参数-召回-延迟对照实验（E5）。

## 考虑过的替代方案

| 方案 | 优点 | 放弃理由 |
|---|---|---|
| **Qdrant** | 向量检索性能强，原生支持 payload 过滤与混合检索，运维简单 | 多一个服务要部署和备份；chunk 与业务表跨库，无法用事务保证一致性（入库失败时会出现 PG 有文档、Qdrant 无向量的脏状态）；当前数据规模远未触及 pgvector 瓶颈 |
| **Milvus** | 亿级规模的工业级方案 | 组件多（etcd + MinIO + 多角色），对个人项目是严重的过度设计 |
| **Chroma** | 最轻，上手快 | 生产能力弱，元数据过滤与持久化不够可靠 |
| **Elasticsearch（同时做向量和 BM25）** | 一个系统解决两路检索，中文分词（IK）比 zhparser 成熟，且是真 BM25 | 资源占用高；为一路词法检索引入整套 ES 不划算；ES 的向量检索能力弱于专用方案 |
| **pg_textsearch / ParadeDB pg_search** | 在 PG 内提供真正的 BM25 排名 | 多一个扩展依赖；v1 先用原生 `ts_rank_cd`，若 E2 显示词法路是瓶颈再换 |

## 接受的代价

**这是本项目最需要坦白的一个代价**：

1. **水平扩展能力弱**。pgvector 的 HNSW 索引常驻内存，超过千万级 chunk 后
   内存与构建时间都会成为瓶颈，且无法分片。
2. **索引构建慢**。必须先灌数据后建索引，反过来会慢一个数量级。
   语料重灌时索引重建是分钟级操作。
3. **词法检索质量双重折损**。zhparser 分词弱于 IK；且 **PG 原生的 `ts_rank_cd` 是
   cover-density 排名，不是 BM25**——词频饱和与文档长度归一化的处理都不同。
   把它叫 BM25 是术语错误，会影响词法一路的召回。
   → **这个差距要在 E2 实验中量化，不能含糊带过。**
4. **过滤与向量检索的配合**。前置过滤选择性高时 HNSW 会退化（候选被过滤后不足 k 个）。
   四种分块策略必须**各建一个部分索引**，剩余过滤用 `hnsw.iterative_scan` 兜底
   （[ADR-0006](0006-分块与标注分层.md)）。

## 重新审视的触发条件

出现以下任一情况就应该迁移到 Qdrant：

- chunk 总数超过 500 万
- P95 检索延迟超过 500ms 且调参无效
- 需要支持多用户，租户隔离导致过滤选择性过高

**M2 计划补一组 pgvector vs Qdrant 的对照数据**，把这个判断从"我认为"变成"我测过"。

## 后续影响

- `chunks` 表冗余了 `doc_type` / `tags` / `invalid_at`，避免 JOIN documents 拖慢向量查询
- 词法检索走 PG 全文索引 + zhparser（`ts_rank_cd`），需要在初始化 SQL 中安装扩展
- 融合层用 RRF 而非加权求和，天然规避了两路分数量纲不同的问题（见 [04 RAG 设计](../04-知识与阅读设计.md)）
