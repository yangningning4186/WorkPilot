## 1. 技术选型

**实际落地**：Next.js 16 (App Router) · React 19 · TypeScript strict · **原生 CSS** ·
react-markdown · **自写 SSE 客户端** · Tauri 2 桌面壳。

原计划是 shadcn/ui + Tailwind + Vercel AI SDK，理由是"生态成熟、训练数据多、coding agent
生成质量高"。**两处偏离，都值得说清楚**：

- **没用 Vercel AI SDK**：事件契约是自己的（`seq` 断点续传、审批卡片、计划卡片、

- **没用 Tailwind/shadcn**：桌面壳里只有一个用户、一套主题，组件库带来的是依赖面而不是速度。

这个偏离在面试里仍然是加分的——**说明选型的依据是这个项目的约束，不是清单上的默认答案**。

## 3. 执行模型与 SSE 协议 ★

前后端唯一的实时契约，先定死再开发。

### 3.1 任务不依附 HTTP 连接

初版设计把流式输出直接绑在请求连接上，于是"关掉页面任务还继续吗"没有答案。
正确的模型是**创建 run → worker 独立执行 → 客户端订阅事件流**：

```
POST /runs                          创建 run，任务入进程内队列，立即返回 {run_id}
  │
  └─ 嵌入式 worker 独立执行 ★ 不依附任何 HTTP 连接
       └─ 每产生一个事件 → 事务写 run_events + 投影 → 提交后发唤醒通知

GET  /runs/{run_id}/events?after_seq=N    SSE：先补发历史事件，再续实时流
POST /runs/{run_id}/resume                中断确认（带 resume_token）
POST /runs/{run_id}/cancel                取消
```

**普通对话也走 run**（goal = 用户问题）。
这样刷新恢复、断线续传、时间线渲染只有一套实现，不必为对话和任务各写一遍。

`run_events` 表是**唯一真相源**（[ADR-0007](adr/0007-agent幂等与事件溯源.md)）：
实时推送和历史回放读的是同一份数据，因此不可能出现"实时看到的和刷新后看到的不一致"。

服务端先订阅唤醒通知，再按 `seq > cursor` 查库补历史；
每次醒来和心跳超时都再查库。这避免了“先查历史、后订阅”两步之间的丢事件窗口；
通知可以丢，数据库事件不能丢。

run 本身有 worker 租约与 heartbeat。页面关闭不会取消 run；worker 崩溃时 watchdog
会把普通流式回答明确标为失败，只有存在 checkpoint 且工具幂等边界成立的 Agent run
才允许自动恢复，避免把一次不确定是否已计费的模型调用静默重发。

### 3.2 事件信封

每个事件都带 `run_id` + 单调递增的 `seq`，这是续传的前提：

```ts
interface RunEventPayloadMap {
  "message.start": { message_id: string };
  "message.delta": { text: string };
  // ...其余事件逐项绑定 payload
}

type StreamEnvelope = {
  [Type in keyof RunEventPayloadMap]: {
  id: string;        // `${run_id}:${seq}` → 直接用作 SSE 的 id: 字段
  run_id: string;
  seq: string;       // DB BIGINT 的十进制字符串；比较时用 BigInt，避免 JS 精度丢失
  type: Type;
  data: RunEventPayloadMap[Type];
  };
}[keyof RunEventPayloadMap];

type EventType =
  | "message.start"   // { message_id }
  | "message.delta"   // { text }
  | "message.snapshot" // { text }，终态正文原子替换
  | "message.reset"   // 新一轮模型输出开始
  | "message.reasoning" // { text }，不进 canonical 消息
  | "citation"        // { citation_id, block_id, version_id, doc_id, title, quote,
                      //   locations: [{page_no, bbox_norm, page_width,
                      //                page_height, rotation, coord_origin}] }
  | "plan"            // { steps: PlanStep[] }
  | "step.update"     // { plan_step_id, step_idx, attempt_no, status,
                      //   tool, summary, latency_ms }
  | "tool.start"      // { step_id, step_idx, tool }
  | "tool.result"     // { step_id, tool, reused, effect_ref }
  | "tool.error"      // { step_id, tool, error }
  | "context.compacted" // { reason, mode, revision, before_tokens, after_tokens }
  | "interrupt"       // { kind, payload, resume_token }
  | "artifact"        // { kind, artifact_id, title, effect_ref }
  | "message.done"    // { message_id, tokens, cost_usd, latency_ms }
  | "run.done"        // { workflow_type, status, effect_ref }
  | "error";          // { user_message, retryable }
```

**设计要点**：

- **`id` 字段直接对应 SSE 的 `id:`**，浏览器 EventSource 断线重连时会自动带
  `Last-Event-ID` 请求头，服务端解析出 seq 后从该位置续发。**这是 B2 成立的机制**
- `citation` 是**独立事件**而非嵌在文本里——正文流到一半时引用元数据可能还没解析完，
  分开发送让引用卡片延后渲染而不阻塞正文
- `citation` 携带**完整定位元数据**（不只是 bbox 四个数），
  前端才能跨渲染器正确高亮（[04 §1.1](04-知识与阅读设计.md)）
- `step.update` 带 `attempt_no`，时间线上能看出"这步重试了几次"——
  **失败可见是可信度的一部分**
- `error` 分 `user_message`（给人看）和 `retryable`（决定是否显示重试按钮）
- `message.done` 带 token 和成本 → 前端显示"这次回答花了 ¥0.003"，
  **让成本对用户可见，这本身就是产品设计**

### 3.3 delta 事件的落库策略

流式 delta 频率极高，逐条写 DB 会拖垮吞吐。
**批量落库**：每 N 个 token 或 50ms 合并写一次；
结构化事件（citation / plan / step.update / interrupt）逐条写，不合并。

worker 正常运行时，断线不会丢正文：服务端会把内存批次继续刷入事件表，重连后补发。
在 `message.done` / `error` / `interrupt` 前必须强制 flush。只有 worker 进程崩溃时，
内存里尚未提交的最多 50ms delta 会丢失；此时消息标为 `failed`，恢复后显式重试，
不能伪装成完整回答。这个边界换来的是写入量下降一到两个数量级。

### 3.4 本机工作文件到 Artifact 的黄金流程

桌面端刻意保留两个不同入口：

1. “添加只读资料副本”上传副本，适合仅供阅读和引用的材料，不会授予原目录写权限。
2. “选择本机工作文件”使用系统文件选择器点名原文件。由于 capability 以目录为边界，界面会
   明示其所在文件夹将获得本会话读写授权；请求同时携带 `workspace_files`，把点名文件冻结进
   run checkpoint 和稳定提示块，要求 Agent 优先处理它们、不得顺手扫描无关同级文件。

服务端不信任选择器结果：每个路径必须是绝对路径、落在已授权 root 内并且仍是普通文件，校验
发生在 run 创建之前。执行后，支持格式的新建/修改文件经格式重开与 SHA-256 校验进入 Artifact；
右栏并行读取沙箱化预览和登记时冻结的有界 diff。DOCX/XLSX/PPTX/PDF 比较抽取后的段落、单元格/
公式、幻灯片文字或页文本，不把二进制 ZIP 差异伪装成用户能理解的改动。没有基线、超限、只有
版式变化和加载失败都有独立状态。

## 4. 边界情况清单 ★ 面试真正会问的

前端不熟最容易在这里翻车。**每一条都要自测到，并且能口头讲清楚处理逻辑。**

| # | 场景 | 必须的处理 |
|---|---|---|
| B1 | **流式生成中刷新页面** | `messages.status = streaming` 标记未完成消息；重进时按 `message.run_id` 调 `GET /runs/{id}/events?after_seq=0` 回放全部事件重建部分输出，run 仍在跑则自动续实时流 |
| B2 | **SSE 断线重连** | EventSource 自动带 `Last-Event-ID`（值即事件的 `id` = `run:seq`），服务端解析出 seq 从该位置续发；前端按 seq 去重 |
| B3 | **Agent 长任务执行中关闭页面** | worker 不依附 HTTP 连接，**任务继续跑完并落库**；重进时回放 `run_events` 渲染完整时间线（与实时路径同一套解析逻辑） |
| B4 | 超长回答渲染卡顿 | 增量渲染 + 虚拟滚动；Markdown 增量解析（不要每个 delta 都全量 re-parse） |
| B5 | 并发任务状态隔离 | 每个 run 独立订阅通道，前端按 `run_id` 分发，不共用全局状态 |
| B6 | 中断确认超时未响应 | `interrupt` 有 TTL，超时后 run 转 `waiting_human` 挂起并可从列表恢复 |
| B7 | 引用指向的文档已被删除 | 软删除仍允许从历史消息只读打开；仅 purge 或源文件缺失时降级为纯文本 + “原文已不存在”，不能白屏 |
| B8 | 首 token 迟迟不来 | 骨架屏 + 阶段提示（"正在检索…"/"正在生成…"），超过 10s 给取消按钮 |
| B9 | 工具执行失败 | 时间线上明示失败与重试次数，不静默吞掉——**失败可见是可信度的一部分** |
| B10 | 输入超长 / 粘贴大段文本 | 前端预估 token 并提示，超限引导用户改为上传文档 |
| B11 | Artifact 预览或 diff 不可用 | 文件索引仍可选，预览和变更分别降级；旧 Artifact 明示“没有执行前快照”，不把失败伪装成零变更 |

> B1/B2/B3 是**必答题**。它们考的不是前端技巧，是"你是否理解流式系统的状态一致性"。

## 5. 交互细节 = 产品思维的物证

JD 反复强调"产品思维""用户视角"。**嘴上说没用，这几个交互就是证据**：

1. **引用可点击定位**：点引用卡片 → 右栏打开原文 PDF → 跳到 `page_no` → 高亮 `bbox`。
   这是"可溯源"从技术承诺变成用户可感知体验的唯一途径
2. **Agent 执行过程可见**：计划先展示、每步实时更新、失败明示、可随时中断。
   把黑盒变成玻璃盒
3. **拒答要体面**：不是冷冰冰的"未找到"，而是"资料库里没有相关内容，
   要不要我基于通用知识回答？"+ 一键切换 —— 把限制转化为选择
4. **记忆可见可编辑**：`/memory` 页让用户看到 AI 记住了什么并能删改。
   这既是产品诚意，也是隐私设计
5. **成本透明**：每条回答下方显示耗时与成本。个人产品里用户是付费方，
   这个信息不该藏起来
6. **原件与副本不混淆**：只读附件和可写工作文件使用不同按钮、不同说明；执行结果固定落在
   Artifact 右栏，预览旁边就是变更统计和语义 diff，用户无需从聊天文字猜“到底改了什么”

## 6. 与 coding agent 的分工

**交给 agent**：页面布局、组件实现、样式、表单、图表、路由、基础状态管理、测试用例。

**自己想清楚再让 agent 落地**：SSE 事件协议（§3）、边界情况处理策略（§4）、
交互设计决策（§5）。这三块是面试主战场。

**每次 agent 产出后自查三件事**：
1. §4 的边界情况有没有被处理，还是只写了 happy path
2. 有没有违反 `CLAUDE.md` 的十条约束
3. 错误态、加载态、空态是不是都有——AI 生成的代码最常缺这三个
