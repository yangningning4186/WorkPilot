# 11 · MVP 边界与 Backlog

> **这份文档是唯一约束开发范围的文档。**
> [01 总体规划](01-总体规划.md) 是长期蓝图，描述项目最终形态；
> 本文档描述**实际要先做完的东西**。两者冲突时以本文档为准。

---

## 0. 为什么需要这份文档

初版排期把完整蓝图铺进 6 周，W1 一周要做完四套基础设施 + 模型网关 + 三种解析
+ 自建评测框架 + 200 篇入库 + 60 条人工标注，W5 又要同时上记忆、知识图谱、
三级缓存、8 组路由实验、成本看板和 CI 门禁。

这违反了项目自己在 [01 §1](01-总体规划.md) 写下的设计哲学：

> 功能宽度不加分，可测量的质量才加分。

**功能没有被删除，只是被排序了。** 砍单机制从"每周五反应式预演"
改为"现在就把边界画死"——区别在于：反应式砍单触发时，
时间已经花在半成品上了。

## 1. MVP 只证明四件事

一个小而完整、带真实指标的闭环，展示价值高于一个完整但做不完的设计。

| # | 命题 | 验收标准 | 现状（2026-08-16） |
|---|---|---|---|
| 1 | **文档能可靠入库** | 200 篇真实资料解析入库，抽样 20 条人工核验解析质量，失败率与失败原因有记录 | ⏳ 40 篇入库；MinerU/PyMuPDF 双路 + 质量门控 + 解析质量台账已有。**扩容到 200 篇已推迟（2026-08-14），不阻塞 M0 收口**；命题本身不降级，扩容后须在同一 suite 上重跑基线 |
| 2 | **回答能准确定位原文** | 点击引用可跳转到原文页码并高亮；引用准确率有实测数字 | ✅ 引用卡片与正文 `[S1]` 锚点都能开原文并按 `bbox_norm` 高亮（验收断言到像素）；人工引用准确率 **95.45%（42/44）** |
| 3 | **找不到时能正确拒答** | `unanswerable` 类问题正确拒答率有实测数字 | ✅ 70 条 dev 修复后生成轨上不可答 **100%（13/13）**，无冒答；可答题误拒从 21/57 降到 13/57，端到端拒答正确率从 70.0% 升到 81.4% |
| 4 | **每次优化都有真实评测数据** | 评测集 + 跑批 + 快照 diff 可用，基线数字入台账 | ✅ 80 条 human（70 dev + 10 隔离 test）；70 条 dev 检索/生成、严格配对 diff、bootstrap 与正式实验台账均已可用，test 尚未访问 |

这四条跑通之后，才逐层加 Agent、记忆、模型路由。

## 2. M0 范围（W1–W2）★ 硬门槛

### 在范围内

| 模块 | 具体到什么程度 |
|---|---|
| 基础设施 | OrbStack + compose（postgres+pgvector / redis）；Python 3.12 |
| 数据模型 | [03](03-数据模型.md) 的知识层 + 评测层 + `llm_calls` + `agent_runs/run_events`（支撑普通问答 SSE）。候选版本成功后才事务激活；**其余 Agent 四表暂不建** |
| 模型网关 | `complete/stream/embed` 统一入口 + 成本记账。**路由表只配 main + external 两档** |
| 解析 | **PDF（MinerU）+ Markdown 两种**。含双栏重排序、表格转 MD、页眉页脚剔除 |
| 数据源 | **local_dir 一个 connector** + 增量同步 |
| 分块 | **只做 `heading` 一种策略** |
| 检索 | **只做 dense 向量检索**。无词法、无 rerank、无查询改写 |
| 拒答 | 阈值先拍一个值，M1 再做 ROC 调优 |
| 引用 | 完整链路：block 字符区间 → SSE citation 事件 → 前端 PDF 定位高亮 |
| 流式 | `run_events` + SSE 续传（B1/B2/B3 三条边界必须成立） |
| 评测 | 40 条人工标注（`gold_spans`）+ 规则轨指标 + 引用语义支撑人工检查 + 跑批 + 基线台账 |
| 安全 | 鉴权 + 限流 + 每日费用上限 + 上传校验（[12](12-安全与部署.md)） |
| 交付 | 本地可验收 demo；公网部署延后到全项目最后一步，使用独立演示语料 |

### 明确不在 M0 范围

Agent 与工具 · 记忆系统 · 知识图谱 · 三档模型路由 · 任何缓存 ·
词法检索与 rerank · 四策略对照 · LLM Judge · CI 门禁 · digest · 看板

> **为什么 dense-only**：MVP 要证明的是命题 2 和 3（溯源与拒答），
> 不是检索排名有多好。混合检索是 M1 的第一个正式实验，
> 有了 dense-only 基线，它的增量才有意义。

## 3. M1 范围（W3–W4）

| 模块 | 说明 |
|---|---|
| 词法检索 + RRF 融合 | 注意：PG 原生是 `ts_rank_cd`，不是 BM25（[04 §4.1](04-RAG设计.md)） |
| rerank | bge-reranker-v2-m3 |
| 查询改写 | 指代消解 + 多查询扩展（引入 `light` 档） |
| 拒答阈值 ROC 调优 | 用 dev 集画曲线取 F1 最优点 |
| **E1 四策略对照** | 此时才建多策略 chunk + 部分索引 |
| **一个固定的综述工作流** | LangGraph 实现，但**流程固定**（筛选→抽卡→分组→对比→生成→写回），不是通用 Agent |
| Agent 扩展四表 + 幂等协议 | 补齐 `agent_plan_steps/agent_attempts/tool_invocations/agent_checkpoints`；写回笔记前必须完成副作用去重 |
| Agent 幂等补充要求 | 过期 `in_flight` / `failed` 用租约 + CAS 回收；副作用尽可能把同一幂等键传给下游 |
| 评测集 → 80 条 human | 70 dev / 10 test；test 按 document version 隔离，最终评测前不跑、不调参 |
| LLM Judge + 校准 | 当前先做六类中间校准；一致率 + quadratic weighted Kappa；`agent_task` 等真实 Agent 执行闭环后再纳入 |

> **2026-08-16 基线变更**：不再硬凑 120 条。首版 80 条自动草稿被内容门禁全部拒绝，
> 随后新增 40 条人工撰写并经作者逐条复核，与原 40 条合并为 **80 条 human**。
> 当前分布为 70 dev + 10 test，覆盖 single/multi/table/temporal/global/unanswerable 六类；
> `agent_task` 在固定工作流、真实工具 schema 与可核验产物完成前不得用占位数据补齐。
> 因此 Judge 当前目标是六类中间结论，不对七类完整可靠性作声明。

> **2026-08-16 扩展评测状态**：70 条 dev 已完成 heading / semantic finalist 检索和两轮
> heading 生成，均为 70/70、0 error，10 条 test 未访问。evidence gate 修复后，可答题实际回答
> 从 36/57 升到 44/57，不可答仍为 13/13。修复后六类 Judge 包为 70 个唯一 case
>（calibration 51 / validation 19），人工标签表和复核指南已准备；DeepSeek heavy 已通过无项目
> 数据健康检查。正式 Judge 仍待真实人工标签和该数据范围的发送授权。

> **为什么是"固定工作流"而不是通用 Agent**：
> 固定流程能把 planner 的不确定性关掉，让 HITL、幂等、断点续跑这些
> **可靠性机制**先被验证正确。通用 Agent（自由选工具、动态规划）放 backlog。

## 4. M2 范围（W5–W6）

**二选一**作为重点深挖，另一个进 backlog：

| 选项 A：长期记忆 | 选项 B：三档模型路由 |
|---|---|
| 四操作分类 + 时序冲突消解 | 路由表 + 置信度升档 |
| `/memory` 页可见可编辑 | 帕累托前沿实验（C1–C8） |
| A5 实验：记忆的可测量增益 | Judge 降档实验 |
| 讲的是**产品差异化** | 讲的是**成本工程** |

**建议选 B**：三档模型是你独有的资源，别人复现不了；
且 Judge 降档实验同时回答"评测可信吗"和"成本能降吗"两个问题。
记忆系统的时序建模设计（[ADR-0005](adr/0005-记忆采用时序有效性建模.md)）
即使不实现，也能在面试中作为设计题讲清楚。

**无论选哪个，这三项必做**：
- [ ] CI 门禁（PR smoke + nightly full）
- [ ] `core-test` 集唯一一次跑批 → 最终数字
- [ ] 博客 ×2 + demo 视频

## 5. Backlog（按解锁顺序）

进度超前时依次解锁。**不是"以后再说"，是"排在后面"**。

| # | 功能 | 解锁前提 | 预估 |
|---|---|---|---|
| 1 | M2 未选的那一项（记忆 或 路由） | M2 主线完成 | 4–5 天 |
| 2 | 通用 Agent（自由选工具 + 动态规划 + reflection） | 固定工作流的可靠性指标达标 | 4 天 |
| 3 | 语义缓存 | 有真实重复查询数据支撑收益 | 2 天 |
| 4 | 个人知识图谱（实体 + 关系 + 图查询） | 有多篇同主题论文可验证关联质量 | 5 天 |
| 5 | 每日 digest / 主动推荐 | 依赖 #4 | 2 天 |
| 6 | sparse 第三路检索 | 混合检索已有增益上限 | 2 天 |
| 7 | 更多 connector（Obsidian / Zotero / web_clip） | local_dir 稳定运行 | 各 1 天 |
| 8 | 全局摘要（GraphRAG 式社区摘要） | `global` 类评测有足够样本 | 3 天 |
| 9 | SFT 小模型做查询改写 / Judge | 一切主线完成 | 3 天 |
| 10 | pgvector vs Qdrant 对照 | 语料规模 > 20 万 chunk | 2 天 |

> **Backlog 里的东西照样写进设计文档**，因为面试问的是"你怎么想的"，
> 不全是"你写了多少行"。能说清一个没实现的设计的权衡，
> 和实现了但说不清，前者更有价值。

## 6. 范围变更纪律

1. **只能从 Backlog 往上解锁，不能往 MVP 里塞新东西。**
   想加新功能 → 先进 Backlog 排队。
2. **解锁前提没满足就不解锁**，哪怕手痒。
3. **每周日更新本文档**，把实际完成的移出范围表，把新想法放进 Backlog。
4. **删除功能需要记录理由**，写进对应里程碑的复盘。
