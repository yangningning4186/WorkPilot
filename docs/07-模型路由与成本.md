# 07 · 模型路由与成本治理

有自建推理集群，"成本治理"就从**讲概念**变成**有真实测量的帕累托实验**——
这是绝大多数候选人做不到的部分。

> **范围提示**：M0 只配 `main` + `external` 两档跑通网关；
> 三档路由、动态升档、帕累托实验、Judge 降档都在 M2。
> 语义缓存在 [Backlog #3](11-MVP边界.md)。详见 [11 MVP 边界](11-MVP边界.md)。

---

## 1. 三档模型

| 档位 | 模型 | 特性 | 部署 |
|---|---|---|---|
| `light` | **Qwen3.5-4B** | 快、便宜、可高并发；分类与抽取够用 | 自建，OpenAI 兼容 |
| `main` | **Qwen3.6-35B-A3B** | MoE 激活约 3B → **速度≈小模型、质量≈大模型**，甜点档 | 自建，OpenAI 兼容 |
| `heavy` | **DeepSeek-V4-Flash** | 最强推理，用于规划、反思、Judge、造题 | 自建，OpenAI 兼容 |
| `external` | 商用 API | 对照基线 + 集群不可用时兜底 + 线上 demo | API |

**为什么 `main` 是 MoE 很关键**：Qwen3.6-35B-A3B 每 token 只激活约 3B 参数，
所以它在延迟上接近 4B 小模型、在质量上接近稠密大模型。
这让"主力生成档"可以选一个便宜档位而不牺牲体感——
**这个甜点位置的存在，本身就是路由实验值得做的原因**。

## 2. 任务 → 档位路由表

配置在 `config/routing.yaml`，改配置不改代码——这是对照实验能跑起来的前提。

| task_type | 档位 | 理由 |
|---|---|---|
| `intent` 意图分类 | light | 纯分类，小模型足够，延迟压到最低 |
| `rewrite` 查询改写 / HyDE | light | 高频高并发，对单次质量不敏感 |
| `memory_op` 记忆抽取与四操作分类 | light | 每轮对话都跑，必须便宜 |
| `extract` 结构化抽取（论文卡片） | light → main 升档 | **置信度驱动动态升档**，见 §3 |
| `generate` 问答生成 | **main** | 甜点档，质量与成本的最优点 |
| `plan` 任务规划 | heavy | 计划错了后面全错，这里省钱是最贵的 |
| `reflect` 反思自检 | heavy | 同上 |
| `relate` 关联发现（场景 D） | main | 离线批量跑，可用便宜档 |
| `judge` 评测判分 | heavy → main | 见 §5 降档实验 |

### fallback 链

```yaml
tiers:
  main:
    primary:  {provider: vllm, endpoint: "http://<cluster>:8102", model: qwen3.6-35b-a3b}
    fallback: [{provider: vllm, endpoint: "...:8103", model: deepseek-v4-flash},
               {provider: anthropic, model: claude-sonnet-5}]
    timeout_s: 30
    max_retries: 2
```

**集群不可用 → 自动切商用 API。** 这是 R5 风险的应对，
也是面试题"没有你的集群怎么办"的答案：**改配置，不改代码**。

### 落地时定下的四条口径

实现在 `app/llm/routing.py` + `app/llm/gateway.py`，`config/routing.yaml` 入 git
（凭据写成 `${NAME}`，由白名单展开，不回落 `os.environ`——pydantic-settings 读 `.env`
时并不写回环境变量，回落只会安静地拿到空串）。

1. **fallback 不传递。** `light.fallback: [main]` 不会自动接上 `main.fallback`。
   每档写全自己的链路，"失败后依次走哪几档"只看它自己那一行，不必跨档推导。
2. **换档就换单价。** 拿 main 的单价给 external 记账，会把"集群挂了切商用 API"
   这笔最该看见的钱在成本曲线上抹平。fallback 的两次尝试各记一条 `llm_calls`，
   `tier` 记的是**实际作答**的档位而不是路由表上写的档位。
3. **流式吐字之后不再 fallback。** 已经送到浏览器的文本收不回来，换模型接着写
   会得到一段前后自相矛盾的话——比直接失败更糟。只有第一个 chunk 之前失败才换档。
4. **预算不足不 fallback。** 预留在 try 之外，`BudgetExceededError` 直接上抛：
   额度不够时换档位重试只会更快烧完。

未部署的档位（`BASE_URL` / `MODEL` 留空）线上沿链降级并在启动日志里报出全部降级路由，
评测模式则直接 `TierUnavailableError`——宁可跑不动，也不能让台账写着 heavy、
实际由别人作答。

> `routes` 的键必须是**代码真的会传的 `task_type` 字符串**，不是上表的类别名。
> 对不上不报错，只会静默落到 `default_route`，路由表看着配了其实没生效。
> `test_every_routed_task_type_actually_exists_in_the_code` 钉住这一点。

## 3. 置信度驱动的动态升档

结构化抽取任务先走 light，输出后做置信度判定，不达标才升档到 main：

```
[light] 抽取论文卡片
    ↓
置信度判定（三选一，全部是免费的确定性检查）：
  ├ schema 校验失败（字段缺失、类型错误）
  ├ 关键字段为空或值为 "unknown"
  └ 输出 logprob 均值低于阈值（若 provider 支持）
    ↓
不达标 → [main] 重做
```

**要测量的**：升档触发率、升档带来的质量增益、相比全走 main 的成本节省。
如果升档率高到 60%，这个机制就不划算——**这种"设计了但数据说不值得"的结论同样要记录**。

### 落地口径

实现在 `app/llm/escalation.py`；起始档与升档目标都由 `config/routing.yaml` 的
`routes` / `escalation` 决定，业务代码里不出现档位常量。

- **只升一档。** 链式升档（light → main → heavy）会把"这题本来就答不了"变成三倍成本。
- **升档那一轮从干净上下文重来。** 把上一档的错误输出塞进新上下文，等于请更强的模型
  去模仿一个已知错误的样例——A2 已经量到过这个坑（加失败样例反而更差）。
- **同档 repair 与升档是两层。** 一轮内部要不要 repair 属于 prompt 策略，不属于路由。
- **判定必须免费且确定。** schema 校验、关键字段空值、逐字引用比对。用另一次模型调用
  判断上一次可不可信，既贵又会把两个模型的错误叠在一起。
- `escalation` 里目标 == 起始档 = **已登记但未启用**，把 `routes` 改低一档即刻生效。

> 现状：`evidence_sufficiency` 与 `agent_extract_card` 都登记了升档目标但**未启用**
> （起始档仍是 main）。把主答路径的证据门控换到 4B 是一次会改变线上答案的变更，
> 得先有对照数据。另外 light 的 `max_model_len` 只有 8192（main 是 102400），
> 长证据类任务路由过去会直接超上下文——**分档不只是质量取舍，还有硬容量约束**。

## 4. 必做实验一：质量-成本-延迟帕累托前沿

**自建算力独有的优势**：300 条 × 8 种配置 × 3 次重复 ≈ 7000+ 次调用。
走商用 API 又贵又慢，自建集群可以随便跑。**实验台账的厚度就是这么堆出来的。**

| 配置 | generate | plan | rewrite | judge |
|---|---|---|---|---|
| C1 全重档 | heavy | heavy | heavy | heavy |
| C2 全主力 | main | main | main | main |
| C3 全轻档 | light | light | light | light |
| C4 推荐配置 | main | heavy | light | heavy |
| C5 生成降档 | light | heavy | light | heavy |
| C6 规划降档 | main | main | light | heavy |
| C7 改写升档 | main | heavy | main | heavy |
| C8 全外部 API | external ×4 | | | |

**产出**：以成本为 X 轴、答案正确率为 Y 轴的散点图 + 帕累托前沿，
标注出"再降档质量就崩"的拐点。

**要能解释的现象**（比数字本身更重要）：
- 哪个环节对档位最敏感？（预判是 `plan`，因为错误会级联放大）
- 哪个环节降档几乎无损？（预判是 `rewrite`，因为后面有检索和 rerank 兜底）
- C8 与 C4 的差距，就是"自建 vs 商用"的量化答案

## 5. 必做实验二：Judge 降档

**这是整个项目最漂亮的一个实验**，因为它同时回答了"评测可信吗"和"成本能降吗"。

```
① heavy 当 Judge，与 80 条人工标注对齐 → 一致率 + quadratic weighted Kappa + 混淆矩阵
       ↓  达标（≥85%）后，heavy 成为「基准 Judge」
② main 当 Judge，同时与人工标注、基准 Judge 比一致率
       ↓
③ 达标 → 日常 CI 回归用 main（便宜 + 快），里程碑节点用 heavy 复核
   不达标 → 分析在哪类题上失守（预判：multi_hop 和 faithfulness 最难降档）
```

**结论无论正反都能讲**：
- 一致率够高 → 省钱案例，且给出"日常用便宜档、关键节点用贵档"的工程范式
- 一致率不够 → **小模型在判分任务上的能力边界分析**，这是更有深度的技术内容

> 这题只有有自建算力的人答得出来——因为需要成千上万次 Judge 调用才能得到可靠结论。

## 6. 三级缓存

| 层 | 命中条件 | 存储 | 预期命中率 |
|---|---|---|---|
| **精确缓存** | prompt 完全一致（hash） | Redis，TTL 24h | 低，但零成本 |
| **语义缓存** | query 向量相似度 > 0.95 且过滤条件相同 | Redis + 向量比对 | 个人场景下较高（会重复问同一件事） |
| **Prompt 缓存** | 系统提示词与工具定义前缀不变 | provider 侧 | 高（前缀固定） |

**语义缓存的坑**（必须处理，否则会答错）：
- 相似 query 不代表相同意图：`"A 的优点"` vs `"A 的缺点"` 向量相似度很高
  → 缓存键必须包含检索过滤条件 + 意图分类结果，不能只用 query 向量
- 资料库更新后，旧缓存必须失效 → 缓存键带 `corpus_version`
- 阈值要用 dev 集测，**测错误命中率**而不只是命中率。
  一次错误命中的代价远大于一次 miss 的成本

**Prompt 缓存的前提**：系统提示词和工具定义必须放在 prompt 最前面且保持稳定。
把动态内容（当前时间、用户记忆）放前面会让整个前缀缓存失效——这是很常见的低级错误。

### 精确缓存的落地口径

实现在 `app/llm/cache.py`。命中率注定不高，但命中时成本是**零**，没命中也只多一次
Redis GET。所以工程重点全在**什么时候不该命中**——错误命中会安静地返回一个
"看起来对"的答案，比不命中贵得多。

四条不缓存：`temperature > 0`（缓存采样等于偷偷改成贪心解码）、评测模式
（命中意味着这条根本没过模型却被算进指标）、失败结果（一次抖动被钉住 24 小时）、
以及 Redis 异常时一律降级成未命中（缓存是纯优化，不该挡住主链路）。

**键里必须带上一切会改变输出的东西**，否则帕累托实验切八种配置会拿到上一个配置的
答案，八条曲线测出来一模一样。已经踩到过一次：`enable_thinking` 改输出但不改
messages / model / base_url，最初没进键，切换开关后直接拿到了旧设置下的答案。
现在由 provider 的 `request_fingerprint` 统一带进去。

语料更新不需要额外处理——证据正文就在 prompt 里，内容变了键就变了。这是精确缓存
相对语义缓存便宜的地方，后者才需要 `corpus_version`。

> 流式路径**刻意没接缓存**：它要同时和取消、预算结算、"吐字之后不许 fallback"
> 三件事保持正确，而它又是唯一用户可见的路径。等非流式那层的命中率数据出来再评估。

## 7. 成本核算口径

自建模型没有 API 账单，必须定义一个**可解释、口径一致**的折算方式，否则数字没有可比性。

### 7.1 错误的算法（必须避免）

```
✗ 单次成本 = (GPU 单价 / 3600) × (latency_ms / 1000) × 节点数
```

**这在并发下会严重高估。** 8 个请求并发跑在同一块 GPU 上，每个都记
"我占用了 2 秒 GPU"，加起来就是 16 秒——但实际只消耗了 2 秒的 GPU 时间。
**同一段 GPU 时间被重复计费 8 次。**

批处理越激进、并发越高，这个口径错得越离谱。
讽刺的是：它会让"提高并发"这个真正的优化在账面上显示为成本上升。

### 7.2 正确的算法：按整批 GPU wall time 摊销

```
批次 GPU 成本 = (等价云 GPU 单价 / 3600) × 批次墙钟秒数 × 节点数
单任务成本   = 批次 GPU 成本 / 批次内任务数
```

实现上给同批并发调用打同一个 `batch_id`（[03 §12](03-数据模型.md)），
按 batch 聚合后再摊到每次调用。

### 落地口径

`app/llm/batch.py` 开批次（contextvar，块内所有网关调用自动带上 `batch_id`），
`app/services/cost_report.py` 聚合摊销，`uv run python -m app.cli.cost_report [label]` 打印。

1. **墙钟必须显式测量，不能从 `created_at` 反推。** PostgreSQL 的 `now()` 返回
   **事务开始时间**，同一事务里写入的多条 `llm_calls` 时间戳完全相同，
   `max - min` 恒等于 0。所以墙钟由进程侧 `monotonic()` 测得后直接写 `gpu_batches.wall_ms`。
   这个坑不会报错，只会让所有批次的墙钟都是 0、单任务成本变成无穷大或零。
2. **只有跑批才有批次。** 线上单条问答的 `batch_id` 是 NULL——给它开批次等于把整段
   GPU 墙钟摊到一次调用上，算出一个荒谬的数字。成本报告只覆盖显式开了批次的调用。
3. **缓存命中不进分母。** 它没有消耗 GPU 时间，算进任务数会把摊销分母撑大、
   单任务成本虚低，等于把缓存的收益重复计算一遍。
4. **未收尾的批次整批排除。** 进程被杀时 `ended_at` / `wall_ms` 留空，
   用半个墙钟摊出来的单价是错的——宁可缺一条数据，也不要一条错数据。
5. **没配单价就硬失败。** 默认 0 会让报告照样生成、图照样能画，但每个数字都是错的
   且看不出来。`GPU_PRICE_SOURCE` 也必填，见 §7.3。

一次 8 并发的实测（light 档，8 次调用 / 0.51s 墙钟）：平均并发 6.59。
也就是说 §7.1 那个错误算法在这次跑批上会把成本高估 **6.59 倍**。

### 7.3 必须同时报告的四个数

只报"每次问答 ¥0.003"是不够的，因为它强依赖当时的并发度：

| 指标 | 为什么必须报 |
|---|---|
| 每千 token 成本 / 每任务成本 | 两种口径都给，便于横向比较 |
| **吞吐**（tasks/s 或 tokens/s） | 成本的分母 |
| **并发度** | 同一模型在并发 1 和并发 16 下的单位成本可以差一个数量级 |
| **GPU 利用率** | 说明摊销是否合理；利用率 30% 时的成本数字没有参考价值 |

> **最后一行目前只做到一半，要说清楚。** 报告给的是**客户端观测的占用率**
> （所有调用忙碌时间之和 / 墙钟 / 节点数），它回答"这批跑批把端点喂饱了没有"。
> 这**不是** GPU SM 利用率——后者要在推理机上采 `nvidia-smi`，本项目没有那条采集
> 链路。占用率足以支撑"利用率 30% 时的成本数字没有参考价值"这层判断，
> 但报告里必须叫它占用率，把它写成"GPU 利用率"就是拿一个没测的数字冒充测量。

- 等价云单价取公开的同规格实例价格，**在报告中明确写出取值与来源**
- 商用 API 用真实计费，直接可比
- 帕累托实验（§4）的每个配置都要在**相同并发设定**下测，否则对比无效

> 面试时不要说"我的成本降低了 X%"就完事，要能说出**折算口径**。
> 说不清口径的成本数字，懂行的人一问就知道是拍脑袋——
> 而"我一开始用 latency × 单价，后来发现并发下会重复计费，改成按批摊销"
> 这个纠错过程本身就是很好的回答。

### 7.4 评测跑批必须关掉 fallback

线上允许档位 fallback，**评测时必须禁用**。
否则 `eval_runs.config` 记的是 `heavy`，实际因超时切到了商用 API，
指标是另一个模型打出来的且你不知道。详见 [06 §4.4](06-评测体系.md)。

## 8. 预算与熔断

| 层级 | 限制 | 超限行为 |
|---|---|---|
| 单次请求 | max_tokens / timeout | 截断或报错 |
| Agent run | token / 调用数 / 墙钟时间（[03 数据模型](03-数据模型.md) `agent_runs`） | `budget_exceeded`，展示已完成部分，询问是否追加 |
| 每日 | 总 token 上限 | 告警 + 降档运行 |
| 评测跑批 | 单次跑批预算上限 | 中止并保留部分结果 |

**反思循环是最大的成本风险**：一个没有 `max_replans` 的 reflector
可以在一夜之间烧掉几百万 token。这不是理论风险，是 Agent 项目的经典事故。

## 9. 成本看板

数据源是 `llm_calls` 表（每次调用都记账）。看板字段：

- 按 `task_type` × `tier` 的调用量、token、成本分布 → **找出成本大头在哪**
- 缓存命中率（分三级）与节省的 token
- P50/P95 延迟、TTFT，按档位拆分
- 每日成本趋势 + 优化动作的时间标记（能看到"哪天做了什么优化，成本掉了多少"）
- 自建 vs 商用的对照曲线

> 看板不是为了好看，是为了**在博客和面试里能贴一张有说服力的图**。
> 一张标注了优化时间点的成本下降曲线，胜过一千字描述。
