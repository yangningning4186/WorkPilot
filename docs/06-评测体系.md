# 06 · 评测体系

**这是本项目的核心差异化。**

三份目标 JD 都点名"效果评估与反馈优化闭环""系统性评估 Agent 效果""质量保障体系"，
而绝大多数候选人的项目停在"我做了个 RAG 聊天机器人"，一问"提升了多少"就哑火。

所以评测不是配套设施，是**主线之一**，投入权重最高。

> **面向个人产品在这里有决定性优势**：语料是我自己读过的，所以我有能力亲手标注 gold answer 和 gold span；
> badcase 来自我每天的真实使用。企业向项目只能用合成数据 + 编造的测试用例，
> 标注质量和反馈闭环都是虚的。

---

## 1. 评测集设计

### 1.1 七类分层

| 类别 | 占比 | 说明 | 例子 |
|---|---|---|---|
| `single_hop` | 25% | 单个 chunk 即可回答 | "InfoNCE 的温度系数默认取多少？" |
| `multi_hop` | 20% | 需要跨文档/跨段落综合 | "这两篇构造负样本的方式有什么区别？" |
| `table` | 10% | 答案在表格里，考验解析 | "论文 X 在 ImageNet 上的 top-1 是多少？" |
| `temporal` | 10% | 需要区分版本/时间 | "我最新版笔记里对这个方法的评价是什么？" |
| `unanswerable` | **15%** | 资料库里根本没有 | "论文 Y 的第 5 个实验结论是什么？"（Y 不在库里） |
| `global` | 10% | 答案不在任何单 chunk 里 | "我这三个月读的论文主要关注哪几个方向？" |
| `agent_task` | 10% | 多步任务，判工具序列与产物 | "把这 5 篇整理成对比表格存进笔记" |

**`unanswerable` 必须占 15% 以上。** 它是幻觉的唯一体检项，也是最容易被忽略的一类——
只测可答问题的评测集，会奖励一个什么都敢答的模型。

### 1.2 规模与切分

| 数据集 | 目标规模 | 用途 | 使用频率 |
|---|---|---|---|
| `core-dev` | 40 (M0) → 100 (M1) → 150 (M2) | 日常迭代、参数调优 | 每次改动 |
| `core-test` | 20 (M1) → 50 (M2) | 里程碑验收 | **只在里程碑节点跑**，防过拟合（R7） |
| `regression` | 持续增长 | badcase 回流 | CI 每次 |
| `smoke` | 20–30，从 dev 抽 | PR 门禁（纯规则轨，无 Judge） | 每个 PR |

> 规模是**渐进的**：M0 只需 40 条就能拿到有意义的基线。
> 一次标 300 条会挤掉 M0 的其他工作，而基线晚一天风险都在放大。

> `core-test` 的纪律必须严格。看多了 test 集的结果，人就会不自觉地对着它调参，
> 那这个集就废了。**每看一次都要在实验台账里记一笔。**

### 1.3 标注 schema

```yaml
id: q-0042
category: multi_hop
question: "SimCLR 和 MoCo 构造负样本的方式有什么区别？"
gold_answer: |
  SimCLR 在同一 batch 内取其他样本作为负样本，因此负样本数受 batch size 限制；
  MoCo 使用动量编码器维护一个队列作为负样本库，负样本数与 batch size 解耦。

# ★ 标注锚定在「版本 + 字符区间」，不是 chunk_id
#   这样同一份标注可以给同一解析版本下的任意分块策略打分
gold_spans:
  - {version_id: "01931f...", char_start: 18420, char_end: 18990,
     quote: "...", note: "SimCLR 负样本"}
  - {version_id: "01932a...", char_start:  9310, char_end:  9840,
     quote: "...", note: "MoCo 队列"}

gold_tools: []                    # agent_task 类才填
constraints:
  must_include: ["队列", "batch"]      # 规则轨硬性检查
  must_not_include: ["BERT"]           # 常见幻觉词
temporal_ctx: null                # 时效类问题的时间基准（timestamptz）
difficulty: 2
origin: human                     # human | synthetic | badcase
```

> **为什么不能标 `chunk_id`**：四种分块策略切出的 chunk 边界和 ID 都不同，
> 标注绑死在某一套 chunk 上，E1 四策略对照就无法公平比较，
> 且任何一次重新分块都会作废全部人工标注——而标注是这个项目最贵的资产。
> 完整论证见 [ADR-0006](adr/0006-分块与标注分层.md)。

`char_start/end` 是 NFC 文本的 Unicode code-point offset，不是 UTF-8 byte offset，
也不是浏览器的 UTF-16 offset。`quote` 是校验锚：标注入库和评测跑批前都要验证
`full_text[char_start:char_end] == quote`，不一致就将样本标为 stale，禁止静默继续。

这只保证**重新分块**不使标注失效。换解析器或解析器升级会生成新 `version_id`，
旧 span 不会自动迁移；需要单独的 quote/context 对齐工具辅助重标，并经人工确认。

### 1.4 构造流程

1. **人工种子渐进到 60 条**：M0 先完成 40 条，M1 再补到 60 条；都来自自己读过的资料，作为 Judge 校准的高质量基准
2. **模型辅助扩充**：用重推理档模型读 chunk 生成候选问答对 → **人工逐条审核**（不审核的合成题不能用）
3. **badcase 回流**：真实使用中点踩的样本 → 标注 → 进 `regression`
4. **对抗构造**：针对 `unanswerable`，故意问库里没有但看起来很像有的问题

## 2. 双轨判分

单靠 LLM Judge 不可信，单靠规则又覆盖不了语义。两轨并行，**分歧本身就是信号**。

### 2.1 gold_spans → chunk 的映射（检索指标的基础）

评测时把标注区间映射成"该策略下哪些 chunk 算相关"：

```python
def hits(chunk, span, theta=0.5) -> bool:
    """chunk 与 gold span 的字符区间重叠比例达到阈值即算命中"""
    overlap = max(0, min(chunk.char_end, span.char_end)
                   - max(chunk.char_start, span.char_start))
    return overlap / (span.char_end - span.char_start) >= theta

# span-level recall：标注的关键段落有几个被召回了
span_recall_at_k = len({s for s in gold_spans
                        if any(hits(c, s) for c in top_k)}) / len(gold_spans)

# 标准 nDCG：每个 chunk 的相关度独立于排序位置
rel(c) = min(1.0, sum(overlap_ratio(c, s) for s in gold_spans))

# 另报 α-nDCG：把 gold span 当 subtopic，对重复覆盖按 α 衰减
# α 固定为 0.5，并与其他评测参数一起记录
```

**θ = 0.5 是可调参数**，在 dev 集上做敏感性检查并在台账中记录取值。

span-level recall 比 chunk-id recall 更贴近“关键证据有没有找到”，
但它单独使用仍会奖励过大 chunk：一个长 chunk 完整包住 span 就能得分。
所以 E1 跨分块策略比较必须同时报告：

- 固定 top-k 的 `span_recall@k`；
- **固定检索 token budget** 的 span recall（主比较口径）；
- 标准 `nDCG@k`、`α-nDCG@k`、`context_precision` 和上下文冗余率；
- 端到端答案质量与延迟。

这样才能把“找到了”与“向模型塞了多少无关文本”同时纳入判断。

### 2.2 规则轨（确定、免费、可复现）

| 指标 | 计算方式 |
|---|---|
| `span_recall@k` / `ndcg@k` / `alpha_ndcg@k` / `mrr` | 检索结果 vs `gold_spans`，区间重叠运算（§2.1） |
| `citation_validity` | 引用格式是否合法、block/version 是否真实存在、quote 是否匹配（不代表语义支撑） |
| `constraint_pass` | `must_include` / `must_not_include` 命中检查 |
| `schema_compliance` | 结构化输出的字段齐全度（场景 C） |
| `tool_sequence_match` | 工具调用序列 vs `gold_tools`（编辑距离） |
| `refusal_detected` | 是否触发拒答（正则 + 拒答标记位） |

### 2.3 模型轨（LLM-as-Judge）

| 指标 | Judge 看到什么 |
|---|---|
| `answer_correctness` | 问题 + gold_answer + 实际答案 → 0/1/2 三档 |
| `faithfulness` | 答案的每个论断 + 检索到的上下文 → 是否被支撑 |
| `citation_accuracy` | 答案句 + 它引用的 block 证据片段 → 该引用是否真的支撑这句话 |
| `completeness` | 是否遗漏 gold_answer 中的关键点 |

**Judge 必须输出理由**（存进 `eval_results.judge_raw`），
否则无法人工复核，也无法诊断 Judge 本身出了什么问题。

## 3. Judge 校准（可信度的地基）

**没校准过的 Judge 打出来的分是废纸。** 这一步决定了后面所有数字有没有意义。

```
① 人工标注 80 条（从 core-dev 抽样，覆盖全部 7 个类别）
        ↓
② 重推理档 (DeepSeek-V4-Flash) 当 Judge，跑同样 80 条
        ↓
③ 计算一致度（三个都要，缺一不可）：
     · 准确率
     · quadratic weighted Kappa   ← 见下方说明
     · 混淆矩阵 + 分类别一致率     ← 定位在哪类题上失守
        ↓
   加权 Kappa ≥ 0.85 ?
   ├─ 是 → 采纳为基准 Judge
   └─ 否 → 分析分歧样本 → 改 rubric → 回到 ②（最多迭代 3 轮）
        ↓
④ 分歧样本归因：是 rubric 模糊？是人工标错？还是 Judge 确实判错？
        ↓
⑤ 【降档实验】主力档 (Qwen3.6-35B-A3B) 当 Judge，与「已校准的基准 Judge」+ 人工标注比一致度
        ↓
   达标 → 日常回归用主力档，只在里程碑用重推理档复核
```

### 为什么必须用 quadratic weighted Kappa 而不是普通 Kappa ★

打分是 **0/1/2 的有序标签**，不是无序类别。
普通（unweighted）Cohen's Kappa 把"把 0 判成 2"和"把 1 判成 2"当作**同等严重的错误**——
但显然前者是灾难性误判，后者只是边界模糊。

**quadratic weighted Kappa** 按 `(i-j)²` 加权惩罚，
差 2 档的惩罚是差 1 档的 4 倍，这才符合有序标签的语义。

同时必须看**混淆矩阵**：一个整体 Kappa 0.87 的 Judge，
可能在 `unanswerable` 类上系统性地把"该拒答"判成"回答正确"——
汇总数字看不出来，分类别一致率才看得出来。

### rubric 设计要点

- 三档打分（0/1/2）比五档更稳定——人和模型在中间档位上都难以稳定区分
- 每档给具体例子，不要只给形容词
- 强制先输出理由再输出分数（先给分会让理由沦为事后合理化）
- 检查长答案偏好：Judge 有系统性偏爱长答案的倾向，
  用同一答案的长短两个版本做对照检验

> 面试题"你怎么知道你的 Judge 判得准"——答案是这整套流程 + 加权 Kappa 的具体数值。
> **能说出"因为是有序标签所以用 quadratic weighted Kappa"，是专业度的分水岭。**

## 4. CI 门禁

> 借鉴 promptfoo 的"评测即代码 + 快照 diff"范式。

### 4.1 分层跑批 ★

**不能每个 PR 都跑全量 + LLM Judge。** 分三层：

| 触发 | 数据集 | 判分 | 时长 | 在哪跑 |
|---|---|---|---|---|
| **每个 PR** | `smoke` 20–30 条 + `regression` | **纯规则轨**（检索指标、格式、约束、拒答检出） | < 3 min | GitHub Actions |
| **每晚** | 完整 `core-dev` | 规则轨 + LLM Judge | ~30 min | 本地/集群，结果回传 |
| **里程碑** | `core-test` | 全量 + 人工抽检 | — | 本地 |

M0 还没有校准后的 Judge，因此不宣称自动得到“引用准确率”。
M0 自动指标名为 `citation_validity`，另对 40 条样本人工判定引用是否真正支撑答案；
M1 Judge 校准后才把语义支撑指标自动化为 `citation_accuracy`。

**为什么 PR 不能跑 Judge——理由不是"太贵"**：
自建集群上 Judge 调用几乎不花钱。真正的硬约束是
**GitHub Actions runner 连不到家里的推理集群**。
在 CI 里跑 Judge 就必须走商用 API，那才是真花钱且慢。

PR 检索门禁使用随仓库版本化的小型公开 fixture 语料和预计算 embedding，
不连接私人数据库或自建集群。涉及 embedding 模型本身的变更只在 nightly 重建索引评测；
PR smoke 负责发现其余检索与输出逻辑的确定性回退。

> 这个区别要记牢：面试被问"CI 为什么不跑全量"时，
> 答"太贵"在有自建算力的前提下是自相矛盾的，答"runner 到不了集群"才成立。

```yaml
# .github/workflows/eval-gate.yml（示意）
on: [pull_request]
jobs:
  smoke-gate:
    steps:
      - 跑 smoke + regression（纯规则轨，不调 LLM Judge）
      - 与 main 分支的 baseline 快照比对
      - 任一门禁条件不满足 → 标记失败，阻断合入
      - 无论成败都把 diff 报告贴到 PR 评论
```

### 4.2 门禁阈值

| 条件 | 阈值 | 理由 |
|---|---|---|
| `answer_correctness` 相对 baseline | 下降 ≤ 2pt | 留出评测噪声空间 |
| `faithfulness` | 绝对值 ≥ 0.90 | 幻觉是产品的生死线，不接受回退 |
| `refusal_correctness`（unanswerable 类） | ≥ 0.90 | 同上 |
| `span_recall@10` 相对 baseline | 下降 ≤ 3pt | 检索退化的早期预警 |
| `regression` 集 | **不允许任何一条从通过变失败** | 修好的 bug 不许再犯 |
| `cost_per_query` | 上涨 ≤ 20% | 防止用堆 token 换指标 |
| `p95_latency` | 上涨 ≤ 30% | 同上 |

上表是“所有层级的完整门禁集”，不是 PR smoke 都能计算。
PR 只执行 `citation_validity` / 约束 / 拒答检出 / 检索指标 / regression；
`answer_correctness` / `faithfulness` / `citation_accuracy` 只在 nightly 与里程碑跑批中门禁。

### 4.3 噪声控制与显著性 ★

LLM 输出有随机性，`temperature=0` 也不能完全消除
（batch 组成、并发调度、MoE 路由都会引入变化）。

**"三次取中位数"不足以支撑"显著提升"的结论。** 正确做法：

| 方法 | 用途 |
|---|---|
| **逐样本 paired bootstrap** | 主力方法。对 N 个样本的**配对差值**重采样 10000 次，给出 Δ 的 95% 置信区间。**置信区间跨 0 就是"无显著差异"，不能写成提升** |
| 固定 seed + 重复 3 次 | 估计单次跑批的方差，判断噪声地板在哪 |
| 分类别报告 | 整体持平可能掩盖"A 类涨 B 类跌"，必须分类别看 |

**门禁阈值必须大于噪声地板**，否则会天天误报——
最后所有人都习惯性点忽略，门禁就名存实亡了。所以顺序是：
**先测噪声，再定阈值**，不能反过来。

### 4.4 评测跑批默认禁用 fallback ★

线上允许模型档位 fallback（集群挂了要能兜底），**但评测时必须关掉**。

否则会发生：`eval_runs.config` 记录用的是 `heavy` 档，
实际跑的时候集群超时自动切到商用 API，
指标是另一个模型打出来的——**实验不可复现，而且你不知道**。

```
评测模式：fallback_enabled = false
  ├ 调用失败 → 该 run 直接失败，不静默降级
  └ 每次调用记录 actual provider/model 到 eval_runs.actual_models
```

## 5. 实验台账

**这是面试的核心弹药库。**
面试官问"你做了哪些优化、分别提升了多少"时，能打开一份逐条记录的台账，
和只能口述"我做了混合检索感觉好一些"，是完全不同的两个候选人。

每个实验在 `docs/experiments/` 建一个 md，格式见该目录的 `TEMPLATE.md`。

### 铁律

1. **一次只改一个变量**，否则归因不了
2. **先写假设再跑**——事后编的假设没有价值，而且会导致选择性解读
3. **负优化必须记录**。这是最有价值的部分：
   > "我以为语义分块会赢，结果在论文语料上比标题分块低 6 个点，
   > 原因是学术写作的章节结构本身就是作者做好的语义分块。"

   这段话在面试里的分量，超过任何一个正向指标。
4. **记录 `git_sha` + `config_hash`**，任何数字都能追溯到确切的代码与配置

## 6. 线上反馈闭环

```
真实使用中点踩
    ↓
feedback 表（含 reason：事实错误 / 引用不对 / 该拒答 / 格式问题 / 太慢）
    ↓
每周固定时间人工过一遍（个人产品，量不大，一次 20 分钟）
    ↓
可复现的 → 标注 gold → 进 regression 集，promoted_to_eval = true
    ↓
CI 门禁保证同类问题不再复发
    ↓
形成"发现问题 → 固化为测试 → 永不回退"的棘轮
```

**这才是 JD 里"效果评估与反馈优化闭环"的完整形态。**
关键在最后一步：修复不是终点，把修复固化成回归测试才是。

## 7. 评测框架实现

**自建，不做 Ragas / DeepEval 的壳。**
理由：评测是本项目的核心差异化，必须自己实现才能在面试中讲透每个指标的算法细节。
借鉴它们的**思想**（Ragas 的指标分解、DeepEval 的 pytest 集成、promptfoo 的快照 diff），
不引入它们的抽象。

```
eval/
├── datasets/           YAML 格式的评测集（进 git，可 review、可 diff）
├── mapping.py          ★ gold_spans → chunk 的区间映射（§2.1）
├── metrics/
│   ├── retrieval.py    span_recall / ndcg / alpha_ndcg / mrr / context_precision
│   ├── generation.py   correctness / faithfulness / citation / refusal
│   ├── agent.py        success / step_efficiency / recovery_rate
│   └── judge.py        LLM Judge 封装 + rubric 管理
├── stats.py            ★ paired bootstrap 置信区间 + quadratic weighted Kappa + 混淆矩阵
├── runner.py           并发跑批（评测模式强制 fallback_enabled=false）
├── compare.py          两次 run 的快照 diff + 显著性判定，输出 markdown 报告
├── calibrate.py        Judge 校准：加权 Kappa + 分类别一致率
└── gate.py             CI 门禁判定
```

```bash
uv run python -m eval.run --dataset core-dev --label exp-hybrid-rrf --no-fallback
uv run python -m eval.compare baseline exp-hybrid-rrf        # 带 bootstrap 置信区间
uv run python -m eval.calibrate --judge heavy --human-labels labels/round1.yaml
uv run python -m eval.gate --against main --dataset smoke    # PR 门禁，纯规则轨
```

## 8. 必须能答上来的问题

1. 你的 Judge 怎么验证判得准？→ §3，说出**加权** Kappa 值，并说明为什么是加权
2. 为什么用 quadratic weighted Kappa？→ 0/1/2 是有序标签，差 2 档不该与差 1 档同罚
3. 你的标注为什么不绑 chunk_id？→ [ADR-0006](adr/0006-分块与标注分层.md)，
   否则四策略对照无法公平比较，且重新分块就会全部作废
4. 评测集会不会过拟合？→ dev/test 分离 + test 集使用纪律 + badcase 持续注入
5. LLM 输出有随机性，你的指标可信吗？→ **paired bootstrap 置信区间**，
   跨 0 就写"无显著差异"；固定 seed 重复跑估噪声地板
6. 一个改动在 A 类涨、B 类跌，怎么决策？→ 看真实分布下的加权收益，
   且 `faithfulness` 和 `refusal` 是不允许交换的硬底线
7. 有没有做了但效果变差的优化？→ **必须准备一个真实案例**，这题答得好加分最多
8. 门禁阈值怎么定的？→ 先测噪声地板，阈值必须大于噪声，否则误报会让门禁失效
9. CI 为什么不跑全量？→ **不是因为贵**（自建集群 Judge 几乎免费），
   是 CI runner 连不到集群，跑 Judge 就得走商用 API
10. 评测时 fallback 为什么要关？→ §4.4，否则 config 记录与实际执行不符，实验不可复现
11. 为什么不直接用 Ragas？→ §7
