# 06 · 评测体系

**这是本项目的核心差异化。**

三份目标 JD 都点名"效果评估与反馈优化闭环""系统性评估 Agent 效果""质量保障体系"，
而绝大多数候选人的项目停在"我做了个 RAG 聊天机器人"，一问"提升了多少"就哑火。

所以评测不是配套设施，是**主线之一**，投入权重最高。

> **面向个人产品在这里有决定性优势**：语料是我自己读过的，所以我有能力亲手标注 gold answer 和 gold span；
> badcase 来自我每天的真实使用。企业向项目只能用合成数据 + 编造的测试用例，
> 标注质量和反馈闭环都是虚的。

---

## 1. 评测集设计

### 1.1 七类分层

| 类别 | 占比 | 说明 | 例子 |
|---|---|---|---|
| `single_hop` | 25% | 单个 chunk 即可回答 | "InfoNCE 的温度系数默认取多少？" |
| `multi_hop` | 20% | 需要跨文档/跨段落综合 | "这两篇构造负样本的方式有什么区别？" |
| `table` | 10% | 答案在表格里，考验解析 | "论文 X 在 ImageNet 上的 top-1 是多少？" |
| `temporal` | 10% | 需要区分版本/时间 | "我最新版笔记里对这个方法的评价是什么？" |
| `unanswerable` | **15%** | 资料库里根本没有 | "论文 Y 的第 5 个实验结论是什么？"（Y 不在库里） |
| `global` | 10% | 答案不在任何单 chunk 里 | "我这三个月读的论文主要关注哪几个方向？" |
| `agent_task` | 10% | 多步任务，判工具序列与产物 | "把这 5 篇整理成对比表格存进笔记" |

**`unanswerable` 必须占 15% 以上。** 它是幻觉的唯一体检项，也是最容易被忽略的一类——
只测可答问题的评测集，会奖励一个什么都敢答的模型。

### 1.2 规模与切分

| 数据集 | 目标规模 | 用途 | 使用频率 |
|---|---|---|---|
| `core-dev` | 40 (M0) → 100 (M1) → 150 (M2) | 日常迭代、参数调优 | 每次改动 |
| `core-test` | 20 (M1) → 50 (M2) | 里程碑验收 | **只在里程碑节点跑**，防过拟合（R7） |
| `regression` | 持续增长 | badcase 回流，**固化为 `backend/tests/` 用例** | 每个 PR（pytest） |
| ~~`smoke`~~ | — | **已取消**，理由见 §4.1 | — |

> 规模是**渐进的**：M0 只需 40 条就能拿到有意义的基线。
> 一次标 300 条会挤掉 M0 的其他工作，而基线晚一天风险都在放大。

> `core-test` 的纪律必须严格。看多了 test 集的结果，人就会不自觉地对着它调参，
> 那这个集就废了。**每看一次都要在实验台账里记一笔。**

### 1.3 标注 schema

```yaml
id: q-0042
category: multi_hop
question: "SimCLR 和 MoCo 构造负样本的方式有什么区别？"
gold_answer: |
  SimCLR 在同一 batch 内取其他样本作为负样本，因此负样本数受 batch size 限制；
  MoCo 使用动量编码器维护一个队列作为负样本库，负样本数与 batch size 解耦。

# ★ 标注锚定在「版本 + 字符区间」，不是 chunk_id
#   这样同一份标注可以给同一解析版本下的任意分块策略打分
gold_spans:
  - {version_id: "01931f...", char_start: 18420, char_end: 18990,
     quote: "...", note: "SimCLR 负样本"}
  - {version_id: "01932a...", char_start:  9310, char_end:  9840,
     quote: "...", note: "MoCo 队列"}

# 每个问题事实可以有多个等价证据位置；第一个 alternative 是上面的 canonical span
gold_evidence_groups:
  - fact_id: simclr-negatives
    alternatives: [{version_id: "01931f...", char_start: 18420, char_end: 18990, quote: "..."}]
  - fact_id: moco-negatives
    alternatives:
      - {version_id: "01932a...", char_start: 9310, char_end: 9840, quote: "..."}
      - {version_id: "01932a...", char_start: 22110, char_end: 22480, quote: "..."}

gold_tools: []                    # agent_task 类才填
constraints:
  must_include: ["队列", "batch"]      # 规则轨硬性检查
  must_not_include: ["BERT"]           # 常见幻觉词
temporal_ctx: null                # 资料库版本快照时点；不得填论文事件日期
difficulty: 2
origin: human                     # human | synthetic | badcase
```

> **为什么不能标 `chunk_id`**：四种分块策略切出的 chunk 边界和 ID 都不同，
> 标注绑死在某一套 chunk 上，E1 四策略对照就无法公平比较，
> 且任何一次重新分块都会作废全部人工标注——而标注是这个项目最贵的资产。
> 完整论证见 [ADR-0006](adr/0006-分块与标注分层.md)。

`char_start/end` 是 NFC 文本的 Unicode code-point offset，不是 UTF-8 byte offset，
也不是浏览器的 UTF-16 offset。`quote` 是校验锚：标注入库和评测跑批前都要验证
`full_text[char_start:char_end] == quote`，不一致就将样本标为 stale，禁止静默继续。

这只保证**重新分块**不使标注失效。换解析器或解析器升级会生成新 `version_id`，
旧 span 不会自动迁移；需要单独的 quote/context 对齐工具辅助重标，并经人工确认。

### 1.4 构造流程

1. **人工种子渐进到 60 条**：M0 先完成 40 条，M1 再补到 60 条；都来自自己读过的资料，作为 Judge 校准的高质量基准
2. **模型辅助扩充**：用重推理档模型读 chunk 生成候选问答对 → **人工逐条审核**（不审核的合成题不能用）
3. **badcase 回流**：真实使用中点踩的样本 → 标注 → 进 `regression`
4. **对抗构造**：针对 `unanswerable`，故意问库里没有但看起来很像有的问题

## 2. 双轨判分

单靠 LLM Judge 不可信，单靠规则又覆盖不了语义。两轨并行，**分歧本身就是信号**。

### 2.1 事实组 × 等价证据 → chunk 的映射（检索指标的基础）

评测时把标注区间映射成"该策略下哪些 chunk 算相关"：

```python
def hits(chunk, span, theta=0.5) -> bool:
    """chunk 与 gold span 的字符区间重叠比例达到阈值即算命中"""
    overlap = max(0, min(chunk.char_end, span.char_end)
                   - max(chunk.char_start, span.char_start))
    return overlap / (span.char_end - span.char_start) >= theta

# 事实组 recall：每个回答要点命中任一等价证据即可
group_hit(R) = any(hits(c, s) for c in top_k for s in R.alternatives)
span_recall_at_k = len({R for R in gold_evidence_groups if group_hit(R)}) \
                   / len(gold_evidence_groups)

# 标准 nDCG：每个 chunk 的相关度独立于排序位置
rel(c) = min(1.0, sum(max(overlap_ratio(c, s) for s in R.alternatives)
                      for R in gold_evidence_groups))

# 另报 α-nDCG：把事实组当 subtopic，对重复覆盖按 α 衰减
# α 固定为 0.5，并与其他评测参数一起记录
```

**θ = 0.5 是可调参数**，在 dev 集上做敏感性检查并在台账中记录取值。

字段名 `span_recall` 为历史报告兼容保留，benchmark-v2 起实际衡量事实组覆盖。
它比 chunk-id recall 更贴近“回答所需事实有没有找到”，
但它单独使用仍会奖励过大 chunk：一个长 chunk 完整包住 span 就能得分。
所以 E1 跨分块策略比较必须同时报告：

- 固定 top-k 的 `span_recall@k`；
- **固定检索 token budget** 的 span recall（主比较口径）；
- 标准 `nDCG@k`、`α-nDCG@k`、`context_precision` 和上下文冗余率；
- 端到端答案质量与延迟。

这样才能把“找到了”与“向模型塞了多少无关文本”同时纳入判断。

### 2.2 规则轨（确定、免费、可复现）

| 指标 | 计算方式 |
|---|---|
| `span_recall@k` / `ndcg@k` / `alpha_ndcg@k` / `mrr` | 检索结果 vs `gold_spans`，区间重叠运算（§2.1） |
| `citation_validity` | 引用格式是否合法、block/version 是否真实存在、quote 是否匹配（不代表语义支撑） |
| `constraint_pass` | `must_include` / `must_not_include` 命中检查 |
| `schema_compliance` | 结构化输出的字段齐全度（场景 C） |
| `tool_sequence_match` | 工具调用序列 vs `gold_tools`（编辑距离） |
| `refusal_detected` | 是否触发拒答（正则 + 拒答标记位） |

### 2.3 模型轨（LLM-as-Judge）

| 指标 | Judge 看到什么 |
|---|---|
| `answer_correctness` | 问题 + gold_answer + 实际答案 → 当前冻结的 binary v2 为 0/1；三档属于后续 rubric，必须重新校准 |
| `faithfulness` | 答案的每个论断 + 检索到的上下文 → 是否被支撑 |
| `citation_accuracy` | 答案句 + 它引用的 block 证据片段 → 该引用是否真的支撑这句话 |
| `completeness` | 是否遗漏 gold_answer 中的关键点 |

**Judge 必须输出理由**（存进 `eval_results.judge_raw`），
否则无法人工复核，也无法诊断 Judge 本身出了什么问题。

## 3. Judge 校准（可信度的地基）

**没校准过的 Judge 打出来的分是废纸。** 这一步决定了后面所有数字有没有意义。

```
① calibration 51 条用于冻结 rubric；validation 19 条由作者独立盲标
        ↓
② 重推理档 (DeepSeek-V4-Flash) 当基准 Judge，跑同样 70 条
        ↓
③ 计算一致度（三个都要，缺一不可）：
     · 准确率
     · quadratic weighted Kappa   ← 见下方说明
     · 混淆矩阵 + 分类别一致率     ← 定位在哪类题上失守
        ↓
   加权 Kappa ≥ 0.85 ?
   ├─ 是 → 采纳为基准 Judge
   └─ 否 → 分析分歧样本 → 改 rubric → 回到 ②（最多迭代 3 轮）
        ↓
④ 分歧样本归因：是 rubric 模糊？是人工标错？还是 Judge 确实判错？
        ↓
⑤ 【降档实验】主力档 (Qwen3.6-35B-A3B) 当 Judge，与基准 Judge + 人工标注比一致度
        ↓
   达标 → 日常回归用主力档，只在里程碑用重推理档复核
```

> **J2 当前结果（2026-08-17）**：六类 `answer-correctness-binary.v2` 上，heavy 的
> validation accuracy/QWK 为 0.9474/0.8725，main 为 1.0/1.0，两档都通过 0.85 点估计门槛；
> 日常 correctness Judge 采用 main。`agent_task`、faithfulness 与 citation accuracy 不在
> 本轮结论内，类别切片也因每类只有 2–5 条而只作诊断。

### 为什么仍报告 quadratic weighted Kappa ★

当前冻结 rubric 是 **0/1 二分类**。此时 quadratic 权重矩阵退化为 0/1，QWK 与普通
Cohen's Kappa 数学上完全相同；保留 `qwk` 字段是为了报告 schema 与未来有序 rubric 连续，
不是声称二分类下存在额外的加权收益。

若未来恢复 **0/1/2 有序三档**，quadratic weighted Kappa 才会按 `(i-j)²` 加权惩罚：
差 2 档的惩罚是差 1 档的 4 倍，比无权重 Kappa 更符合语义。换 rubric 必须重新人工标注和校准，
不能继承 J2 的数字。

同时必须看**混淆矩阵**：一个整体 Kappa 0.87 的 Judge，
可能在 `unanswerable` 类上系统性地把"该拒答"判成"回答正确"——
汇总数字看不出来，分类别一致率才看得出来。

### rubric 设计要点

- 当前 correctness 采用严格二分类：部分正确一律 0，减少小样本中的中间档歧义
- 若任务确实需要有序程度，再考虑三档；不能为了让数字好看临时改标签尺度
- 每档给具体例子，不要只给形容词
- 强制先输出理由再输出分数（先给分会让理由沦为事后合理化）
- 检查长答案偏好：Judge 有系统性偏爱长答案的倾向，
  用同一答案的长短两个版本做对照检验

> 面试题"你怎么知道你的 Judge 判得准"——答案是冻结 rubric、独立 validation、混淆矩阵、
> Kappa 与 bootstrap 边界。还要能说清：**二分类 QWK 等于 Cohen's Kappa，只有有序三档时
> quadratic 权重才真正改变惩罚。**

## 4. CI 门禁

> 借鉴 promptfoo 的"评测即代码 + 快照 diff"范式。

### 4.1 分层跑批 ★

**不能每个 PR 都跑全量 + LLM Judge。** 分两层：

| 触发 | 跑什么 | 判分 | 时长 | 在哪跑 |
|---|---|---|---|---|
| **每个 PR** | 静态检查 + `pytest`（含 `regression` 用例） | 确定性断言 | < 3 min | GitHub Actions |
| **每晚** | 完整 `core-dev` | 规则轨 + LLM Judge | ~30 min | 本地/集群，结果回传 |
| **里程碑** | `core-test` | 全量 + 人工抽检 | — | 本地 |

#### 决策：PR 层不跑独立的 smoke 评测 ★

原设计是三层，PR 层跑 20–30 条 `smoke` 的纯规则轨快照 diff。
[G0](experiments/2026-08-17-G0-门禁准备与噪声地板.md) 评估后**取消这一层**，
把规则轨回归并入 `pytest`。三条理由：

1. **合成 fixture 上的"逐位相等快照"就是 golden-file 测试，它天然属于 pytest。**
   另起一套 eval 快照只是换个地方做同一件事，而且失败信息更差——
   assert 会指出哪条不变量断了，快照 diff 只会说"17 个数变了"。
2. **`backend/tests/` 已经覆盖了规则轨的全部确定性路径**，且每个 PR 都在跑：
   端到端链路 `test_retrieval_generation_and_block_citation_chain`（真库 + 确定性
   provider，ingest → 检索 → 证据门控 → 生成 → 引用解析）、RRF
   `test_lexical_terms_and_rrf_cover_exact_identifier`、词法三模式排序、
   证据打包与字符预算、引用 fail-closed、两条拒答路径、HNSW 与精确扫描等价。
3. **合成语料上的指标不是质量信号。** PR 层若不连私人库就只能用手写的公开 fixture，
   在它上面报"span_recall 掉了 3pp"没有意义，"PR 贴指标 diff"的叙事在这一层立不住。
   真正有意义的是夜间真语料那一层，而它跑在家里，压根不需要公开 fixture。

**这个取消是有代价的，要认**：改了检索策略（RRF 的 k、top_k 默认值、打包顺序）的 PR
能在没有任何**指标**检查的情况下合入——测试挡的是行为破坏，不是质量回退。
兜底是[约束 6](../CLAUDE.md)（改输出逻辑必须补评测样本）加夜间门禁，
单用户产品上暴露窗口小于一天。这是个交换，不是免费的。

连带结论：**不需要版本化的公开 fixture 语料，也不需要预计算 embedding 入 git**，
[约束 7](../CLAUDE.md) 与门禁之间原本的张力随之消失。

M0 还没有校准后的 Judge，因此不宣称自动得到“引用准确率”。
M0 自动指标名为 `citation_validity`，另对 40 条样本人工判定引用是否真正支撑答案；
M1 Judge 校准后才把语义支撑指标自动化为 `citation_accuracy`。

**为什么 PR 不能跑 Judge——理由不是"太贵"**：
自建集群上 Judge 调用几乎不花钱。真正的硬约束是
**GitHub Actions runner 连不到家里的推理集群**。
在 CI 里跑 Judge 就必须走商用 API，那才是真花钱且慢。

同一条约束也解释了 PR 层为什么连**检索**都不跑：runner 既到不了推理集群，
也到不了本机的私人库；要在 CI 里跑检索就得自带语料与 embedding，
而那份语料只能是合成的（见上方决策）。

> 这个区别要记牢：面试被问"CI 为什么不跑全量"时，
> 答"太贵"在有自建算力的前提下是自相矛盾的，答"runner 到不了集群"才成立。

```yaml
# .github/workflows/ci.yml（已落地）
on: [pull_request]
jobs:
  backend:    # pgvector + redis service → uv sync --locked → ruff → mypy → pytest
  frontend:   # npm ci → eslint → tsc
```

```
# 夜间门禁（跑在本机/集群，不在 GitHub Actions）
uv run python -m eval.gate --against main --dataset core-dev
      - 跑完整 core-dev（规则轨；Judge 校准收口后再纳入）
      - 与 main 的 baseline 快照比对
      - 任一门禁条件不满足 → 标记失败并回传
```

### 4.2 门禁阈值

阈值全部落在**夜间**层（PR 层没有指标，只有断言）。
下表已按 [G0](experiments/2026-08-17-G0-门禁准备与噪声地板.md) 实测的噪声地板修订。

| 条件 | 阈值 | 依据 |
|---|---|---|
| `span_recall@10` / `citation_validity` / 约束 / 拒答等**规则轨**指标 | **聚合值不允许回退**（零容忍，不留百分比余量） | 实测：`main` 档生成三次重复**逐位一致**（四个质量指标跨度均为 0，`total_tokens` 也逐位相同）。既然噪声是 0，聚合值掉了就是真掉了 |
| `regression` | **不允许任何一条从通过变失败** | 修好的 bug 不许再犯。已下沉到 `backend/tests/`，由 PR 层的 pytest 执行 |
| `cost_per_query`（token 计） | 上涨 ≤ 20% | 实测噪声最坏 8.8%（heavy 生成档），阈值 > 噪声 |
| `answer_correctness` | 下降 ≤ 2pt | J2 已完成 binary v2 校准；待首份 nightly baseline 把 Judge 字段接入快照后启用。n=70 时一条样本 = 1.43pp，2pt ≈ "最多退 1 条" |
| `faithfulness` | 绝对值 ≥ 0.90 | 幻觉是产品的生死线；本指标尚未独立校准，不能复用 correctness 的 J2 结论 |
| `refusal_correctness`（unanswerable 类） | ≥ 0.90 | 同上 |
| ~~`p95_latency`~~ | **移出门禁** | 实测同配置三次重复的相对跨度已达 75.8%（C6），远超原定的 30%；且墙钟受机器负载影响。要门禁延迟必须先有固定机器的专门测量 |

**两条定阈值时容易踩的坑**（这一节的实操教训）：

1. **阈值不能大于噪声，也不该小于量化下限。** 比率指标只能取 `k/n`，
   一条样本翻转就是一格：n=20 时 5.00pp、n=30 时 3.33pp、n=70 时 1.43pp。
   在 20–30 条的集合上写"下降 ≤ 2pt"是**表示不出来**的——最小的非零回退一步就越过它，
   实际效果等于"一条都不许退"，但百分比的写法会让人误以为留了容错余量。
2. **分母自己会动。** heavy 生成档下 `completed_count` 三次是 19/20/19（错误本身不确定），
   引用对齐的分母是 30/23/21。分子分母都在动的比率跨跑批比较根本不是配对的，
   所以门禁必须先**逐样本配对**再算聚合，不能直接比两份报告的聚合率。

**阻断条件是聚合值，逐样本胜负只报不拦。** 最初把规则定成"任何一条样本回退即阻断"，
拿 E1 的 semantic 一试就发现它把净收益的改动也拦下来了——semantic 省 16.8% 检索 token，
但 nDCG 上有 21/57 条重排。那种门禁会天天红，然后被习惯性忽略，比没有门禁更糟。
逐样本的胜/负计数照样出现在报告里，它是给人看的信息（也是"整体持平掩盖 A 涨 B 跌"的
唯一线索），但不是阻断条件。

> 想让一次有取舍的改动通过，正确动作是**重新生成 baseline 快照**（`eval.gate snapshot`）
> 并把取舍写进台账，而不是放宽阈值。门禁的作用是逼取舍显式化，不是替你做取舍。

### 4.3 噪声控制与显著性 ★

LLM 输出有随机性，`temperature=0` 也不能完全消除
（batch 组成、并发调度、MoE 路由都会引入变化）。

**"三次取中位数"不足以支撑"显著提升"的结论。** 正确做法：

| 方法 | 用途 |
|---|---|
| **逐样本 paired bootstrap** | 主力方法。对 N 个样本的**配对差值**重采样 10000 次，给出 Δ 的 95% 置信区间。**置信区间跨 0 就是"无显著差异"，不能写成提升** |
| 固定 seed + 重复 3 次 | 估计单次跑批的方差，判断噪声地板在哪 |
| 分类别报告 | 整体持平可能掩盖"A 类涨 B 类跌"，必须分类别看 |

**门禁阈值必须大于噪声地板**，否则会天天误报——
最后所有人都习惯性点忽略，门禁就名存实亡了。所以顺序是：
**先测噪声，再定阈值**，不能反过来。

**已测出的噪声地板**（[G0](experiments/2026-08-17-G0-门禁准备与噪声地板.md)，
数据来自实验 C 的 7 配置 × 3 重复）：

| 生成档 | 拒答正确 | 引用有效 | 约束通过 | 引用对齐 | token |
|---|---|---|---|---|---|
| `light` / `main` | **0** | **0** | **0** | **0** | **0** |
| `heavy` | 5.26pp | 0 | 2.89pp | **13.48pp** | 8.8% |

**噪声只来自 heavy 的「生成」槽位，不是"含 heavy"。** C7 把 heavy 放在证据门控上，
四个指标逐位一致。机制：门控输出是短的离散判定，采样噪声要翻转它得跨过整个决策边界；
生成输出是长自由文本，第一个 token 的微小差异会放大成完全不同的引用集合。

> 推论不能过度外推成"heavy 用在门控上就是确定性的"——真正的判据是
> **输出是短离散量还是长自由文本**。换个短输出任务，用 `main` 也可能抖。
> 对实验 J 的影响比原先估计的宽松：当前 Judge 输出 0/1 属"短离散"那一类，
> **未必**需要多次重复——但这要实测，不能靠类比免掉。

### 4.4 评测跑批默认禁用 fallback ★

线上允许模型档位 fallback（集群挂了要能兜底），**但评测时必须关掉**。

否则会发生：`eval_runs.config` 记录用的是 `heavy` 档，
实际跑的时候集群超时自动切到商用 API，
指标是另一个模型打出来的——**实验不可复现，而且你不知道**。

```
评测模式：fallback_enabled = false
  ├ 调用失败 → 该 run 直接失败，不静默降级
  └ 每次调用记录 actual provider/model 到 eval_runs.actual_models
```

## 5. 实验台账

**这是面试的核心弹药库。**
面试官问"你做了哪些优化、分别提升了多少"时，能打开一份逐条记录的台账，
和只能口述"我做了混合检索感觉好一些"，是完全不同的两个候选人。

每个实验在 `docs/experiments/` 建一个 md，格式见该目录的 `TEMPLATE.md`。

### 铁律

1. **一次只改一个变量**，否则归因不了
2. **先写假设再跑**——事后编的假设没有价值，而且会导致选择性解读
3. **负优化必须记录**。这是最有价值的部分：
   > "我以为语义分块会赢，结果在论文语料上比标题分块低 6 个点，
   > 原因是学术写作的章节结构本身就是作者做好的语义分块。"

   这段话在面试里的分量，超过任何一个正向指标。
4. **记录 `git_sha` + `config_hash`**，任何数字都能追溯到确切的代码与配置

## 6. 线上反馈闭环

```
真实使用中点踩
    ↓
feedback 表（含 reason：事实错误 / 引用不对 / 该拒答 / 格式问题 / 太慢）
    ↓
每周固定时间人工过一遍（个人产品，量不大，一次 20 分钟）
    ↓
可复现的 → 标注 gold → 进 regression 集，promoted_to_eval = true
    ↓
同时固化成 backend/tests/ 里的一条确定性用例（这才是"每个 PR 都在挡"的那一层）
    ↓
PR 门禁（pytest）保证同类问题不再复发
    ↓
形成"发现问题 → 固化为测试 → 永不回退"的棘轮
```

**这才是 JD 里"效果评估与反馈优化闭环"的完整形态。**
关键在最后一步：修复不是终点，把修复固化成回归测试才是。

### 棘轮怎么落地的

`backend/tests/test_regression_badcases.py` 里有一张 `BADCASES` 登记表，
每条记：症状、根因、修法、来源台账，以及**哪几条用例挡住它**。
`test_every_registered_badcase_is_still_covered` 会把 `covered_by` 逐条解析成真实的
测试函数——**covering 用例被改名或删掉就直接红**。这条元测试才是棘轮的锁：
它让"覆盖悄悄消失"变成一个必须显式处理的失败，而不是没人发现的沉默。

登记的是**已经修好**的问题；仍在归因中的（D7 精排 badcase、E7 retrieval miss）不进表——
棘轮锁的是"不许退回去"，不是待办清单。

### 当前缺口：点踩还没有采集入口 ★

`feedback` 表在 [03 数据模型](03-数据模型.md) 里定义了，migration 也建了，
**但 `backend/app/` 里没有任何代码写它**——没有记录反馈的接口，前端也没有点踩入口。

所以上面这条链现在是从"作者自己发现 badcase"开始跑的，不是从点踩开始。
链路的后半段（标注 → regression 集 → pytest 用例 → 棘轮）已经通了并且在用，
前半段（采集 → 每周过一遍）还缺一个接口。这个接口属于产品功能，不在门禁范围内，
排期里也还没有它的位置——**先把缺口写在这里，免得对着"闭环"这张图以为它已经闭上了。**

## 7. 评测框架实现

**自建，不做 Ragas / DeepEval 的壳。**
理由：评测是本项目的核心差异化，必须自己实现才能在面试中讲透每个指标的算法细节。
借鉴它们的**思想**（Ragas 的指标分解、DeepEval 的 pytest 集成、promptfoo 的快照 diff），
不引入它们的抽象。

```
eval/
├── datasets/           YAML 格式的评测集（进 git，可 review、可 diff）
├── mapping.py          ★ gold_spans → chunk 的区间映射（§2.1）
├── metrics/
│   ├── retrieval.py    span_recall / ndcg / alpha_ndcg / mrr / context_precision
│   ├── generation.py   correctness / faithfulness / citation / refusal
│   ├── agent.py        success / step_efficiency / recovery_rate
│   └── judge.py        LLM Judge 封装 + rubric 管理
├── stats.py            ★ paired bootstrap 置信区间 + quadratic weighted Kappa + 混淆矩阵
├── runner.py           并发跑批（评测模式强制 fallback_enabled=false）
├── compare.py          两次 run 的快照 diff + 显著性判定，输出 markdown 报告
├── calibrate.py        Judge 校准：加权 Kappa + 分类别一致率
└── gate.py             夜间门禁判定（PR 层由 pytest 承担，见 §4.1）
```

```bash
uv run python -m eval.run --dataset core-dev --label exp-hybrid-rrf --no-fallback
# 已实现：位置参数是两次跑批的 report.json（或其所在目录），配对 bootstrap 置信区间
uv run python -m eval.compare <baseline-run> <candidate-run> --output-dir <dir>
uv run python -m eval.calibrate --judge heavy --human-labels labels/round1.yaml
uv run python -m eval.gate --against main --dataset core-dev  # 夜间门禁，跑在本机
```

## 8. 必须能答上来的问题

1. 你的 Judge 怎么验证判得准？→ §3，说出**加权** Kappa 值，并说明为什么是加权
2. 为什么当前仍报 QWK？→ binary v2 下它等于 Cohen's Kappa；未来改回 0/1/2 有序标签时，quadratic 权重才区分差 1/2 档
3. 你的标注为什么不绑 chunk_id？→ [ADR-0006](adr/0006-分块与标注分层.md)，
   否则四策略对照无法公平比较，且重新分块就会全部作废
4. 评测集会不会过拟合？→ dev/test 分离 + test 集使用纪律 + badcase 持续注入
5. LLM 输出有随机性，你的指标可信吗？→ **paired bootstrap 置信区间**，
   跨 0 就写"无显著差异"；固定 seed 重复跑估噪声地板
6. 一个改动在 A 类涨、B 类跌，怎么决策？→ 看真实分布下的加权收益，
   且 `faithfulness` 和 `refusal` 是不允许交换的硬底线
7. 有没有做了但效果变差的优化？→ **必须准备一个真实案例**，这题答得好加分最多
8. 门禁阈值怎么定的？→ 先测噪声地板，阈值必须大于噪声，否则误报会让门禁失效。
   **还要大于量化下限**：n=20 时一条样本就是 5pp，"下降 ≤ 2pt"这种阈值根本表示不出来
9. CI 为什么不跑全量？→ **不是因为贵**（自建集群 Judge 几乎免费），
   是 CI runner 连不到集群，跑 Judge 就得走商用 API
9b. PR 门禁为什么干脆不跑评测？→ §4.1。PR 层若不连私人库，就只能用手写的合成
   fixture，而在合成语料上比指标不构成质量信号；而合成 fixture 上的"逐位相等快照"
   本质就是 golden-file 测试，pytest 做同一件事失败信息还更好。
   **这是一个我评估后主动砍掉的设计，代价（检索策略改动在 PR 层无指标兜底）写在文档里**
10. 评测时 fallback 为什么要关？→ §4.4，否则 config 记录与实际执行不符，实验不可复现
11. 为什么不直接用 Ragas？→ §7
