# 03 · 数据模型

**全部状态在本机文件里，没有外部数据库**
（[ADR-0012](adr/0012-退役postgres与redis改用本机文件.md)）。

**单用户产品**：不引入 `workspace_id` 和语料 ACL。多用户扩展点见 [02 §7](02-架构设计.md)。

---

## 0. 四种载体，各有各的理由

| 载体 | 装什么 | 为什么是它 |
|---|---|---|
| **SQLite** `~/.workpilot/cowork.db` | run / 事件 / checkpoint / 幂等租约 / 授权 / 调度 / 记忆 / Inbox | 需要条件更新、唯一索引、外键级联和事务的地方——租约抢占靠的就是"条件 UPDATE 命中零行" |
| **JSONL** `~/.workpilot/conversations/<id>.jsonl` | 规范 user/assistant/tool 消息 | 对话天然 append-only。可以被任何工具读、可以 `tail`、损坏尾行可以容忍 |
| **SQLite** `~/.workpilot/telemetry.db` | 调用审计 + 每日费用闸门 | 与业务库分开：跑批会写进它，业务库不该被评测污染 |
| **目录** `kb/<slug>/`、`skills/<name>/`、`skills-candidates/<key>/` | 知识库索引、Skill、蒸馏候选 | 目录即真相。用户可以直接用编辑器改，可以 `git` 管，可以拷走 |

**三条跨载体的铁律**（都是踩出来的，CLAUDE.md 里也有）：

1. **时间一律 UTC ISO 字符串。** SQLite 里时间是字符串、比较是字典序。混了本地偏移，
   `22:59+08:00` 会排在 `15:05+00:00` 后面——两者其实是同一刻，租约与过期清扫会判错。
2. **钱一律整数微美元。** SQLite 没有 decimal。用 REAL 存美元会让 `0.1 + 0.2 != 0.3`
   直接发生在预算比较上，而且不报错。
3. **`os.replace` 是原子的但不排他。** 两个进程都会"成功"。要互斥用
   `O_CREAT|O_EXCL` 建锁文件，过期判定读锁里的 `claimed_at`，**不要读 mtime**。

## 1. cowork.db

`PRAGMA foreign_keys = ON`、WAL、`busy_timeout`、短 `BEGIN IMMEDIATE` 事务。
**任何模型、浏览器、Shell、MCP 调用期间不得持有事务**
（[ADR-0010](adr/0010-cowork本地存储与rag数据面分离.md)）。

版本号是 `PRAGMA user_version`，当前 **22**。升级路径以
`PRAGMA table_info` 探测 + `ALTER TABLE ADD COLUMN` 为主；需要补外键或清理隐私数据时执行
显式版本迁移。没有 Alembic——单机单用户只向前迁移；数据库版本高于当前程序支持范围时
直接拒绝打开，不能用旧程序静默破坏新表。

### 1.1 会话与消息

```sql
conversations(
    id PK, title,
    provider_profile_id, model_override,     -- 会话级 Provider / 模型切换
    unattended, approval_mode,               -- 'interactive' | 'auto'
    persona_name,                            -- 当前会话选择的 Persona
    inbox_name,                              -- 路由到哪个命名 Inbox；空 = default
    kb_slug,                                 -- ★ 挂载了哪个本地知识库
    archived_at, summary, summary_upto,      -- 压缩：摘要覆盖到第几条
    created_at, updated_at)

cowork_conversation_skill_mutes(
    conversation_id FK, skill_name, created_at,
    PK(conversation_id, skill_name))          -- 会话级 deny；删会话时级联清除

conversation_message_index(
    record_id PK, conversation_id FK, seq,
    role, status, run_id,
    jsonl_offset, jsonl_length,              -- ★ 指回 JSONL 的字节区间
    created_at,
    UNIQUE(conversation_id, seq))
```

**消息为什么分成两半**：正文在 JSONL（append-only、可外部读），索引在 SQLite
（可按 `seq` 排序、按 `status` 查、外键跟着会话级联删）。`jsonl_offset/length` 让读一条
消息不必扫全文件。

> **一个由此产生的真实回归**：watchdog 原来在 SQL 里一句话就把"卡在 streaming 的助手
> 消息"标成 failed。消息搬进 JSONL 之后 store 的 SQL 够不着它，那段逻辑必须上移到
> `runstore/runs.py`（`list_streaming_message_ids` + 收尾循环）。删 Postgres 分支时差点
> 连这个行为一起删掉——界面会永远转圈而 run 早就是终态了。

### 1.2 run 与事件

```sql
agent_runs(
    id PK, conversation_id FK, goal, status,
    worker_id, lease_until, heartbeat_at,    -- 租约抢占
    cancel_requested_at,
    wake_at,                                 -- ★ status='sleeping' 时到点重新入队
    budget_tokens/calls/wall_ms,             -- 三维计量；0=不限，正数才启用熔断
    used_tokens, used_calls,
    next_seq,                                -- ★ 事件发号器
    error, answer_mode, workflow_type,
    schedule_id, unattended, run_trigger,
    source_wake_id UNIQUE,                    -- durable wake/outbox 的去重身份
    retrieval_top_k,
    recovery_count,                          -- ★ 重投计数，见下
    started_at, finished_at, created_at, updated_at)

run_events(run_id FK, seq, type, payload, created_at, PK(run_id, seq))
```

`next_seq` 在同一事务里自增并写入事件，因此 `seq` 是**单调无洞**的——SSE 断线重连靠
`after_seq` 续传，有洞就等于丢事件（[ADR-0007](adr/0007-agent幂等与事件溯源.md)）。
`seq` 以字符串出信封，避免 JS number 精度问题。

**`claim_run` 只认 `queued`。** Postgres 版允许第二个 worker 直接偷走过期租约；这里不行。
那条偷租约的路绕开了 `recovery_count`，而 ADR-0007 正是用它挡住"稳定把 worker 拖垮的
run 被无限重投"。**回收必须经过 watchdog**：

```
租约过期
  ├─ 有 checkpoint 且 recovery_count < max  → 退回 queued，recovery_count += 1
  ├─ 有 checkpoint 但次数耗尽              → 判失败，交给人
  └─ 没有 checkpoint                       → 判失败（重跑等于从头再烧一遍预算）
```

退回时必须真的写回 `queued` 而不是只清租约，否则 `claim_run` 的条件谁都命中不了。

### 1.3 执行状态

```sql
agent_plan_steps(id PK, run_id FK, step_idx, description, tool,
                 depends_on, status, UNIQUE(run_id, step_idx))
agent_attempts(id PK, run_id FK, plan_step_id FK, attempt_no, node,
               tool_name, tool_args, tool_result, status,
               idempotency_key, latency_ms, tokens, error_model,
               UNIQUE(run_id, plan_step_id, attempt_no, node))
cowork_run_configs(run_id PK/FK, config, created_at, updated_at)
agent_checkpoints(run_id FK, checkpoint_id, parent_id, state, created_at,
                  PK(run_id, checkpoint_id))
```

`agent_plan_steps` 是 runtime 从 tool call 派生的**事后日志**；模型主动声明的计划是
`todo_write` 那份任务清单，存在 checkpoint 里。两者并存不互相替代。

通用 checkpoint 对状态内容不作假设，只要求能编码成 JSON（约束 2）。Cowork v3 是明确的
特例：21 个 run 内冻结字段只写进单行 `cowork_run_configs`，30 个可变字段才进入每个
`agent_checkpoints.state`；读取边界透明重组。已知 v1/v2 通过显式 migrator 升到 v3；
当前 v3 缺字段、多字段或不能无损解析时抛具名 corruption error，绝不 `setdefault` 猜回。
runtime snapshot 中已加载工具或 provider/model 身份不存在时同样拒绝恢复。

### 1.4 副作用幂等 ★

```sql
tool_invocations(
    idempotency_key PK,                      -- ★ 不是自增 id
    run_id FK, plan_step_id, tool_name, args_hash,
    result, status,
    lease_owner, lease_until, retry_count,
    effect_ref,                              -- 下游系统给的 id，用于对账
    created_at, updated_at, completed_at)
```

**这张表是约束 9 的落点。** 有副作用的工具在执行**之前**先抢租约：

- 已 `succeeded` → 直接复用结果，不重放
- 租约有效且属于别人 → 拒绝
- 明确在副作用前失败 → `failed`，可按原幂等身份安全重试
- handler 已开始后取消、缺少 `effect_ref`、结算失败或租约过期 → `outcome_unknown`，永久阻止自动重放

租约过期不再等价于“动作没发生”：进程可能已在下游完成，只是没来得及结算。因此通用工具、
本地存储动作和 MCP 都使用同一 unknown-effect 终态；跨系统副作用只承诺 at-most-once / 可对账，
并尽量向下游透传同一幂等键（`effect_ref` 用来事后对账）。持久错误只保存脱敏、限长的错误类型，
不把异常正文写进库。

不得依赖 Agent 状态里的 `cursor` 或任何步骤序号做去重——从 interrupt 恢复会从节点开头
重跑，**状态恢复 ≠ 副作用不重放**。

### 1.5 授权

```sql
session_roots(id PK, conversation_id FK, requested_path, canonical_path,
              label, access_mode, enabled, UNIQUE(conversation_id, canonical_path))
capability_grants(id PK, conversation_id FK, session_root_id FK,
                  capability, resource_scope, grant_source, expires_at, revoked_at)
    UNIQUE(conversation_id, IFNULL(session_root_id,''), capability,
           IFNULL(resource_scope,'')) WHERE revoked_at IS NULL
cowork_approval_rules(id PK, conversation_id FK, scope, schedule_id FK,
                      tool, match_kind, target, created_by, revoked_at)
cowork_workspace_trust(canonical_path PK, trusted_at, revoked_at)
```

**`canonical_path` 是主键而不是会话**（`cowork_workspace_trust`）：用户信任的是"这个目录"，
不是"这一次对话里的这个目录"。信任跟着路径走而不是配置快照，因为"每次仓库改 allowlist
都重新问一遍"会把信任变成又一个闭眼点过的弹窗。

**计划派生的审批规则跟着计划一起消失**（`schedule_id ... ON DELETE CASCADE`）：删掉计划却
留下它攒下的免审批授权，是那种"以为已经收回了"的权限。

审批规则只省掉「再问一次」，**不放大 capability**：没有 `shell.execute` 的会话攒再多规则
也跑不了命令。

### 1.6 交付物、附件、调度、消息面

```sql
artifacts(id PK, conversation_id FK, run_id FK, session_root_id FK,
          kind, title, uri, mime_type, meta)
cowork_attachments(id PK, conversation_id FK, message_id, run_id FK,
                   kind, filename, media_type, storage_path,
                   size_bytes, sha256, extracted_text)

cowork_schedules(id PK, conversation_id FK, title, goal,
                 schedule_kind, cron_expression, run_at, timezone,
                 enabled, next_run_at, last_run_at, last_run_id FK,
                 run_count, skipped_count,
                 dispatch_lease_owner, dispatch_lease_until)

cowork_inbox_items(id PK, run_id FK, conversation_id FK, kind, status,
                   resume_token UNIQUE, tool_call_id, plan_step_id FK,
                   request, response, unattended, delivery_ref,
                   UNIQUE(run_id, tool_call_id))
    UNIQUE(run_id) WHERE status = 'pending'      -- ★ 一个 run 同时只能等一件事
cowork_steering_messages(id PK, run_id FK, conversation_id FK,
                         content, status, consumed_at)

cowork_inbox_bindings(id PK, name UNIQUE, platform, chat_id,
                      connector_account_id, enabled,
                      CHECK ((platform IS NULL) = (chat_id IS NULL)))
cowork_messaging_event_receipts(event_key PK, platform, event_type,
                                status, received_at, completed_at)
cowork_channel_subscriptions(id PK, conversation_id FK, platform, chat_id, revoked_at)
cowork_thread_sessions(target PK, conversation_id FK, platform, chat_id, thread_id)
cowork_unrouted(id PK, kind, platform, chat_id, summary, payload, created_at)
```

`cowork_thread_sessions` 的主键就是 **thread 地址串本身**（`feishu:oc_x:om_y`）：发消息、
查会话、判定授权共用同一个字符串。分别拼一次迟早出现"看起来一样但比不相等"的地址。

`cowork_messaging_event_receipts.event_key` 只保存 `SHA256(platform + NUL + upstream_event_id)`，
不保存上游 event id 或消息正文。验签、时效与有界 JSON 解析通过后，入口在任何副作用前先
`claim`；进程即使在动作后崩溃，后续重投也只会被压成 duplicate。这是刻意选择的
**at-most-once**：不以重复创建 run / 重复批准动作换取自动重试。

`cowork_unrouted` 是**可见性设施不是队列**，条目不会被重投。没有它，"我在群里说了一句，
什么都没发生，也查不到为什么"就是彻底静默的失败。

### 1.7 记忆 ★

原 PostgreSQL `memories` 与 Cowork `cowork_memories` 已合并成一张表。取舍见
[ADR-0005](adr/0005-记忆采用时序有效性建模.md)，形态在两个参照物之间：

| | 存储 | 改写方式 | 历史 |
|---|---|---|---|
| **OpenWorker** | 扁平表，scope/key/content | 直接改写那条 | 没有 |
| **DeepTutor** | 三层 markdown + 脚注引用 | LLM 定期重新合并 | 文档修订 |
| **WorkPilot** | 扁平（抄 OpenWorker） | **失效 + 接替** | 「当前 / 历史」两个视图 |

```sql
cowork_memories(
    id PK,
    scope CHECK IN ('global','workspace','conversation'),
    conversation_id FK, workspace_path, key, content,
    source CHECK IN ('agent','user'),
    forgotten_at,                            -- 软删除
    -- 时序有效性与人工策展
    category CHECK IN ('preference','profile','interest','fact'),
    confidence CHECK (0 <= confidence <= 1),
    pinned,
    valid_from NOT NULL, invalid_at,         -- ★ 与 created_at 分开
    superseded_by FK → cowork_memories(id),
    access_count, last_used_at,
    source_message_id, run_id,
    CHECK (scope 与 conversation_id / workspace_path 三选一互斥))

cowork_memory_owner_policy(singleton_id=1, save_enabled, recall_enabled,
                           standing_rules, revision, updated_at)
cowork_memory_conversation_policies(conversation_id PK/FK,
                                    save_mode, recall_mode, revision, updated_at)

-- 当前视图与历史视图各一个部分索引
ix_..._active (scope, updated_at) WHERE forgotten_at IS NULL AND invalid_at IS NULL
ix_..._history (invalid_at DESC)  WHERE invalid_at IS NOT NULL
-- key 的唯一性只在"当前"里成立
uq_..._key (scope, conversation_id, workspace_path, key)
    WHERE key IS NOT NULL AND forgotten_at IS NULL AND invalid_at IS NULL
```

**纪律：不覆盖，只失效。** `valid_from` 与 `created_at` 分开，是因为模型可以在今天写下
"从上个月起改用表格"。一条晚到的旧事实会被存成**已失效**并指向当前记录
（`applied=True, current_changed=False`），而不是覆盖掉更新的那条。

**去重不用向量。** pgvector 退役后 `recall_memories` 已经没有调用者了，改成 OpenWorker 的
做法：把最近 N 条活跃记忆整批放进 prompt，让模型指名道姓选一条改。对个人记忆这个量级反而
更准——语义最近邻常挑出"相似但说的是别的事"的那条。

```sql
memory_extraction_jobs(
    id PK, run_id UNIQUE, conversation_id, source_message_id,
    content, source_created_at,              -- ★ 来源快照随作业一起存
    status CHECK IN ('queued','running','done','failed'),
    attempts, worker_id, lease_until, available_at,
    error, result_json, finished_at)
```

作业和记忆在**同一个库**里，所以"提炼出一条记忆"与"把作业标记完成"可以在同一个事务里，
不会出现记了却没结算、或结算了没记的半截状态。来源快照只在 `queued/running` 期间保留；
进入 `done/failed` 会清空 `content`，失败详情只留固定错误码或脱敏短诊断，会话删除时作业级联
清理。owner / conversation 两层 policy 都带 revision，所有 Agent 写入在同一个 SQLite 写事务里
做 CAS 复核；任一层关闭保存都 fail closed，避免“抽取时允许、落库前已经关闭”的竞态。

### 1.8 Agent Team 控制面 ★

```sql
cowork_teams(...)                         -- 生命周期、写委派收据、四维总预算/预留
cowork_team_workers(...)
cowork_team_worker_sessions(...)          -- 可恢复的 worker checkpoint
cowork_board_tasks(...)                   -- assignment / review / rework 状态机
cowork_team_budget_reservations(...)       -- 并发派发前预留，完成后结算
cowork_team_worker_tool_attempts(...)      -- succeeded / failed / unknown
cowork_team_events(...)                    -- append-only hash chain
cowork_team_event_heads(...)               -- 独立 head，识别尾删
cowork_team_event_cursors(...)
cowork_team_wake_outbox(...)               -- durable wake feed / claim / receipt
cowork_team_event_projection_summaries(...)
```

Team 的 projection 与不可变事件在同一事务写入；独立 head 校验序号、parent、prev-hash 与尾部，
普通路径由 trigger 禁止更新/删除。写委派需要显式 scope 与签名收据，撤销、暂停、归档都会停止
新派发；模型调用、工具调用、墙钟和 assignment 都在并发前预留，防止多个 worker 同时越过预算。
effectful worker tool 若无法证明结果，结算为 `unknown` 并阻止同一 call 自动重放。只有用户显式
删除会话时，事务内临时 purge guard 才允许连同隐私敏感 Team audit 一并物理清除。

## 2. conversations/*.jsonl

```python
JsonlMessage(record_id, conversation_id, seq, role, content,
             status,               # streaming | completed | failed | cancelled
             run_id, tool_call_id, tool_calls, attachments, citations,
             created_at)
```

append-only + `fsync` + 损坏尾行容忍 + `record_id` 去重。写入用 `fcntl` 排他锁。

**JSONL 只承担消息，不承担租约、审批或调度锁。** 那些需要条件更新与唯一索引，文件做不到。

**"修改一条消息"是再 append 一条同 `record_id` 的记录**，读取时后写的赢。绑定附件走的就是
这条路径。历史因此完整保留——这是 DeepTutor "历史活在文档修订里"那个思路在消息层的对应物。

## 3. telemetry.db

```sql
llm_calls(id PK, trace_id, run_id, eval_run_id, task_type, tier,
          model, provider, prompt_tokens, output_tokens, latency_ms, success,
          cost_micro_usd,                    -- ★ NULL ≠ 0
          prompt_cache_read_tokens, prompt_cache_write_tokens,
          cached, cache_type, was_fallback, batch_id,
          span_id, parent_span_id, stop_reason, created_at)

agent_spans(span_id PK, trace_id, run_id, parent_span_id,
            name CHECK IN ('agent.run','agent.turn','agent.tool'),
            status, started_at, ended_at, duration_ms, attributes, error_type)

daily_cost_budgets(budget_date PK, limit_micro_usd,
                   reserved_micro_usd, spent_micro_usd)

cost_reservations(idempotency_key PK, budget_date, run_id,
                  estimated_micro_usd, actual_micro_usd,
                  status CHECK IN ('reserved','settled','released','charged_estimate'),
                  expires_at)
```

`agent_spans` 的 name 与 attributes 都由 `workpilot_telemetry.spans` 的封闭类型定义。
触发工具批次的 turn id 会随 checkpoint 保存，因此跨 worker 恢复的 tool span 仍能挂回
原 turn；`llm_calls.parent_span_id` 则把每次 provider request 挂到对应 turn。

**`cost_micro_usd` 的 NULL 与 0 严格区分**：本机自部署模型的单价真的是 0，"没有可用单价"
是另一回事。折成同一个值之后，成本看板再也分不出"免费"和"没测过"（[07 §7.4](07-模型路由与成本.md)）。

**`charged_estimate` 与 `settled` 必须分开**：前者是"没人来结算，按预留上限扣的"，后者是
"provider 报了真实用量"。合并之后就再也看不出有多少钱是估出来的。

## 4. 目录即真相

### 4.1 知识库 `~/.workpilot/kb/<slug>/`

```
manifest.json          KbManifest：显示名、文档清单、版本清单、active 指针（原子写）
versions/<version_id>/ FAISS + docstore + bm25/ sidecar；一版一个目录
```

语料本身留在用户自己的目录里，清单只记它的绝对路径。理由与代价见
[04 §3](04-知识与阅读设计.md)。

### 4.2 Skill：builtin + user + project 三层

```
backend/app/cowork/skills/builtin/<name>/
  SKILL.md                         随产品发布，只读；升级时可整体替换
  <其他文件>                       出厂资源

~/.workpilot/skills/<name>/        user 层（实际位置由 cowork_skills_path 配置）
  SKILL.md                         正文（带 frontmatter）
  .disabled                        存在即停用这份 user Skill
  <其他文件>                       用户资源，按需加载

~/.workpilot/skills/.builtin-disabled/<name>
                                   存在即停用同名 builtin Skill

<已授权工作区>/.workpilot/skills/<name>/
  SKILL.md                         project 层，跟仓库走
  .disabled                        存在即停用这份 project Skill
  <其他文件>                       项目资源，按需加载
```

运行时只扫描会话已经授权的工作区，并按 **project > user > builtin** 合并。同名 project
Skill 让项目自己的流程跟着仓库走；离开该授权工作区就不可见。user 同名覆盖 builtin 仍是
出厂 Skill 的 fork 路径：删掉 user 版本就恢复出厂版。builtin 不能删除；自动蒸馏也不能
占用 builtin 名字，避免模型生成的内容静默接管出厂流程。完整 procedure 和资源仍按需读取，
不会因为多一层就全部塞进 system prompt。

停用状态仍是标记文件而不是数据库行。builtin 的标记必须写在 user 根的
`.builtin-disabled/`：出厂目录可能只读，也会随升级替换，把用户偏好写进去既不可靠也会丢失。
当前出厂技能是 `skill-creator`、`immersive-reading` 与四个格式 Skill：`docx`、`xlsx`、
`pptx`、`pdf`。格式 Skill 通过通用文件工具、受控 Shell 和工作区 Artifact 交付，不注册
段落/单元格级 Office 正式工具。

### 4.2.1 轻量 Persona

Persona 是一份比 Skill 更薄的运行时描述：`system_block`、`tool_patterns`、
`default_approval_mode`、`recommended_connectors`、`recommended_work_mode`。内建 Persona
之外，用户可以在 `~/.workpilot/personas/*.toml` 定义自己的版本，项目可以在
`.workpilot/personas/*.toml` 覆盖同名版本。

会话只持久化 `persona_name`；一次 run 开始时把 Persona 快照进该 run 的 RunConfig。Persona 的工具面
只能收窄 registry，不能注册工具、授予 capability 或创建审批规则。默认审批档只在用户显式
切换 Persona 时应用；换 Provider、改模型等普通 runtime 更新必须保留当前审批档。

### 4.3 Skill 蒸馏候选 `skills-candidates/<capability_key>/`

```
SKILL.md                 蒸馏正文，可手工编辑
meta.json                状态、评分与晋升记录
evidence/<run_id>        空文件，一次独立成功一条
.queue/<run_id>.json     待蒸馏作业，来源快照自带
.queue/<run_id>.lock     作业租约（O_CREAT|O_EXCL）
.queue/<run_id>.failed.json  重试耗尽，留档但不再派发
```

候选落成与 Skill 同构的目录之后，「晋升」从"读 DB 里的文本 → 写文件 → 回写状态"这种跨两个
系统的双写，变成一次目录内的原子安装；人也可以在晋升前直接用编辑器改候选再晋升。

**evidence 用"一个 run 一个空文件"而不是 `meta.json` 里的数组**：计数是 `listdir`，写入是
`O_CREAT|O_EXCL`，天然幂等且不需要读-改-写，两个作业同时命中同一个 `capability_key` 也不会
互相盖掉对方的证据。

### 4.4 密钥与账户

| 文件 | 内容 | 权限 |
|---|---|---|
| `data/secrets/master.key` | Fernet 主密钥 | 0600，**在所有存储之外** |
| `~/.workpilot/provider_profiles.json` | Provider 配置 + 密文 API key | 0600 |
| `~/.workpilot/connector_accounts.json` | 连接器账户 + 密文 token | 0600 |

**只有载体从 Postgres 换成了 JSON，密文没有变成明文。** OpenWorker 的 `secrets.json` 存的是
明文（外加 `${ENV_VAR}` 引用），WorkPilot 已经有带主密钥的 `LocalSecretStore`，所以这一条
刻意没抄。

写入顺序是 `core/private_json.py` 定的：**先把父目录收到 0700，再写 tmp、chmod、`os.replace`**。
顺序反了会有一个窗口期文件是可读的。读失败一律返回 `{}`——一个损坏的配置文件不该让设置页
打不开。

原来靠 `lower(name)` 唯一索引做的重名检查，现在是 Python 侧的 `ProviderNameTakenError` /
`ConnectorNameTakenError`。

连接器类型本身不落第二份配置表。`cowork/connector_descriptors.py` 是代码内 catalog：一条
Descriptor 同时声明展示名、官方 API 主机、OAuth adapter、鉴权方式、默认 scopes、能力与
专用工具 registrar。账户校验、OAuth、工具请求和前端目录都消费它；平台专属 API 仍在各自
registrar 中提供固定 schema，不能退化成到处追加 `if account.kind`。

## 5. 三种删除语义

| 语义 | 做法 | 用在哪 |
|---|---|---|
| **软删除** | 打 `deleted_at` / `forgotten_at` / `revoked_at`，行还在 | 单条记忆、授权、订阅——需要"我什么时候撤销的"这个答案 |
| **失效** | 打 `invalid_at` + `superseded_by`，行还在且可查历史 | 记忆的改写（ADR-0005） |
| **物理删除** | 真的删文件 / 删行 | 附件、KB 索引、会话级联 |

单条“忘掉记忆”只做软删除，因为"他曾经这么说过、后来改了"本身是有用的信息；但用户显式
删除整个会话是隐私清除边界，会级联物理删除 conversation scope 记忆、抽取作业、Skill mute
与 Team audit。审计完整性不能凌驾于明确的数据删除动作。

## 6. 已经不存在的东西

删掉的时候要说清楚它去哪了，否则半年后看到旧代码里的引用会以为是 bug。

| 原表 | 去向 |
|---|---|
| `sources` / `source_sync_entries` | 删。连接器同步那条路径随 RAG 主答路径退役，KB 是"指着一个文件夹说索引这个" |
| `documents` / `document_versions` | 删。版本激活协议（约束 10）在 KB 路径上由 embedding 签名承担同一职责 |
| `parsed_blocks` / `parsed_block_locations` | **不再持久化**，但类型还在（`app/ingest/types.py: ParsedBlock`）。阅读引擎在内存里用它，进程内缓存 |
| `chunks` | 删。片段在 FAISS docstore 里 |
| `memories`（RAG 侧） | 并入 `cowork_memories`（§1.7） |
| `eval_*` | 见 [06 §4.5](06-评测体系.md)——这一块**目前是断的**，不是搬走了 |
| `conversations` / `messages`（PG） | → SQLite 索引 + JSONL |
| Alembic `migrations/`（35 个文件） | 删。改成 `PRAGMA user_version` |

> **约束 8 仍然成立但落点变了**：gold 标注"锚 `parsed_blocks` 字符区间、绝不锚 `chunk_id`"
> 这个判断没有被推翻——chunk 随分块策略而变，标注绑上去就废了。但 `parsed_blocks` 不再持久化，
> 所以重建评测轨时锚点应该是 **`(文件 content_hash, 页码, 字符区间)`**：文件哈希跨重建稳定，
> 页码是新的最小溯源单位。详见 [04 §5](04-知识与阅读设计.md)。
