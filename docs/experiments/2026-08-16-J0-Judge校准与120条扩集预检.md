# J0 · Judge 校准与 120 条扩集预检（2026-08-16）

## 结论先行

Judge 校准工程链路已经可用，但**正式校准尚未开始**：当前只有 20 个唯一生成 case、
覆盖 4/7 类，未达到 80 条门槛，也没有新的模型发送授权。系统因此保持 `pending`，
没有调用任何 Judge 模型，也没有产出 Kappa 数字。

120 条扩集方面，已经完成可重复的 dev/test 分割、候选构建、七类标注契约和独立审计，
但首版 80 条自动草稿被内容质量门禁拒绝，**一条都没有写进数据库**（既未落 candidate，
也未升 human）。这次拒绝是预期的 fail-closed 行为，不是 120 条已完成。

**扩集路线已改为「缩小规模、提高质量」**：不再硬凑 120，改为补一批人工撰写的
40 条（`m1-handwritten-40-v1`）。这批已经作者逐条复核通过并升为 `human`，
全库 human 标注因此从 40 条增至 **80 条**。这 40 条不含 `agent_task`——agent
运行时尚未实现，这一类只能写成空壳，详见「agent_task 缺口」一节。
因此**七类目前只覆盖六类**，agent_task 恒为 0。

## 目标与预注册门槛

| 项目 | 门槛 |
|---|---|
| 数据规模 | dev 100 / test 20；旧 40 只进入 dev |
| 类别分布 | single 25% / multi 20% / table 10% / temporal 10% / unanswerable 15% / global 10% / agent_task 10% |
| 语言 | 新增 dev 中英文各 30；test 中英文各 10 |
| 数据来源 | 新增 80 条在人工逐条复核前保持 `synthetic/pending_human` |
| Judge case | 80 个唯一 `(dataset,item_id)`，不得用多策略重复结果凑数 |
| Judge 指标 | answer correctness 0/1/2；准确率、QWK、混淆矩阵、边际与类别切片 |
| 验收 | validation 整体 QWK/accuracy ≥ 0.85；类别切片只诊断不设门禁（见下） |
| 模型 | 显式 provider/model，fallback=false，逐调用记录实际身份与 raw/reason/token |

### 复核修正：temporal 判据原本是坏的

首版 `temporal_without_historical_contrast` 按类别无条件打标，没有任何内容判断。
后果不是「严格」而是**死锁**：只要 120 条设计里有 temporal，内容门禁就永远非空，
`--apply` 永远失败，人工逐条改写也过不了。这不是 fail-closed，是坏掉的闸门。

已改成真实判据，满足任一即通过：证据跨 ≥2 个 version，或问题含明确的时间对照词
（`相比 / 变化 / 此前 / 更新前 / 改为 / 不再`、`compared with / changed from /
previously / no longer` 等）。词表刻意不收 `之前 / since` 这类过宽的词，否则改写者
随手加一个词就能骗过门禁。

当前 12 条 temporal 草稿**仍全部被判定**——它们确实是快照式提问（"At the time this
corpus version became active, what did X report..."），本来就没有跨时间点比较。
区别在于这个 12 现在是量出来的，且存在明确的通过路径。

## 转向：人工撰写 40 条（`m1-handwritten-40-v1`）

自动草稿的根因不是"质量不够需要润色"，而是**根本没有生成**：
`extractive-no-model-v1` 从 `parsed_blocks` 抽原文再套七句 f-string 模板，
锚点按文档顺序取前 N 个够长的块。没有任何环节判断过"这个问题能不能由这段证据
回答"——那需要语义理解，而语义理解需要模型或人，两者当时都没有。

因此 80 条里几乎没有一条能靠改措辞挽救：agent_task 12 条无证据无参数、
unanswerable 10 条同一模板、multi_hop 28/28 证据相邻、58 条 gold answer 原文照搬、
80 条 constraints 全空。"逐题改写"实际等于"重新出题"。

采纳的方案是**缩小规模、提高质量**：由助手阅读原文后撰写 40 条，
不硬凑 120。产物 fingerprint `21696951e2851b39`。

| 指标 | 自动草稿(80) | 人工撰写(40) |
|---|---:|---:|
| 内容质量门禁 | rejected（7 类 finding） | **passed（0 finding）** |
| gold answer 原文照搬 | 58 | 0 |
| gold answer 是作者块 / frontmatter / 图表标题 | 17 | 0 |
| constraints 全空 | 80 | 0 |
| multi_hop 证据相邻（< 1024 字符） | 28/28 | 0/8 |
| temporal 构成真实历史对照 | 0/12 | 8/8 |
| global 跨文档 | 0/12 | 8/8 |
| unanswerable 模板重复 | 10 条同 1 个 | 7 条各不相同 |

规模与纪律：dev 30 / test 10，zh 21 / en 19，57 条 gold span 逐条与
`full_text[char_start:char_end]` 精确比对通过，dev 与 test 的 document version
完全不相交。类别为 single_hop 7 / multi_hop 8 / table 2 / temporal 8 /
global 8 / unanswerable 7。

导入走的是与自动草稿**同一套** `import_candidates`（确定性 uuid5、幂等 upsert、
内容漂移即失败、`validate_eval_spans` 校验），只是换了 dataset 名与套件名，
导入纪律不允许有第二份实现。落库结果：

| dataset | split | 条目 | gold span |
|---|---|---:|---:|
| `core-dev-handwritten-zh-v1` | dev | 17 | 22 |
| `core-dev-handwritten-en-v1` | dev | 13 | 20 |
| `core-test-handwritten-zh-v1` | test | 4 | 4 |
| `core-test-handwritten-en-v1` | test | 6 | 11 |

导入时全部 `origin=synthetic` / `review_status=pending_human`，0 stale span，重复执行幂等。

### 复核与升级（2026-08-16 完成）

作者逐条复核通过后升为 `human`，经 `eval/promote_candidates.py` 执行。
升级前的 fail-closed 校验：40/40 落库内容与 manifest 逐字段比对无漂移、
`validate_eval_spans` 全过、复核人必须显式给出。升级动作把
`candidate_review` 一并改写为 `status=approved` 并写入 `reviewer` /
`reviewed_at` / `promoted_from`——**只翻 `origin` 而不留痕，事后就无法分辨
这批到底复核过没有**，所以留痕与升级是同一个事务里的一件事。

| 项目 | 结果 |
|---|---|
| 升级条目 | 40/40，全部 `origin=human` + `candidate_review.status=approved` |
| 复核人留痕 | 40/40 带 `reviewer` 与 `reviewed_at` |
| gold span | 0 stale，升级后复验仍全部有效 |
| 幂等 | 复跑显示 `already_human=40, to_promote=0`，不重复改写 |
| 全库 human | 40 → **80** |

升级后全库 human 的类别分布：`single_hop 21 / multi_hop 16 / table 12 /
unanswerable 15 / temporal 8 / global 8 / agent_task 0`。

**没有动 `core-dev` 与 `english-dev`**：新题落在独立 dataset，因此
`core-dev/human` 仍是 20 条，dataset fingerprint
`4a76d60a72d2…` 与 E1 检索/生成跑批时逐字符一致，
既有 E1 结论仍可复现、可比较。若日后把新题并入 `core-dev`，
E1 的 fingerprint 会变，届时必须重跑而不是沿用旧结论。

**撰写与复核的边界**：证据由助手阅读原文后选定、答案由助手综述，
作者复核确认后才升 `human`。CLAUDE.md 的"所有 gold answer 由作者亲手标注"
在这批上的成立方式是**作者逐条确认**，而非作者逐条起草；这个差别在对外表述时
不应含糊。

出题过程中被自身校验拦下并修正的两处，记录在案：

- 一条 unanswerable「ASP 用了多少 A100 GPU-hours」**实际可答**——论文附录写了
  "one node with 8 H100 GPUs ... approximately 48 hours"，正确回答会被判成幻觉。
  已换成 license 问题（`license` 在该论文零出现，全库 `released under` 零命中）。
  教训：unanswerable 必须逐条反查全库要害词，不能凭直觉。
- 一条 multi_hop 两段证据仅隔 130 字符，被间隔规则拦下。阈值取自分块参数
  （`DEFAULT_MAX_TOKENS=512`，中文最坏 1 token≈1 字符 ⇒ 1024 字符），
  保证任何单个 chunk 都装不下两段，否则是 single_hop 冒充 multi_hop。

## agent_task 缺口（阻塞七类验收）

**这 40 条一条 agent_task 都没有，是刻意的。**

`backend/app/agent/` 尚未实现，工具集不存在。此时写 agent_task 只能凭空编工具名
和参数——这正是自动草稿犯的错：12 条 agent_task 全部 `gold_spans` 为空、
`gold_tools` 的 `arguments` 全空、12 条 `gold_answer` 是同一句写死的英文常量
（中文条目也是英文）。这类条目无法判分，进库只会稀释指标。

由此产生三条连锁约束，必须一起看：

1. **数据侧**：七类中 `agent_task` 恒为 0，覆盖率上限是 6/7。
2. **Judge 侧**：`calibration_report` 里有一条无条件规则——
   `if "agent_task" in category_names: failures.append("agent_task_execution_closure_pending")`。
   也就是说**凑齐七类反而必然触发失败**。"凑够 80 条就能验收"的读法是错的。
3. **因此**：要么七类验收整体推迟到 agent 运行时闭环完成，要么先做六类验收拿中间
   结论并在结论里标注"未覆盖 agent_task"。这是一个待决策项，不是已解决项。

解除条件（缺一不可）：

- `backend/app/agent/` 有真实工具注册表，工具名与参数 schema 可枚举；
- agent run 能产出可核验的实际产物（副作用走 `tool_invocations` 幂等协议，
  见 [ADR-0007](../adr/0007-agent幂等与事件溯源.md)）；
- 在此基础上人工设计 agent_task 题目，`gold_tools` 写真实工具序列与必要参数。

在这三条满足之前，`agent_task` 的任何自动产出都应视为占位，不得入库。

## Judge 工程预检结果

校准工具已经实现四段式闭环：

1. `prepare`：从唯一 generation cases 导出冻结样本、人工标签模板和 rubric；
2. `run`：只有显式授权才允许调用模型，严格核对实际 provider/model；
3. `import`：以版本化 `judge_calibration/rubric/metric` namespace 合并写回，不覆盖
   M0 的 `human_label.citation_accuracy`；
4. `calibrate`：只用未参与 rubric 调整的 validation split 执行 QWK/accuracy 门禁，
   同时报告混淆矩阵、标签边际、类别切片、bootstrap CI 与逐条分歧。

| 缺失类别 | temporal / global / agent_task |
| calibration / validation | 15 / 5，稳定分层 hash |
| agent_task 执行闭环 | 未完成 |

### 复核修正：类别切片改为只诊断不设门禁

首版把 `min_slice_accuracy = 0.70` 直接作用在类别切片上，且没有最小样本量保护。
按预注册规模推：80 case → validation 20 → 7 类 → 每类 2~3 条。3 条错 1 条 = 0.667，
2 条错 1 条 = 0.5，都必然跌破阈值。这个门禁报出来的是「样本太少判不了」，
却写成了「Judge 在这个类别上不合格」——把抽样噪声当成质量结论。

要让逐类判定有意义，需要每类至少 5 条可解读样本 ⇒ validation ≥ 35 ⇒ 约 140 个
Judge case，**超出 120 条数据集规划本身**。因此采纳的方案是：

- 验收只卡 validation 的**整体** QWK / accuracy；
- 类别切片照常计算并报告，标注 `interpretable` / `below_threshold` /
  `insufficient_samples`，但不进 `gate_failures`；
- 报告强制携带一句 caveat：**类别级可靠性未验证，通过不代表每个类别都达标**；
- 判据一直在算，数据规模上来后 `--slice-gate-policy enforce` 一个开关即可打开。

**这是一个明确的能力缺口，不是已解决项**：在 120 条规模上，我们不会知道 Judge
是否在某个类别（尤其 table / temporal / agent_task）系统性偏斜。切片数值只能当
方向性线索用于人工归因，不能写进任何对外结论。

## 阶段决策

- 采纳扩集与 Judge 的工程基础设施和质量门禁。
- 不采纳首版 80 条自动草稿，不写入数据库，不升级 human。**放弃"逐题改写这 80 条"
  的路线**——实测几乎每条都要连证据锚点一起重选，等于重新出题。
- 不用四策略的重复答案凑 80 个 Judge case。
- 改为缩小规模：采纳人工撰写的 40 条，作者逐条复核通过后升 `human`，
  全库 human 达 80 条。不追求 120 这个数字。
- 新题保留在独立 dataset，不并入 `core-dev`/`english-dev`，以免作废 E1 的基线指纹。
- 若后续使用内网模型辅助出题，必须取得覆盖问题、gold answer、证据与答案的新授权。
- agent_task 的固定工作流和实际产物闭环完成前，七类 Judge 正式验收继续保持 pending。
  注意这是一条无条件规则（`agent_task_execution_closure_pending`）：**凑齐七类反而
  必然触发它**。所以要么整体验收推迟到闭环完成，要么先做六类验收拿中间结论——
  「凑够 80 条就能验收」的读法是错的。
- 类别级可靠性在 120 条规模上不做验收（见上），作为已知缺口带入下一阶段。
