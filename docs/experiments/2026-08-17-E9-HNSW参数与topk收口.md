## 0. 假设

[E7](2026-08-16-E7-retrieval-miss归因.md) 把 11 条 retrieval miss 拆成两组，
并推断 B 组（5 条 / 8 个 span，`relevant_chunk_not_ranked`）是**多样性**问题
——单一文档霸榜 top-K，题目真正需要的第二篇被饿死。

但 B 组的症状（chunk 已索引、同文档其他块已召回、该块从未进入 50 深排序）
也完全符合另一个解释：**HNSW 候选扫描不足**。这正是 [03 §4.1](../03-数据模型.md)
点名的 pgvector 陷阱。两个解释的修法完全相反，必须先分开。

假设：调大 `ef_search` / `max_scan_tuples` 能把 B 组的 8 个 span 捞回来。
若不能，则 E7 的多样性诊断成立，且扫描深度这条线可以关掉。

## 2. 机制：HNSW 索引根本没被用上 ★

不是"调了没效果"，是**这几个参数当前完全不起作用**。对生产同形状的查询做 EXPLAIN
（字面量向量、带 `strategy` 与 `is_searchable` 过滤、带 `, c.id` 全序 tiebreak）：

```
Limit  (cost=1551.80..1551.92 rows=50)  (actual time=7.000..7.005 rows=50)
  -> Sort  (Sort Method: top-N heapsort  Memory: 30kB)
       -> Seq Scan on chunks c  (actual time=0.028..6.823 rows=1862)
            Filter: (is_searchable AND (strategy = 'heading'))
```

**规划器选的是顺序扫描 + top-N 堆排序，不是 `idx_chunk_vec_heading`。**
`heading` 策略下可检索 chunk 只有 1,862 条，全表扫一遍 6.8ms，比走索引便宜。
`SET LOCAL hnsw.*` 那三个 GUC 因此是空操作——这解释了为什么四个配置逐位相同。

排除过的两个替代解释（都实测否掉了，不是推测）：

- **不是 `, c.id` tiebreak 挡住索引**：去掉 tiebreak 仍然是 Seq Scan。
- **不是索引坏了**：`enable_seqscan=off` 强制后走的也不是向量索引，仍是排序路径。

推论有两条，方向相反但都重要：

1. **当前 dense 臂实际上是精确检索**，不是近似。召回率上限已经拿满，
   B 组的缺失不可能来自候选生成——**E7 的多样性诊断因此被独立证实**。
   这也顺带解释了另一件事：8/16 原批与今天的 baseline **逐条逐位相同**
   （span recall 差异 0 条），检索轨的可复现性来自"根本没有近似"。
2. **这个结论强依赖语料规模。** 语料涨到规划器改用索引之后，
   03 §4.1 那个陷阱（部分索引 + `iterative_scan`）就会真正生效，
   届时必须重跑本实验。**现在不调，不等于以后不用调。**

## 3. top-k：确认 E7 的结论，不调

E7 已经论证过不该调 `top_k`，本轮独立复核了它的关键数字并补了一个更硬的量化：

| 项 | E7 台账 | 本次独立复算 |
|---|---:|---:|
| K=10 的 context precision | 0.1035 | **0.1035**（一致） |
| 覆盖 A 组全部 gold span 所需 K | 35 | —（沿用） |

补充量化 —— **单文档霸榜比 E7 举的 5 个例子更普遍**：

- Top-K 里最大单文档占比 **均值 75.86%**
- **25/70 条题目的 Top-K 被单一文档 100% 独占**

也就是说，三分之一强的题目里，检索给生成模型看的十个块全部来自同一篇文档。
对跨文档题这直接等于答不了。加大 K 改不了这个比例（挤占是排序造成的，不是深度），
而 gate 的 6000 字符预算在前十名附近就耗尽——**K 再大也到不了门控模型面前**。

**决策：`top_k=10` 不动。** 该修的是排序多样性（按 `version_id` 限额 / MMR 去冗），
不是候选深度。

## 4. 一个工程缺陷（顺手修了）

`eval/dense_baseline.py` 的 `config` 字典**不含任何 HNSW 参数**，而 `config_hash`
就是这个字典的 sha256。后果不只是"报告里查不到用了什么参数"：

`reuse_completed` 按 `config_hash` 复用已完成的 run —— 于是
**两次只改 `ef_search` 的跑批会算出同一个 hash，第二次直接把第一次的结果原样返回。
实验看起来跑了，其实没跑，而且看不出来。**

这正是本实验要做的事，不修就会拿到假的"逐位相同"。
已把 `hnsw_ef_search` / `hnsw_iterative_scan` / `hnsw_max_scan_tuples` 三项加进 config。

> 与 C 台账那次 `label` 撞车、以及 J1 的 `enable_thinking` 是同一类问题：
> **影响输出但没进配置指纹的参数，会让实验静默失效。**
> 三次了，值得作为一条检查项固定下来。

## 5. 决策与遗留

**两项都维持现状**，本轮不产生任何配置变更：

- `hnsw.ef_search=100` / `max_scan_tuples=20000` / `iterative_scan=relaxed_order` 不动
- `top_k=10` 不动

遗留：

- [ ] **语料规模到多少时规划器会改用向量索引**？需要一个阈值观测，
      到点前本实验的结论都要打个"当前规模下"的前缀
- [ ] B 组的真正修法（排序多样性）：按 `version_id` 限额、MMR 去冗、
      或跨文档题走子查询分解后按子查询分名额。**这才是下一个该做的检索实验**
- [ ] `alpha_ndcg_at_k` 当前恒等于 `ndcg_at_k`（0.7117），多样性维度没被测出来；
      修多样性之前得先把这个观测指标修好，否则改了也看不见
- [ ] 把"影响输出的参数必须进 `config_hash`"补成一条检查项或测试
