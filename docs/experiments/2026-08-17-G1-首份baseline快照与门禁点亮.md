## 1. 为什么重跑而不是直接用 8/16 的批次

`m1-dev70-finalists`（8/16）就是 E1 的正式批次，数字可用。但 baseline 快照会被提交进 git，
成为此后每次改动的判据，所以它必须满足两条：

1. **git_sha 等于当前 HEAD**。8/16 之后合入了 E5 证据门控修复、E8 阈值结论、E9 参数收口，
   快照挂在旧 sha 上，日后回看无法判断"这份基线是哪套代码跑出来的"。
2. **只含生产配置**。finalists 批次同时跑了 `heading` 与 `semantic` 两套，
   是对照产物；baseline 只应该是生产那一套。

代价是一次本机跑批（70 条，约 5 分钟，全本地模型，零外发、零费用）。

### 顺带得到一次复现验证

| | span Recall | budget Recall | nDCG | α-nDCG | MRR | ctx precision |
|---|---:|---:|---:|---:|---:|---:|
| 8/16 原批 / E9 baseline | 0.7924 | — | 0.7117 | — | — | 0.1035 |
| 本轮（HEAD `92dd6b8`） | **0.7924** | 0.8012 | **0.7117** | 0.7117 | 0.7116 | **0.1035** |

span 诊断分布同样逐位一致：`hit 64 / outside_top_k 15 / relevant_chunk_not_ranked 8`。
跨 12 小时、跨若干次合入，检索轨**逐位可复现**——这正是 E9 §2 的推论：
当前语料规模下规划器走顺序扫描，dense 臂实际是精确检索而非近似，没有随机性来源。

失败样本 0 条。延迟 mean 4338ms / p95 4765ms（不进门禁，理由见 G0 结论 3）。

## 2. 快照的隐私审计

快照要进 git，所以逐字段扫过一遍（约束 7 与 06 §4.2 的白名单设计）：

- 70 条，246KB，字段只有数字、UUID、`gold_fingerprint`（sha256 前 16 位）
- 全文正则扫描 **0 处** CJK 字符、**0 处** 超 80 字符的字符串
- `answer` / `gold_answer` / `citations[].title` / `span_diagnostics[].quote` /
  `source_uri` / `document_id` 均不存在

白名单而不是黑名单的价值在这里兑现：`retrieved[]` 里留下的是 `chunk_id` / `version_id` /
`char_start` / `char_end` / `content_tokens`，**位置留了、原文没留**，
既能判回归又不把语料带进版本库。

## 3. 三条路径实跑验证

工具能跑 ≠ 门禁在工作。三条路径各跑一次真报告：

| 路径 | 输入 | 期望 | 实际 |
|---|---|---|---|
| 通过 | baseline 跑批自比 | 退出码 0 | ✅ 全部 +0.0000，成本 +0.0% |
| 阻断 | E1 的 `semantic` 跑批 | 退出码 1 | ✅ 5 项指标回退，逐项列出 |
| 拒判 | `core-dev` 的 M0 跑批（数据集不同） | 退出码 2 | ❌ **traceback + 退出码 1** |

第三条挂了。见下节。

### 阻断路径抓到的正是 E1 那个取舍

`semantic` 候选被拦下的同时，成本一项是 **-16.8%**：

| 指标 | baseline(heading) | semantic | 判定 |
|---|---:|---:|---|
| span_recall_at_k | 0.7924 | 0.7719 | 回退，阻断 |
| ndcg_at_k | 0.7117 | 0.6541 | 回退，阻断 |
| mrr | 0.7116 | 0.6547 | 回退，阻断 |
| retrieved_tokens | — | **-16.8%** | 通过（上限 +20%） |

这就是门禁设计意图的实证：**它不阻止你做取舍，它逼你把取舍显式化**。
想让 semantic 上线，正确动作是重新生成 baseline 并把这张表写进台账，不是放宽阈值。

## 4. 抓到的真 bug：拒判与不合格撞了退出码 ★

`gate.py` 的模块文档写得很清楚：

> fail-closed：候选跑批含失败样本、gold span 指纹与 baseline 不一致、**数据集不一致、
> 受控配置漂移**，一律拒绝判定（**退出码 2**），与"判为不合格"（退出码 1）分开。

四个条件里**只有前两个真的这样做了**。原因是异常来自两个层：

- `_reject_incomplete` / `_reject_gold_drift` 在 `gate.py` 里，抛 `GateRefused` → 退出码 2 ✅
- 数据集不一致、受控配置漂移、`item_id` 配不上，都在 `compare.py` 的
  `check_compatibility` / `pair_items` 里，抛 `ValueError` → `main()` 不接 → 
  **traceback + 退出码 1** ❌

`ValueError` 对 `eval.compare` 是合适的：那是人在终端手工比两次跑批，看见 traceback 就改命令。
但门禁是给夜间自动化用的，退出码是唯一契约。撞码的后果很具体：
**把"跑批配错了"报成"质量回退"**——最坏的情况是有人为了让门禁变绿去改检索代码，
而真正的问题只是传错了一个目录。顺带还违反约束 4：吐给调用方的是 stack trace 而不是可执行说明。

**修法**：在 `gate.py` 里把比较层的 `ValueError` 统一转成 `GateRefused`，
不改 `compare.py` 的对外口径（那条链路的语义是对的）。候选报告本身载入失败同样归入拒判。

修复后：

```
$ eval.gate check <core-dev 的跑批> --against working
门禁拒绝判定：数据集不一致，配对比较无效: baseline=m1-dev-70, candidate=core-dev
退出码=2
```

已按棘轮登记为 `G1-门禁拒判退出码撞车`，四条用例锁住（`test_eval_gate.py`）。
其中两条原本断言的就是 `ValueError`——**测试把错误的契约钉住了**，
所以本轮同时改了断言。这也是个教训：测试写的是"当前行为"还是"应有行为"，
在异常路径上特别容易搞混。

## 5. 结论与边界

**一句话结论**：首份 baseline 快照已提交，夜间门禁的通过 / 阻断 / 拒判三条路径全部实跑验证；
点亮过程中修掉一个会把配置错误误报成质量回退的退出码 bug。

**当前门禁的覆盖边界**（不写清楚就会被误读成"质量已经被全面挡住"）：

- **只覆盖 retrieval 轨**。生成轨的 baseline 需要一次带模型外发的正式跑批，尚未做。
- `refusal_correct_at_threshold` 进了门禁，但**当前几乎没有分辨力**：
  阈值 0.35 下 `true_refusal = 0 / false_refusal = 0`，13 条不可答全部由证据门控（生成轨）
  拦下，分数门一条都没贡献（E8 §2 已证明这条参数是死的）。它现在恒为 57/70 = 0.8143，
  只有当 `top_score` 跨过 0.35 才会动。**留着不是因为它有用，是因为它变了就说明分数分布变了。**
- `answer_correctness` / `faithfulness` / `citation_accuracy` 仍是 pending。
  J2 已校准 binary correctness，但快照还不携带 Judge 字段。
- 语料规模一变（E9 §2：规划器改用向量索引后），检索轨的逐位可复现性会消失，
  届时零回退阈值必须按新的噪声地板重定。
