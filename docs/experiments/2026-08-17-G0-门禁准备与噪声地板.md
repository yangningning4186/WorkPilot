## 1. 已落地：静态轨门禁

`.github/workflows/ci.yml`。此前仓库**根本没有 `.github` 目录**，09 排期里"静态检查范围
已冻结"冻结的只是范围，没有任何东西在执行它。

| job | 步骤 | 服务 |
|---|---|---|
| `backend` | `uv sync --locked` → ruff → mypy → pytest | postgres(pgvector) + redis |
| `frontend` | `npm ci` → eslint → tsc | — |

刻意**不挂任何评测跑批**：smoke 规则轨的 fixture 未就绪，先挂上去就是一条常红的门禁，
而常红的门禁等于没有门禁（06 §4.3）。

### 验证方式与抓到的两个真实缺陷

本机全绿不构成 CI 会绿。用 `git worktree` 开了一份干净检出（**没有被 gitignore 的
根 `.env`**）逐条跑，抓到两条只在 CI 上才会炸的问题：

1. **pytest 需要真 Redis。** `test_rate_limit.py::test_redis_token_bucket_enforces_burst_atomically`
   直接 `Redis.from_url(Settings().redis_url)`，`/ready` 健康检查同理。把 `REDIS_URL`
   指向死端口复现：2 failed / 32 passed。→ workflow 补 redis service。
   其余 redis 相关用例注入的是假客户端，不受影响。

2. **`npm run typecheck` 在干净检出里必失败。**
   `src/app/layout.tsx:11` 用了 `LayoutProps<"/">`，这是 Next 生成的全局类型，
   来自 `.next/types/`。本机因为 `.next/` 已经被 `next dev` 填过所以看不出来；
   干净检出直接 `error TS2304: Cannot find name 'LayoutProps'`。
   → 修在 `package.json` 而不是只修在 workflow 里：`"typecheck": "next typegen && tsc --noEmit"`。
   放 workflow 里只能救 CI，放 npm script 里才能让 CLAUDE.md 写的那条命令
   在新克隆的仓库上真的能跑。

干净检出复跑结果：ruff 通过、mypy 93 文件通过、pytest **378 passed**（全新库，
migrations 自己 `CREATE EXTENSION vector`）、eslint 通过、tsc 通过。

> 顺带确认：378 条用例**不依赖根 `.env`**。这件事必须实测，
> 因为 `.env` 里有 `EMBEDDING_DIM`、`DEMO_ADMIN_PASSWORD_HASH` 这类会改变行为的值。

## 2. 噪声地板：把实验 C 的三次重复重新拆开算

C 台账只报了引用对齐一列。这里按配置 × 指标全量重算跨度（max − min，pp）：

| 配置 | 生成 | 门控 | 拒答正确 | 引用有效 | 约束通过 | 引用对齐 | 完成题数 |
|---|---|---|---|---|---|---|---|
| C1 | heavy | heavy | 5.26 | 0 | 0 | **9.52** | 0 |
| C2 | main | main | 0 | 0 | 0 | 0 | 0 |
| C3 | light | light | 0 | 0 | 0 | 0 | 0 |
| C4 | light | main | 0 | 0 | 0 | 0 | 0 |
| C5 | main | light | 0 | 0 | 0 | 0 | 0 |
| C6 | heavy | main | 1.58 | 0 | 2.89 | **13.48** | 1 题 |
| C7 | main | **heavy** | 0 | 0 | 0 | 0 | 0 |

### 结论 1：噪声只来自 heavy 的**生成**槽位 ★

C 台账写的是"只有含 heavy 的两个配置在三次重复间抖动"。**C7 也含 heavy**——它把
heavy 放在证据门控上——而 C7 在四个质量指标上逐位一致，`total_tokens` 三次只差 0.5%。

抖的是 C1 和 C6，两者的共同点不是"含 heavy"，是**生成档 = heavy**。

机制上说得通：门控输出的是短的、离散的判定，采样噪声要翻转它得跨过一整个决策边界；
生成输出的是长自由文本，第一个 token 的微小数值差异会一路放大成完全不同的引用集合。
**所以不能把这条推广成"heavy 用在门控上就是确定性的"**——真正的判据是
输出是短离散量还是长自由文本，换个短输出任务用 main 也可能抖。

对实验 J 的影响比 C 台账写的更宽松一档：基准 Judge 输出的是 0/1/2 三档离散标签，
属于"短离散"那一类，**未必**需要多次重复；但这要实测，不能靠这里的类比直接免掉。

### 结论 2：分母自己会动，所以那不是配对比较

C6 的 `completed_count` 三次是 19 / 20 / 19——**错误本身是不确定的**。
引用对齐的分母更夸张：30 / 23 / 21，因为模型每次吐的引用条数不一样。

一个分子分母都在动的比率，跨跑批比较时根本不是配对的。这直接说明门禁不能只比聚合率，
**必须逐样本配对**（compare.py 已经是这么做的，门禁要沿用同一套口径）。

### 结论 3：成本口径安全，延迟口径不安全

| 指标 | 非 heavy 生成 | heavy 生成 | 06 §4.2 阈值 | 判定 |
|---|---|---|---|---|
| `total_tokens` | **0%**（逐位相同） | 7.8% ~ 8.8% | 上涨 ≤ 20% | 阈值 > 噪声，**可用** |
| 平均延迟 | 2.7% ~ 12.0% | 10.9% ~ **75.8%** | p95 上涨 ≤ 30% | C6 单配置就冲破，**不可用** |

延迟这一列还是**串行、同一台机器**测出来的；C 台账自己也标了"C1/C2/C6/C7 与
C3/C4/C5 在不同时间跑，墙钟横向比较存在机器负载差异"。
GitHub runner 的抖动只会更大。→ **延迟不该进 PR 门禁**，要么放 nightly 且大幅放宽，
要么单独用固定机器测。

## 3. 阈值不能比一条样本更细 ★

比噪声更硬的约束是**量化下限**：题集上的比率指标只能取 `k/n`，一条样本翻转就是一格。

| 数据集 | n | 一条样本 = |
|---|---:|---:|
| PR smoke（06 §3 规划 20–30 条） | 20 | **5.00 pp** |
| | 30 | **3.33 pp** |
| m0-core-40 | 40 | 2.50 pp |
| m1-dev-70 | 70 | 1.43 pp |
| 曾规划的 120 条 | 120 | 0.83 pp |

06 §4.2 写的 `answer_correctness` 下降 ≤ **2pt**、`span_recall@10` 下降 ≤ **3pt**：

- **在 20–30 条的 smoke 上不可表示。** 20 条时最小的非零回退是 5.00pp，
  一步就越过 2pt 和 3pt。这条阈值实际执行下来等于"**一条都不许退**"，
  但写成百分比会让人误以为留了容错余量。要么把它如实写成"回退样本数 = 0"，
  要么把 smoke 扩到阈值能表示的规模。
- **在 70 条 dev 上是有意义的**：1.43pp 一格，2pt 阈值 ≈ "最多允许 1 条回退"
  （1.43 ≤ 2 < 2.86）。所以 §4.2 那张表在 nightly 尺度上自洽，在 PR 尺度上不自洽。

这也是 06 §4.2 表尾那句"上表是所有层级的完整门禁集，不是 PR smoke 都能计算"
需要补上的另一半：不只是**算不算得出来**，还有**表不表示得了**。

## 4. 规则轨能不能要求逐位相等：确定性审计

如果 PR 门禁不调模型，理论上应该完全确定性，阈值就可以是"快照逐位相等"。逐条查了链路：

| 环节 | 是否确定性 | 依据 |
|---|---|---|
| dense 排序 | ✅ | `ORDER BY c.embedding <=> ..., c.id` —— 有全序 tiebreak |
| lexical 排序 | ✅ | `ORDER BY score DESC, length(c.content), c.id` |
| RRF 融合 | ✅ | `sorted(key=(-score, str(chunk_id)))` |
| chunk id | ✅ | `_chunk_id()` 是 `uuid5(version_id, strategy, signature, chunk_index, char_start, char_end)`，**内容寻址** |
| version_id / block_id | ❌ | `uuid7()`，每次 ingest 都不一样 |
| HNSW 检索 | ⚠️ | 图构建带随机性；`ef_search` 限制候选池 |

结论：**规则轨确实可以要求逐位相等**，阈值不是百分比而是"零样本回退"。
这同时绕开了第 3 节的量化下限问题——不比率，就没有 5pp 一格的麻烦。

两条推论，以及它们后来的命运：

1. ~~**fixture 必须是冻结 UUID 的数据库 seed，不能是"CI 里重跑一遍 ingest"。**~~
   `version_id` 是 uuid7，重跑 ingest 会换掉它 → chunk id 全变（tiebreak 跟着变），
   更要命的是 **gold span 锚在 `block_id` 上**（约束 8），block_id 也是 uuid7，
   重新 ingest 等于把标注的锚整个换掉。
   → **第 5 节决定取消 PR 评测层后，这条作废**：夜间跑在本机真库上，
   `version_id` / `block_id` 本来就稳定，不需要冻结任何东西。
   保留在这里是因为它是"PR 层要付多少工程代价"这个判断的依据之一。

2. **不要在小规模数据上建 HNSW 索引。** 几十个 block 的规模下 pgvector 走精确扫描，
   既确定又快；建了 HNSW 反而引入图构建的随机性。
   `SET LOCAL hnsw.*` 那几个 GUC 在没有索引时是无害的空操作。
   这条对夜间层仍然成立，只是边界换了个位置：真库上索引是长期存在的，
   所以 HNSW 参数回退归夜间门禁管，与 06 §4.1
   "涉及 embedding 模型本身的变更只在 nightly 重建索引评测"是同一条边界。

## 5. 决策：分层从三层收成两层 ★

原设计的 PR 评测层（20–30 条 smoke 快照 diff）**取消**。分层变成：

| 层 | 跑什么 | 在哪跑 |
|---|---|---|
| **每个 PR** | 静态检查 + `pytest`（含 regression 用例） | GitHub Actions |
| **每晚 / 里程碑** | 完整 `core-dev` 真语料 + Judge | 本机/集群 |

决策依据是一次覆盖度核对：`backend/tests/` 现有 51 个文件、12006 行，
规则轨想测的每一项都已经有对应用例，且每个 PR 都在跑——

| 门禁本来想测的 | 已有用例 |
|---|---|
| 检索 → 生成 → 引用链路 | `test_retrieval_generation_and_block_citation_chain`（真库 + 确定性 provider，端到端） |
| RRF 融合 / 精确标识符 | `test_lexical_terms_and_rrf_cover_exact_identifier` |
| 词法三模式排序 | `test_ranked_modes_beat_coverage_on_english_stopword_query` |
| 证据打包与字符预算 | `test_evidence_is_block_anchored_and_respects_character_budget` |
| 引用 fail-closed | `test_unknown_or_missing_citation_fails_closed` |
| 两条拒答路径 | `test_low_score_refuses_before_generation`、`test_semantically_insufficient_evidence_refuses_before_answer_generation` |
| E5 gate 修复 | `test_gate_evidence_keeps_rerank_order_and_later_blocks` |
| HNSW 与精确扫描等价 | `test_index_scan_returns_the_same_top_k_as_exact_search` |

三条理由：

1. **合成 fixture 上的"逐位相等快照"就是 golden-file 测试**，天然属于 pytest。
   另起一套 eval 快照只是换个地方做同一件事，失败信息还更差——
   assert 指出哪条不变量断了，快照 diff 只会说"17 个数变了"。
2. **上表已经覆盖完了**，边际价值薄。
3. **合成语料上的指标不是质量信号。** PR 层不连私人库就只能用手写的公开 fixture，
   在它上面报"span_recall 掉了 3pp"没有意义，"PR 贴指标 diff"的叙事立不住。

**代价（必须记下来，不许粉饰）**：改了检索策略（RRF 的 k、top_k 默认值、打包顺序）的
PR 能在没有任何**指标**检查的情况下合入——测试挡的是行为破坏，不是质量回退。
兜底是约束 6 加夜间门禁，单用户产品上暴露窗口小于一天。这是交换，不是白拿。

连带取消：公开 fixture 语料、预计算 embedding 入 git、冻结 UUID 的 DB seed。
**约束 7 与门禁之间原本的张力随之消失**——这是取消 smoke 最大的一笔额外收益。

其余三条决策：

- **rerank 不进门禁**（原问题在"smoke 里放不放 rerank"，随 smoke 取消而消解；
  夜间层跑在本机，cross-encoder 可达，按线上策略跑）
- **阈值形态**：规则轨零样本回退（依据是 `main` 档逐位一致），
  Judge 打分的三项等实验 J 收口再启用
- **延迟移出门禁**（依结论 3）

## 6. 落地后的一处规则更正 ★

`eval/gate.py` 写完后拿 E1 的两份真实报告试跑，发现**第 5 节定的规则太严，是错的**。

原规则：规则轨"不允许任何一条样本回退"。理由看起来很硬——噪声地板实测是 0，
任何回退都是真的。但拿 semantic 当候选、heading 当 baseline 一跑：

| 指标 | 聚合 Δ | 逐样本 |
|---|---|---|
| `span_recall_at_k` | −0.0205 | 5 胜 / 5 负 |
| `ndcg_at_k` | −0.0576 | 13 胜 / **21 负** |
| `mrr` | −0.0569 | 13 胜 / 13 负 |
| `context_precision` | **+0.0018** | 7 胜 / 6 负 |
| `retrieved_tokens` | **−16.8%** | — |

按逐样本零回退，连聚合是**正**的 `context_precision`（+0.0018，7 胜 6 负）都会被拦下。
任何真实的策略改动都会动几十条样本的排序，这条规则等于"什么都不许改"——
天天红的门禁最后会被习惯性点忽略，比没有门禁更糟（正是 06 §4.3 自己警告过的失效模式）。

**更正后**：阻断条件是**聚合值**零回退，逐样本胜负照算、照报，但只作信息不作阻断。
"噪声是 0 所以不留百分比余量"这个论证依然成立，它论证的是**零容忍**，
不是**逐样本**——这两件事被我一开始混在一起了。

`context_precision` 那一格是这次更正的判据：它是唯一一个逐样本有输赢、
聚合却是正的指标。如果一条规则连它都拦，那条规则量的就不是"变好还是变坏"。

> 教训与 C 台账那条同构：**先确认判据量的是不是你要的东西，再上规则。**
> 这次是靠"写完就拿真实数据跑一遍"发现的，不是靠想。
