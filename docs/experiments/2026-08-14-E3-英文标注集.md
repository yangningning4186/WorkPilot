# E3 · 补纯英文标注集，实测 E2 的英文收益（2026-08-14）

## 背景

[E2](2026-08-14-E2-分语言tsvector与词法排序函数.md) 把词法打分换成分语言 tsvector +
`ts_rank`，中文侧显著提升。但 E2 的结论里挂着一个自己承认的洞：

> 三个数据集 **49 条题全部含中文，0 条纯英文**，而语料里 20 篇 PDF 全是英文论文。

也就是说 E2 最初要修的那条毛病——英文自然语言查询下词法臂完全失明——
**一条指标都没测到**。E2 换默认的依据里，英文收益是"未计入"，不是"已验证"。
本次先补数据集，再回头量那个收益。

## 结论

- 英文收益**是真的，而且显著**：词法单臂 Recall@10 从 **0.6562 → 0.8750**，
  Δ **+0.2188（CI [+0.0625, +0.4375]）**，16 条可答题里 **4 条变好、0 条变差**。
  single_hop 从 0.5714 直接到 **1.0000**。
- 但**融合后的收益恰好为零**：`dense-lexical-rrf` 三档打分的 Recall@10 全是 0.8125，
  逐样本 Δ = **0.0000，16 条全部持平**。这不是四舍五入，是逐条相同。
- 一个没预期到的收获：英文集上**拒答 AUROC 从 0.734 提到 0.969**。
  E2 换默认在英文上换来的主要是拒答判别力，不是 Top-10 召回。
- 顺带修了评测框架的一个真缺陷：`config_hash` 漏了 `dataset`，
  同参数跑不同数据集会撞出同一个 hash（E2 台账里 6 组 hash 与 E3 的重了）。

## 数据集

`english-dev`，20 条，最初以 `origin='synthetic'` 写入，`split='dev'`。
种子脚本 `eval/seed_english_dev.py`，gold span 锚 `parsed_blocks` 字符区间（约束 8），
脚本里只写 `(标题前缀, block_idx)`，字符区间入库时从激活版本现取。

| 类别 | 条数 | gold span 数 |
|---|---:|---:|
| single_hop | 7 | 7 |
| table | 5 | 5 |
| multi_hop | 4 | 8 |
| unanswerable | 4 | 0 |

gold 覆盖 9 篇英文论文：ReAct（6 span）、Toolformer（3）、AgentBench（2）、
ToolLLM（2）、Reflexion（2）、GAIA（2）、VOYAGER（1）、SimpleMem（1）、MetaGPT（1）。

**两条有效性前提写进了种子脚本，违反即拒绝入库：**

1. **问题不得含任何 CJK 字符。** 混一个中文词进去，中文 bigram 列就会开始出力，
   测的就不再是英文路径。
2. **问题不得与 gold 原文连续重合 4 个词。** 这条最关键——
   如果题目是从证据块里抄的，词法臂靠字面重合就能命中，
   测出来的是抄袭度不是检索能力，整个集直接失去意义。
   窗口取 4：3 个词在英文里太容易自然撞上（"the number of"），5 个词几乎放行一切。

两条都补了单元测试（`test_eval_metrics.py`），并额外校验 `unanswerable`
与 gold span 的有无严格互斥。入库后又在库里核对了一遍
`gold_spans[].quote` 与 `parsed_blocks.text` 逐字一致：**0 条 stale**。

4 条 unanswerable 都是同主题 hard negative——落在语料覆盖的领域内，
但答案确实不在库里（ReAct 的商业订阅价、AgentBench 要求的 Kubernetes 版本、
Toolformer 训练的碳排放、DeepWisdom 的团队规模）。

**2026-08-14 复核升级：** owner 已逐条人工复核全部 20 条，并明确确认可以标记为
`origin='human'`。正式 M0 suite 因此将其与 `core-dev` 合并为 40 条 human；种子脚本仍坚持
写入 `synthetic` 候选，未来重新 seed 后必须再次人工复核，不能让脚本自动升级证据等级。

## 归因

**英文单臂的提升落在 single_hop，符合预期。** 英文 single_hop 题恰好是
"自然语言句子 + 一两个判别词"的形状，也就是 coverage 被停用词灌满的那个场景。
`english` 配置丢掉 how/does/in/the、把 embeddings 还原成 embed、
且是词元匹配不是子串匹配，判别词才拿得回权重。
table 类两档都是 1.0000——表格块本来就塞满数字和专名，任何打分都能命中，
这类题对词法改动不敏感。

**融合后 Δ 恰为 0，说明 dense 在这个集上已经吃满。** 英文单臂从 0.6562 抬到 0.8750，
甚至反超 dense-only 的 0.6875，但 RRF 的 Top-10 一条都没变。
RRF 只看名次不看分数，一条证据只要在任一路进了前列就会被融合捞上来；
dense 在这 20 条上已经把该捞的都捞到了，词法臂变强只是**把同一批证据换了个路径捞**。

这条要说清楚，因为它限定了 E2 的决策依据：
**E2 换默认在英文上买到的不是 Top-10 召回，是拒答判别力和冗余度。**
AUROC 0.734 → 0.969 说明融合后的 top score 对"有没有证据"的区分变干净了；
而两条路都能捞到同一批证据，意味着 dense 单点失效时有真正的兜底——
这个价值在 Recall@10 上看不见，要靠 dense 退化场景才测得出来。

**`ts_rank_cd` 在英文上同样是最差的（0.5625，低于 coverage）。** E2 归因说
cover density 是被中文 bigram 坑的，英文这边说明问题更普遍：
OR 语义的 tsquery 下，cover density 会奖励"少数几个词挨得紧"，
而英文长句查询里挨得紧的往往是残留的功能词组合。

**融合 nDCG/MRR 轻微变差（−0.0396 / −0.0469，CI 跨 0，3 好 6 差 7 平）。**
方向不利但不显著，且发生在 Recall 完全不变的前提下，属于 Top-10 内部的重排抖动。
n=16 不足以定论，记在这里等数据集扩容后复查。

## 顺带修的缺陷：config_hash 漏 dataset

`eval/dense_baseline.py` 与 `eval/refusal_baseline.py` 的 `config` 字典里有
`strategy` / `top_k` / `origin` / `lexical_mode` 等等，**唯独没有 `dataset`**。
后果是同一套参数跑 `multihop-test-v1` 和 `english-dev` 会得到**完全相同的 config_hash**——
E2 台账追溯段里的 6 组留出集 hash 与本次英文运行逐个撞上。
`dataset` 在报告里是独立字段，所以结果本身没错，但台账拿 config_hash 当 run 句柄，
撞了就会指错运行。

已把 `dataset` 加进两处 config 字典并重跑 E2 的 12 组 + E3 的 7 组，
**指标逐位一致**（改的是 hash 的输入，不是评测逻辑），E2 台账的追溯段已换成新 hash。

## 决策

1. **`english-dev` 进常规对照集**，凡是动词法检索、分词、查询改写的实验，
   必须同时报中文集与英文集。E2 的教训是全中文题集会把英文失效整个藏起来。
2. **E2 的换默认结论维持**，但依据要改写准确：
   英文上买到的是**拒答判别力（AUROC 0.734 → 0.969）与检索冗余**，
   **不是 Top-10 召回**（Δ 恰为 0）。E2 台账已加交叉引用。
3. **英文集作者复核已完成。** 20 条已逐条复核并升级为 `origin='human'`；
   复核 provenance 固化在 `eval/suites/m0-core-40.json`。
4. **新增待办：融合方式本身要做实验。** RRF 只看名次不看分数，
   所以词法臂变强完全没能转化成融合收益。分数加权融合、
   或按查询语言动态调整两路权重，都值得单独测。
   这比继续调词法打分更可能拿到融合层的收益。
5. **新增待办：需要 dense 退化场景的样本。** 本次融合 Δ=0 的根因是 dense 在
   20 条英文题上已经吃满，词法臂的价值测不出来。要量出兜底价值，
   得有 dense 明确失效的题（生僻标识符、精确版本号、拼写变体）。
6. E4（zhparser 对照）优先级不变，排在上面几条之后。

## 环境与口径

- 语料：40 篇（21 PDF / 19 Markdown，其中 20 篇为英文论文），1862 个可检索 chunk，
  与 E2 相同。
- 三档只切换 `--lexical-mode` 一个变量；dataset、Top-K、diagnostic-K、
  token budget、embedding identity、gold span、RRF k 全部固定。
- 全程本地 Postgres 与本地 embedding，无远端调用。
  原始资料只读，逐样本内容只留在 Git 忽略的本地报告。
