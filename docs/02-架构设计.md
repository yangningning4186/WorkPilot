**为什么模型网关单独画一层**：它是整个成本治理主线的落点。
业务代码不感知模型，路由策略是声明式配置——这样"换一档模型"是改配置而不是改代码，
对照实验才跑得起来。这也是面试问"没有你的集群怎么办"时的答案。

## 2. 关键请求时序

### 2.1 溯源问答（场景 A）

```
用户提问
  │
  ├─→ [轻量档] 意图分类：问答 / 任务 / 闲聊  ─────────┐
  │                                                    │
  ├─→ [轻量档] 查询改写：指代消解 + 多查询扩展 + HyDE  │ 可并行
  │                                                    │
  ├─→ 记忆检索：用户长期记忆 + 会话摘要 ──────────────┘
  │
  ├─→ 混合检索（并发）
  │     ├─ dense 检索  top-50   (pgvector HNSW + 部分索引)
  │     └─ 词法检索    top-50   (PG ts_rank_cd + zhparser，**非 BM25**)
  │           └─→ RRF 融合 → top-30
  │
  ├─→ rerank (bge-reranker-v2-m3) → top-5
  │
  ├─→ 拒答判定：rerank 最高分 < 阈值 → 直接返回"知识库中未找到"
  │
  ├─→ [主力档] 生成答案（强制输出消息内短引用标记 [S1]/[S2]，服务端映射回 block）
  │     └─→ 流式回传：message.delta + citation 事件
  │
  └─→ 异步：写入 llm_calls 成本记录 / 记忆抽取候选 / trace 上报
```

### 2.2 多步任务（场景 B）

```
用户下达任务
  │
  ├─→ [重推理档] planner：任务分解成带依赖的步骤列表
  │     └─→ 步数 > 3 → 发 plan 事件，等待用户确认（interrupt）
  │
  ├─→ 循环 executor：
  │     ├─ 选工具 + 生成参数 [主力档]
  │     ├─ 参数校验（Pydantic）→ 失败则返回面向模型的错误信息，重试
  │     ├─ ★ 副作用工具先抢 tool_invocations 幂等键（已 succeeded 则直接复用）
  │     ├─ 执行工具（超时 / 重试 / 降级）
  │     ├─ 写 checkpoint + agent_attempts
  │     └─ 写 run_events → 推送 step.update
  │
  ├─→ [重推理档] reflector：结果自检
  │     ├─ 通过 → 下一步
  │     └─ 不通过 → 重规划（受最大重试次数与预算约束）
  │
  ├─→ 遇到写操作 / 外发操作 → interrupt，等待人工确认
  │
  └─→ 预算熔断检查（每步）：token / 调用数 / 墙钟时间任一超限即终止
```

**核心设计**：Agent 状态是显式的可序列化 dict，每个节点是 `state → state` 的纯函数，
重启后从 Postgres 读回 state 继续。

但**状态恢复不等于副作用不重放**：LangGraph 从 interrupt 恢复时会从节点开头重新执行。
因此幂等必须落在 `tool_invocations` 这一层，而不是 Agent 的 cursor 上
（[ADR-0007](adr/0007-agent幂等与事件溯源.md)）。

## 4. 技术选型与理由

**面试必问：为什么是它？替代方案是什么？为什么放弃？**
这张表的第 3、4 列比第 2 列重要。

| 组件 | 选型 | 替代方案 | 为什么不选替代方案 |
|---|---|---|---|
| Agent 编排 | **LangGraph** | AutoGen / CrewAI / 自研 | AutoGen 偏对话式多智能体，控制流隐式、调试困难；CrewAI 抽象层级过高，出问题定位不到；自研 checkpoint 和中断恢复成本太高。LangGraph 的显式状态机正好匹配"可恢复 + HITL"的硬需求 |
| 向量存储 | **PostgreSQL + pgvector** | Qdrant / Milvus / Chroma | 单人项目要压运维面；chunk 与业务表同库可用事务保证一致性；千万级以下 pgvector HNSW 够用。**代价是水平扩展能力弱**，M2 会补一组 pgvector vs Qdrant 的对照数据来支撑这个判断 |
| 词法检索 | **PG 全文索引 + zhparser**（`ts_rank_cd`） | ES / pg_textsearch / ParadeDB pg_search | 少一个中间件。**注意：PG 原生是 cover-density 排名，不是 BM25**，文档中一律称"词法检索"。已知风险：zhparser 弱于 IK、`ts_rank_cd` 弱于 BM25，两处差距在 E2 中量化；若成为瓶颈则换 pg_textsearch |
| Embedding | **bge-m3** | OpenAI text-embedding-3 / bge-large-zh | m3 同时输出 dense + sparse，混合检索天然受益；中英混合与长文本（8k）友好；可本地部署，批量灌库不花钱 |
| Rerank | **bge-reranker-v2-m3** | Cohere Rerank / 不做 rerank | 交叉编码器质量显著优于双塔；本地部署无调用成本。代价是增加约 200–400ms 延迟，会在实验中量化"值不值" |
| 后端 | **FastAPI** | Django / Go | 异步原生、Pydantic 契约、AI 生态全在 Python |
| 任务队列 | **Arq** | Celery | Celery 配置重、对 asyncio 支持别扭；Arq 基于 Redis + asyncio，够用且轻 |
| 前端 | **Next.js + Vercel AI SDK** | 纯 React / Streamlit | AI SDK 把流式渲染、工具调用状态做好了；Streamlit 做不出 Agent 时间线这种交互，而交互质量正是产品思维的证据 |
| 可观测 | **Langfuse** | Phoenix / 自研 | trace + 成本 + dataset 三合一，自建评测框架可以直接复用它的数据集与打分存储 |
| 评测 | **自建 + 借鉴** | 直接用 Ragas / DeepEval | 评测是本项目的核心差异化，**必须自己实现才能在面试中讲透**。借鉴 Ragas 的指标分解思想与 promptfoo 的快照 diff 范式，但不做壳 |
| 容器 | **OrbStack** | Docker Desktop / Colima | macOS 上启动快、内存占用低 |

## 6. 横切关注点

| 关注点 | 方案 |
|---|---|
| 追踪 | 每个请求生成 `trace_id`，贯穿日志、LLM 调用、Langfuse span |
| 错误 | 双通道：`user_message`（给人看）+ `model_message`（给 LLM 看，含修复指引） |
| 配置 | Pydantic Settings + `.env`，模型路由表用独立 YAML，改配置不改代码 |
| 幂等 | 文档入库按 `content_hash` 幂等；**工具副作用按 `tool_invocations.idempotency_key` 幂等**（不是靠 Agent cursor，见 [ADR-0007](adr/0007-agent幂等与事件溯源.md)） |
| 过滤 | 来源 / 标签 / 时间下沉到 chunk 元数据，**检索前过滤**而非检索后过滤 |
| 安全 | 见 [12 安全与部署](12-安全与部署.md)：鉴权 / 限流 / 费用熔断 / 上传校验 / SSRF / 路径穿越 / 语料物理隔离。写操作与外发操作强制 HITL 确认 |
| 降级 | 模型档位 fallback 链；rerank 超时则退回 RRF 结果；集群不可用切商用 API |

## 7. 多用户扩展点（明确不实现，但要说得清）

本项目是单用户产品（[01 §4 非目标](01-总体规划.md)）。
但"如果要支持团队需要补什么"是面试必问题，答案必须具体到改动点：

| 维度 | 现状 | 扩展所需改动 | 难度 |
|---|---|---|---|
| 数据隔离 | 单 `user_id` | 引入 `workspace_id`，所有表加维度 + 复合索引；chunk 检索加租户前缀过滤 | 低，机械改动 |
| 权限 | 无 | ACL 下沉到 chunk 元数据（`acl JSONB`），**检索前过滤**。关键点：不能检索后过滤，否则 top-k 会被无权文档占满，有权文档挤不进来 | 中，设计已预留 |
| 连接器 | 本地文件 / Obsidian | 增加 Slack / Confluence / Drive 连接器，需处理 OAuth、增量游标、**权限同步**（源系统的 ACL 要跟着文档一起进来） | 高，权限同步是真难点 |
| 并发 | 单用户串行 | 向量检索加连接池上限；Agent run 加队列与配额；pgvector 到千万级需换 Qdrant | 中 |
| 成本 | 个人预算 | 从 run 级预算扩到用户级/团队级配额，需要配额中心 | 中 |
| 记忆 | 个人记忆 | 分裂为个人记忆 + 团队共享记忆，共享记忆需要写入审核 | 高，是产品问题不是技术问题 |

**架构上已经预留的**：`chunks` 表的过滤字段设计、检索前过滤的管线位置、
连接器抽象与增量同步机制——这三处即使单用户也按可扩展的方式实现了，
不是"以后再说"，而是"现在就没堵死"。
