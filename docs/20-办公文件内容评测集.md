# WorkPilot 办公文件内容评测集

## 1. 要解决的问题

WorkPilot 已有两类检查，但它们没有回答同一个问题：

- `artifact_suite` 检查固定渲染器能否生成可打开、可渲染、无明显错版的文件，并对 PPT 的
  “非空但空洞”页面做保守门禁；
- Cowork 端到端 suite 检查工具选择、权限、最终状态和少量关键词；
- 新增的 `office_content_suite` 检查最终 DOCX、XLSX、PPTX、PDF 是否把任务内容做对。

内容评测不能只做全文关键词搜索。错误数字、把未决事项写成结论、把机密放进对外文件、
把所有关键词堆到一页，以及用常量冒充 Excel 公式，都应当被区分并留下可复核证据。

## 2. 参考工作的可复用设计

| 工作 | 可复用设计 | WorkPilot 落地 |
| --- | --- | --- |
| [PresentBench](https://arxiv.org/html/2603.07244) | 每题实例化的二元检查清单；逐项独立判定并定位证据；先在维度内归一化，再汇总维度 | 每个任务有实例级 rubric，结果保留 `detail` 与 `evidence`；五个自动维度等权，避免检查项多的维度天然占优 |
| [PPT-Eval](https://arxiv.org/html/2606.31154) | 叶子级部分得分、关键/非关键要求、显式惩罚；用分档候选校准 judge | `critical` 只控制是否通过，不抹掉部分得分；`penalties` 单独扣分并可 blocking；pytest 用好稿与关键词堆砌反例校准排序 |
| [SpreadsheetBench 2](https://arxiv.org/html/2606.29955) | 对最终工作簿的目标单元格、计算结果与格式分别检查；公式结果需要执行语义 | XLSX 检查目标单元格、公式计算值、数字格式、图表与工作表结构；简单公式按结果判定，允许等价写法 |
| [OmegaUse-OfficeVal](https://github.com/baidu-frontier-research/OmegaUse-OfficeVal/blob/main/docs/verifier-contract.md) | 先做可用性/格式门禁，再执行规则级 verifier；门禁失败整题归零 | `gate` 先检查文件存在、格式可重开、安全和所需视觉测量；门禁失败时自动分为 0，但仍保留失败原因 |
| [Office Comprehension Benchmark](https://github.com/microsoft/OfficeComprehensionBench) | 原子二元断言，避免一个模糊总分掩盖具体错误 | 自动 rubric 使用小粒度、可审计检查；每条都有 `source_refs`，方便标注复核 |
| [OfficeBench](https://github.com/zlwang-cs/OfficeBench) 与 [FORTE](https://agi-eval-official.github.io/FORTE/) | 多办公格式、最终交付物和专业任务覆盖 | 首版同时覆盖 DOCX、XLSX、PPTX、PDF，并按 create/transform/analyze/conflict handling 分层 |

这些方法不能机械拼接。纯二元断言适合事实、结构和计算，却不能可靠评价叙事与审美；纯
LLM/VLM judge 又可能被错数字和漂亮版式带偏。因此本评测使用“确定性自动轨 + 带锚点复核轨”。

## 3. v1 数据集

套件位于 `eval/suites/office-content-dev-v1.json`，当前是合成种子集：

| 格式 | dev | test | 任务类型示例 |
| --- | ---: | ---: | --- |
| DOCX | 2 | 1 | 季度经营简报、会议决策备忘录、冲突口径状态 memo |
| PPTX | 2 | 1 | 月度经营复盘、受约束立项提案、指导委员会待决策简报 |
| XLSX | 2 | 1 | 销售汇总、预算差异、容量预测 |
| PDF | 2 | 1 | 对外事故说明、政策速查、证据综合一页纸 |

总计 12 题、99 条自动检查、12 条显式惩罚、36 条复核标准。每种格式固定 2 道 dev 与
1 道 test。test 是“访问需留痕的冻结切分”，不是保密切分；发布级基准仍应将隐藏 test
放在仓库外的受控存储。

每题都覆盖五个自动维度：

1. `fundamentals`：文件结构、页数、标题、工作表、公式或图表等基本交付约束；
2. `completeness`：任务要求的关键部分是否齐全；
3. `correctness`：数字、日期、计算、责任人和事实关系是否正确；
4. `fidelity`：是否保留资料中的范围、限定、冲突和不确定性；
5. `usability`：内容顺序、行动登记、数字格式和决策入口是否可用。

复核轨覆盖 `coherence`、`decision_utility`、`visual_quality`。每条标准都有 0/1/2 分锚点，
不能只交一个无解释的印象分。

## 4. 评分协议

### 4.1 格式门禁

首先对最终文件运行独立 Artifact Validator，并提取原生结构。以下情况按整题 0 分处理：

- 文件缺失、后缀错误、损坏或无法解析；
- 文件超过题目允许的压缩体积，或 OOXML 解压后超过上限；
- `gate.fail_on_dimensions` 指定的结构、视觉或安全维度失败；
- 要求测量的维度是 `not_run`；
- Validator 质量分低于该题阈值。

门禁结果与内容得分分开保存，避免把“文件打不开”和“内容漏了一项”混成同一错误。

### 4.2 自动轨

单个检查只有通过/失败两种得分，但每条题保留部分进度：

```text
dimension_score[d] = Σ(weight_i × pass_i) / Σ(weight_i) × 100
raw_auto = Σ(dimension_weight[d] × dimension_score[d])
automatic_score = max(0, raw_auto - triggered_penalty_points)
```

当前五个维度各占 20%。`critical` 检查失败或 `blocking` 惩罚命中会使
`automatic_pass=false`，但不会把已经完成的其它内容从报告中抹去。只有 gate 失败会按协议
把自动分强制归零。

自动检查支持：

- 整份文件、Word 标题节/表格、PPT 单页、Excel 工作表/区域、PDF 单页内的文本存在、
  禁止文本和顺序；
- 用有界上下文把数值、日期和责任人与业务标签绑定；例如 `ARR=860 / 计划=900` 与交换两者
  不再等价，相邻字段的数字也不能跨标签借用；
- 对“超额完成”“自动批准”等事实性 claim 做否定上下文识别，避免把“并非自动批准”误判为
  越界；机密字符串不使用这项宽容规则，即使是否定句也严格禁入；
- 标题、页数、表格、图表、公式、工作表等结构计数；
- PPT 原生图表的系列名、分类和内嵌数值；百分比的 `18/24` 与 `0.18/0.24` 可按同一业务值
  比较，避免“放了一个空图表对象”通过；
- Excel 单元格值、多个目标单元格、数字格式和公式计算结果；
- Artifact Validator 的维度或具体检查状态。

所有文本检查都绑定范围。比如“风险页必须有黄灯”只在标题匹配“风险”的 PPT 页面中查找，
不会因为其它页面堆词而通过。PPT 演讲者备注明确不属于观众可见内容，把必需事实藏在备注中
也不会得分。所有 PPT 题还必须实际渲染，并把结构、视觉、安全三维同时设为已测量硬门禁。

### 4.3 复核轨与总分

自动轨权重为 60%，复核轨为 40%。自动轨同时保留独立通过门禁，因此降权不会让错误事实、
关键缺项或越界结论依靠主观复核高分翻盘：

```text
final_score = 0.6 × automatic_score + 0.4 × review_score
review_pass = 每条复核分数均不低于该 criterion.minimum_score
engineering_pass = automatic_pass AND review_pass AND final_score ≥ pass_threshold
benchmark_pass = engineering_pass AND review_eligible_for_benchmark
```

只有该题所有复核标准都完成、且复核记录中的 `artifact_sha256` 与当前文件一致时，才生成
`final_score` 和 `benchmark_pass`。复核缺失或引用旧文件时，总分为 `null`，报告只展示
`automatic_score`；这比把“未评价”偷偷当满分或 0 分更诚实。每条复核标准默认最低分为 1；
因此即使自动分为 100，连贯性、决策价值或视觉质量任一项为 0，也不能被加权结果掩盖。

人工复核默认具备 benchmark 资格。视觉模型也可以按同一锚点评出 `review_score` 和
`engineering_pass`，但当前 Office VLM Judge 尚未完成与办公专家的盲评校准；其记录固定为
`source=model + calibration_status=uncalibrated`，因此 `review_eligible_for_benchmark=false`。
这一区分使模型分可用于快速迭代，又不会把未经验证的自动审美判断伪装成正式发布结论。

## 5. 使用方法

先校验套件：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_content_suite validate
```

将 dev 任务物化为隔离工作区：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_content_suite prepare \
  --workspace-root /tmp/workpilot-office-content-dev
```

每题目录包含 `TASK.md`、`task.json`、`inputs/` 和空的 `submission/`。被测系统只需按
`task.json.required_output` 保存最终文件。运行被测系统时应把单个 case 目录设为唯一可读写
工作区，不能让它读取 suite JSON、scorer 或其它 case；随后评分：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_content_suite score \
  --submission-root /tmp/workpilot-office-content-dev \
  --output-dir eval/outputs/office-content/<label>
```

上面的命令适合开发期自动轨，退出码只反映自动检查。发布/晋升候选必须加载哈希绑定的复核文件，
并启用完整复核门禁：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_content_suite score \
  --submission-root /tmp/workpilot-office-content-dev \
  --reviews /path/to/reviews.json \
  --require-complete-reviews \
  --output-dir eval/outputs/office-content/<release-label>
```

### 5.1 一键规则 + 视觉模型评测

若各题最终文件已经位于 `submission/`，以下一条命令会依次执行确定性门禁、PPT/PDF 逐页栅格化、
DOCX/XLSX 原生预览（无原生 renderer 时使用明确标记的结构预览）、视觉模型复核和最终汇总：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_eval \
  --submission-root /tmp/workpilot-office-content-dev \
  --output-dir eval/outputs/office-content/<model-label> \
  --allow-model-send \
  --authorization-note '仅允许本次 synthetic Office dev 文件发送到内部视觉模型'
```

默认使用配置完整的 heavy 端点，否则使用 main 端点。若默认模型不支持图片，须显式选择视觉模型：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_eval \
  --submission-root /tmp/workpilot-office-content-dev \
  --output-dir eval/outputs/office-content/<model-label> \
  --judge-base-url http://<vision-endpoint>/v1 \
  --judge-model <vision-model> \
  --api-key-env VISION_API_KEY \
  --allow-model-send \
  --authorization-note '<获批的数据范围、端点和用途>'
```

安全与可复现约束：

- 未同时提供 `--allow-model-send` 和非空授权说明时，Office 文件及题目来源资料都不会发给模型；
  报告只保存授权说明的 SHA-256，不保存说明原文；
- 每题图片按页附加，文本模型拒绝图片时 fail-closed，不会静默删图后继续打视觉分；
- Judge 只能返回固定顺序的严格 JSON，criterion 缺失、乱序、越界分、截断或模型身份漂移均失败；
- 默认最多 24 次模型调用、50 万 token、每题 12 页和 32 MiB 图片，可用对应 CLI 参数收紧；
- 结构预览不能证明原生排版，使用该兜底时 `visual_quality` 最高只能给 1 分；
- 输出目录原子落盘且不可覆盖，失败不会留下看似完整的最终报告。

一键输出在普通 `report.json`、`review-packet.jsonl` 之外增加：

- `model-reviews.json`：与最终文件哈希绑定的 v2 模型复核记录；
- `model-review-run.json`：prompt/实现/model/授权 fingerprint、逐页图片 SHA-256、渲染模式、用量、
  重试和模型原始 JSON，便于审计。

该命令评测现有最终文件，不负责让被测 Agent 生成文件。生成阶段仍应在隔离 case 工作区执行；
生成结束后只需运行上述一条评测命令。

访问 test 必须同时留下原因：

```bash
PYTHONPATH=backend backend/.venv/bin/python -m eval.office_content_suite prepare \
  --split test --include-test --test-access-note '<冻结验收原因>' \
  --workspace-root /tmp/workpilot-office-content-test
```

`score` 输出：

- `report.json`：门禁、逐条 rubric、局部证据、维度分、惩罚、自动分、复核和总分，并记录
  `generated_at`、规范化 suite 哈希和 scorer implementation fingerprint；
- `review-packet.jsonl`：按最终文件哈希绑定的复核任务包。

复核文件格式：

```json
{
  "schema_version": "workpilot-office-content-reviews.v2",
  "reviews": [
    {
      "item_id": "office-docx-001-quarterly-brief",
      "criterion_id": "docx-001-review-coherence",
      "artifact_sha256": "<64 位 sha256>",
      "score": 2,
      "evidence": "执行摘要先指出收入缺口，风险和行动均能回扣该缺口。",
      "reviewer": "reviewer-id",
      "source": "human"
    }
  ]
}
```

## 6. 已知边界

- 文本断言适合精确事实，但不能覆盖所有正确改写；容易产生同义表达时，应使用复核轨或增加
  有限、经审阅的表达变体，不能无限扩大模糊匹配。
- 标签—数值检查只证明局部关系，不等价于完整自然语言推理；复杂表述、图像化文本和扫描件仍需
  OCR/VLM 或人工复核，而且新增同义标签必须通过正反例校准。
- 内置 Excel 公式解释器当前覆盖四则运算、跨表单元格/区域、`SUM`、`AVERAGE`、`MIN`、
  `MAX`、`ROUND` 和百分数字面量。复杂函数需要使用隔离 LibreOffice 重算 adapter，不能退回
  到公式字符串完全一致。
- DOCX 的逻辑节依赖 Word Heading 样式；仅把正文加粗不会被当成标题。这是有意的，因为最终
  文件应保留可导航的原生结构。
- 自动视觉门禁能发现空白页、空容器型页面、低信息密度、focus 页滥用、越界、重叠、过小字号和
  渲染失败；但它不能判断视觉是否真正优美、图片是否语义贴切，后者仍必须走带锚点复核。
- v1 数据是 synthetic 且 `pending_human_review`，只能作为工程候选集，不能宣称为产品质量
  baseline 或外部 benchmark 成绩。
- 一键 VLM Judge 已可自动执行三项复核，但在完成专家双盲标注、冻结校准集并达到预设一致性门槛
  前只产生工程信号；模型满分不等价于 benchmark 通过。

评测实现本身以 `eval/contracts/office-eval-v1.json` 登记为零模型 deterministic contract，
nightly 固定回归最终文件验证、四格式代表 oracle、PPT 备注/标签关系/原生图表反例、复核否决和
Cowork Office 工作流覆盖；这只能证明 scorer 没有回退，不代表候选内容集已经获得人工晋升。

## 7. 晋升到正式基准前

1. 由办公场景专家逐题复核 prompt、fixture、source ref、关键项与惩罚，修订后签字冻结版本；
2. 为每题制作“完整正确、部分正确、严重错误、关键词投机”至少四档候选，验证 scorer 排序；
3. 对复核轨做双人盲评，计算一致性；LLM/VLM judge 只有在与专家排序达到预设相关性后才能替代
   部分人工复核；
4. 扩到至少 100 道从真实岗位流程抽象而来的任务，并平衡行业、语言、复杂度、创建/编辑任务；
5. 把隐藏 test、原始敏感资料和 judge 提示放到仓库外，开发期只暴露 dev；
6. 报告每种格式、任务类型、难度和维度的分层结果，不用一个平均分掩盖格式短板。
