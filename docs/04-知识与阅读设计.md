# 04 · 知识与阅读设计

**核心承诺**：模型下的每一个关于文档的论断，都要能落回原文的具体位置；落不回去就说落不回去。

这一条有**两条**实现路径，解决的是两个不同的问题，不要混为一谈
（[ADR-0013](adr/0013-沉浸阅读作为工作模式而非第二条产品线.md)）：

| | 沉浸阅读 `cowork/reading/` | 知识库 `rag/kb/` |
|---|---|---|
| 面对 | 用户此刻打开的**这一份**文件 | 跨文档的资料库 |
| 问题形态 | "这篇第三节在论证什么" | "我读过的论文里谁在做负样本构造" |
| 寻址单位 | **locator**：1-based 的页 / 节序号 | chunk，溯源到页 |
| 存储 | **不入库**。读工作区原始文件，进程内解析缓存 | `~/.workpilot/kb/<slug>/` 的 FAISS + BM25 |
| 引用形式 | `[p.12]`，阅读器渲染成可点链接并滚过去 | `[K1]`（预检索）/ `[S1]`（`search_knowledge`） |
| 溯源精度 | **bbox**（unit 由 `ParsedBlock` 组成） | **页** |
| 检索 | 没有检索。全文三层匹配，线性扫 | dense + BM25 两路 RRF |

两条路径共用 `app/ingest/` 的解析器，此外没有共享状态。

## 1. 解析：解析即结构化

> 借鉴 RAGFlow DeepDoc — 不把 PDF 当纯文本流，先做版面分析得到 block 序列，再按类型分流。

```
原始文件
  │
  ├─ 版面分析（MinerU，中文/学术 PDF 首选；PyMuPDF 轻量路径与兜底）
  │    └─→ block 序列：{type, content, char span, locations[]}
  │        type ∈ title|paragraph|table|list|figure|formula|header|footer|code
  │
  ├─ 按类型分流处理
  │    ├ title      → 构建标题层级树（heading_path 的来源）
  │    ├ paragraph  → 清洗（去连字符断行、合并跨页/跨栏段落）
  │    ├ table      → 转 Markdown，**处理跨页表格合并**，保留表头
  │    ├ formula    → 转 LaTeX；行内公式保留在段落中，避免切碎段落
  │    ├ figure     → 提取 caption；无 caption 用视觉模型生成一句描述
  │    └ header/footer → **丢弃**
  │
  └─→ 归一化产物 `ParsedDocument`：
       full_text     （NFC，字符偏移基准）
       blocks[]      （`ParsedBlock`，稳定最小单元）
         └─ locations[]   （一个 block 可跨页/多区域）
```

**学术 PDF 的两个特有难点**：
- **双栏排版**：阅读顺序不是自上而下，必须先做栏识别再定序，否则段落全乱
- **公式**：行间公式独立成 block，行内公式必须留在原段落——
  把 `$\mathcal{L}_{con}$` 切出去，这段话就读不懂了

**为什么 header/footer 必须丢**：论文每页都有会议名、arXiv 编号、页码。
不去掉的话每个片段都被这段噪声污染，向量被拉向同一方向，检索区分度骤降。

### 1.1 定位元数据必须完整（不只是 bbox）

只存 `[x0,y0,x1,y1]` 四个数是不够的。PDF 原生坐标原点在**左下角**，
而 pdf.js 等前端渲染器用**左上角**；页面可能带旋转；不同解析器坐标基准不一致。

`ParsedBlock` 记录文本与字符区间，`locations[]` 记录一到多个位置：

| 字段 | 作用 |
|---|---|
| `bbox_norm` | 归一化到 `[0,1]`，前端按实际渲染尺寸缩放 |
| `page_width` / `page_height` | 解析时的页面尺寸（pt） |
| `rotation` | 0/90/180/270 |
| `coord_origin` | `top_left` / `bottom_left` |
| `parser` + `parser_version` | 坐标语义的解释依据 |

漏掉任何一项，换个渲染器高亮就会错位（约束 3）。
位置列表让跨页表格和多栏段落能够对应多个 bbox，而不是丢掉其中一页。

`char_start/end` 统一是 NFC 文本的 Unicode code-point offset。
前端 UTF-16 选区必须交给后端转换，并用 quote 校验，不允许混用字节、UTF-16 与 code-point 偏移。

### 1.2 解析质量校验

每批入库随机抽 **20 个 block** 人工检查，重点看表格是否错位、跨栏段落是否断裂、
公式是否被切出段落。解析质量单独建一组评测样本（给定 PDF 页 → 期望的 Markdown 表格），
**不混进问答评测**。

解析必须跑在独立子进程并设资源上限——MinerU 处理畸形 PDF 时 OOM 并不罕见
（[12 §2.3](12-安全与部署.md)）。`app/ingest/pdf_worker.py` 是那个子进程边界。

- `auto` 路由先跑 PyMuPDF 轻量分析；检测到多栏、嵌入图片或文本质量问题时选择 MinerU。
- MinerU CLI 在独立进程组运行，整文档超时/取消会杀掉进程组；其 Python/模型环境与后端隔离。
- MinerU `content_list.json` 统一转换为 `title/paragraph/table/formula/figure_caption/list/code`，
  坐标从 0–1000 归一化到左上原点 `[0,1]`；页眉、页脚、页码、旁注和脚注不进入索引。
- 结构门控强制校验 block 顺序、Unicode 区间回切、页码、页面尺寸、旋转角和 bbox；文本门控检查
  空结果、低密度、替换字符、控制字符及定位覆盖率。MinerU 失败可配置回退 PyMuPDF。

质量跑批由 `eval/pdf_parsing_quality.py` 执行，输出机器可读 JSON、人工可读 Markdown 和抽样 bbox
叠图。跑批产物不提交，只把人工验收结论登记到 `docs/experiments/`。

## 2. 沉浸阅读：locator 是唯一的地址

一份**材料**就是工作区里一个用户正在读的文件。它被切一次成 **unit**，此后所有操作都按
**locator** 寻址。就是这一个抽象，让"模型引用第 12 页"和"阅读器滚到第 12 页"两件事
都不需要知道文件到底是 PDF 还是 Markdown。

```
工作区文件 ──app/ingest/──→ ParsedDocument
                                │
                    units_from_pages（PDF：物理页）
                    units_from_sections（文本/MD：按加权字符切节）
                                │
                                ▼
                    ReadingUnit[]  ← 每个带 locator（1-based）与它的 ParsedBlock[]
                                │
        ┌───────────────────────┼────────────────────────┐
   material_outline        search_material          read_material
     （结构）              （定位，三层匹配）        （原文，按 locator 取）
        └───────────────────────┼────────────────────────┘
                                ▼
                          reader_goto（驱动用户侧阅读器：翻页 + 高亮）
```

### 2.1 三条纪律，都是踩出来的

**空页也占一个 locator。** 一页只有图、没有文字层的论文很常见。跳过它会让此后所有页码
整体偏移一位——模型引第 12 页，用户翻到第 13 页，而且**没有任何迹象表明出了错**。
这是这一层最容易犯且最难发现的 bug。

**PDF 按物理页切，不按块数或字符数。** 页码是唯一同时对得上"用户在阅读器里看到的东西"
和"模型引用的东西"的单位。按字符切出来的第 7 段，用户在 PDF 上找不到。

**搜索返回的片段不能直接当引文。** `search_material` 返回的是开了窗口的片段，可能从句子
中间断开；照抄一句会产生和原文对不上的引用。所以 playbook 里写死了"下任何论断之前先用
`read_material` 读到原文——**没读过就是不知道**"。

### 2.2 匹配分三层，并且告诉调用方命中在哪一层

一份材料至多几百个 unit，线性扫一遍是毫秒级。这里**替掉**了检索，而不是检索的降级实现——
每条命中天然带着自己的 locator，因为它就是在那一页上搜到的，而不是事后被提示词要求补
一个页码。向量检索给不了这个性质：它返回 chunk，chunk 到页码要再映射一次。

| 层 | 做什么 | 为什么需要 |
|---|---|---|
| `exact` | 原样匹配，忽略大小写 | 最便宜的那一层 |
| `normalised` | 折叠空白、软化标点 | 从 PDF 里复制出来的句子在原文里往往被硬换行截断过 |
| `terms` | 按命中词数排序 | 自然语言问句在前两层必然全落空；没有这一层等于告诉模型"文档里没有"，而实际只是问法和原文用词不同 |

命中层级要回给模型，它据此区分逐字命中和模糊命中。

### 2.3 引文校验的强度刻意不对称

`reader_goto` 在引文对不上时**照样翻页、只是不高亮**。

用中文问一篇英文论文时，模型给的"引文"是它自己的翻译，永远不可能逐字命中；为此拒绝跳转
会让阅读器看起来是坏的。**落到正确的页而不画高亮，远比原地不动有用，而且绝不会把高亮涂在
错误的字上。**

会持久化的批注是更强的承诺，那一档必须对不上就直接拒绝——那只工具留到阅读器面板落地时再加。

`verify_quote` 命中哪个 block，就把那个 block 的 `locations[]` 原样交出去：
高亮几何是解析的产物，不是前端猜出来的。

### 2.4 玩法只在选了阅读档时才注入

工具常驻（模型随时可能要读一份文档），但那段"先看结构、读过再引、一处一跳、`[p.N]` 标注"
的 playbook 由 `work_modes.render_work_mode_block` 在用户选了论文阅读时才写进 system prompt。
无条件注入的后果实测过：模型在非阅读任务里也开始给每句话标页码。

模式块在 run 起始渲染一次就不再变，因此可以安全地放进 system prompt——provider 的前缀缓存
从 system 起算，每轮会变的内容放进去等于每轮把整段前缀重新计费。

## 3. 本地知识库：一个 KB 就是一个目录

```
~/.workpilot/kb/<slug>/
├── manifest.json     KbManifest：显示名、文档清单、★ embedding 签名
└── index/            FAISS + BM25 + docstore
```

语料本身**留在用户自己的目录里**，清单只记它的绝对路径。`index/` 是派生数据，删了可以
`uv run python -m app.cli.kb rebuild <slug>` 重建。

**slug 与显示名分开**：用户会把 KB 叫成「我的论文 / papers (2026)」，这些字符不能直接当
目录名。slug 同时是路径穿越的防线——只允许 `^[a-z0-9][a-z0-9-]{0,62}$`，因此 `../`、
绝对路径、Windows 盘符都不可能通过。

### 3.1 embedding 签名是这里最要紧的字段 ★

一份 FAISS 索引只对建它的那个 embedding 模型有意义。换了模型、换了维度、甚至同一模型换了
revision，旧向量和新查询向量就不在同一个空间里——**检索不会报错，只会安静地返回胡说八道
的结果**。

Postgres 那边靠 `document_versions` 的事务切换把这件事挡住（约束 10）。换到文件系统之后，
只能靠每次加载时比对 `manifest.json` 里的 `EmbeddingSignature(model, dimensions, revision)`，
不一致就**拒绝检索并要求重建**。

这是无声失败和显式失败的区别，也是这个字段存在的全部理由
（[ADR-0012](adr/0012-退役postgres与redis改用本机文件.md) 代价 §2）。

### 3.2 重建是就地覆盖，不做原子替换

约束 10 要求"候选版本全部成功才事务激活"。KB 这条路径上**刻意不还这个债**：重建直接覆盖
`index/`，中途失败会让这个 KB 暂时没有索引。

取舍是明知的——个人 KB 重建是秒级，而"没有索引"是**显式失败**（`search_index` 直接拒绝并
要求重建），不会安静地返回旧结果。真正不能接受的是安静，不是短暂不可用。

`manifest.json` 仍然原子写：它是"这个库里有什么"的唯一事实来源，写坏了连重建都不知道该
重建哪些文件。

### 3.3 切分：一份 PDF 切成「每页一个 Document」

LlamaIndex 的切分器会把 Document 的 metadata 原样复制给它切出来的每个节点。所以**按页**
喂进去，页码就自动跟着每个片段走，代价只是构造时多一层循环。整篇喂进去的话，节点只知道
自己属于哪个文件，不知道在哪一页。

`SentenceSplitter`，`CHUNK_SIZE = 512` / `CHUNK_OVERLAP = 64`。LlamaIndex 默认的 1024/200
对论文偏大——一个片段跨了三个小节，检索命中之后还得让模型自己在里面找。

溯源字段（`doc_id` / `filename` / `title` / `page_no` / `heading_path`）**不能进 embedding
文本，也不能进给 LLM 的文本**：把文件名和页码混进待编码文本会稀释语义向量。

> **这里换掉的是 bbox 级精确高亮。** 切分器按字符窗口切，块边界和字符区间对不上了，所以
> KB 路径的证据只带页码，不带矩形框。需要圈出那句话的时候走阅读路径（§2），那条路仍然是
> block 级的。

### 3.4 检索：dense + BM25 两路 RRF

```
query
  ├─ dense 召回  FAISS，top-30
  └─ BM25 召回   BM25Retriever，top-30
        └─→ RRF 融合（k=60）→ top_k
```

**为什么要 BM25 这一路**：稠密召回处理同义改写，BM25 处理精确术语、编号、人名和公式——
中文学术语料上后者经常是唯一能命中的那一路。

**每路取 30 而不是 top_k**：两路各取 top_k 的话，融合退化成"谁排第一谁赢"，没有东西可融。

**为什么 RRF 而不是加权求和**：两套系统的分数既不同尺度也不同形状，加权求和需要先归一化，
而归一化方式本身引入偏差且要按数据集调。RRF 只用**排名**，无量纲、无需调参、对异常分数
鲁棒。代价是丢弃了分数的绝对强度信息——所以拒答不能靠融合分数的阈值判（§3.6）。

### 3.5 建索引不进队列

建索引是纯本地的活：读磁盘上的文件、调本机 embedding 端点、写磁盘上的索引。它不碰数据库、
没有跨进程副作用、也不需要重试语义。为它加一个队列作业类型意味着改 `RunQueue` 协议、两个
队列实现、worker 注册和一张作业表——那些复杂度换来的唯一好处是"进程重启后作业能续上"，
而这件事**恰好不需要**：索引要么写成了，要么没写成，清单里的签名就是答案。

所以它是一个进程内作业表，每个 KB 同时只允许一个作业，状态给界面轮询。进程重启会丢作业
记录，不会丢数据——用户看到的是"这个库没建索引"，那正是事实。

但它必须存在：一个文件夹的论文解析是分钟级的活，挂在 HTTP 请求上必然超时（CLAUDE.md：
worker 不依附 HTTP 连接），而一条不动的进度条和一个卡死的界面在用户看来没有区别。

### 3.6 挂载 KB 后的确定性预检索

会话可以挂一个 KB（`conversations.kb_slug`）。挂了之后，run 起始拿用户这次的问题去检索
一遍，把命中折进这次 run 的**稳定前缀**。不调决策 LLM，所以不推迟第一个 token，而且可以
写单测而不是靠采样。

它修的是一个真实故障：**弱模型在原生工具调用下经常一次检索都不调，直接凭印象作答。**
开局就把命中递到手上，即使模型自己不会去找，接地也已经发生了。模型觉得不够，再调
`search_knowledge` 补——预检索是垫底，不是替代。

和阅读那条 `render_locate_block` 是同一个招式，只是数据源换成了挂载的 KB。

**引用编号刻意分成两套**：预检索发 `K1…Kn`，`search_knowledge` 发 `S1…Sn`。两边都从 1 开始
且内容不同，共用一套前缀会让 `[S2]` 在同一段回答里指向两段不同的原文。不共享编号状态就不
会有这个问题，代价只是模型要认两个前缀，而这在 block 里写清楚了。

预算：`PREPASS_TOP_K = 4`，单段 420 字符，总计 2000 字符。预检索进的是 system 前缀，
整段 run 都在为它付费，所以比工具返回收得紧。

### 3.7 授权

`knowledge.read` 是**独立的全局授权**，不得借用 `filesystem.read`
（[ADR-0010](adr/0010-cowork本地存储与rag数据面分离.md)）。撤销该 grant 后 `search_knowledge`
必须在进入 KB 之前失败关闭。

### 3.8 embedding 不经模型网关（约束 1 的唯一豁免）

`build_embedding` 直连本机 embedding 端点。这条链路指向本地 Ollama：没有 API 花销也没有
配额，网关能提供的路由与预算在这里没有可管的东西。**代价是 embedding 调用不进成本看板**——
本地推理免费，这个代价是自洽的；哪天换成云端 embedding，就要把它接回网关。

必须自己造 httpx client：默认 `trust_env=True` 会读 `HTTP_PROXY`，把发往 `127.0.0.1` 的
embedding 请求塞进用户的代理，回来的是 502 而不是向量。开着代理是常态，所以这不是边缘情况。

## 4. 溯源实现

两条路径各自的完整链路，任何一环断掉前端就无法定位原文。

**阅读路径（bbox 级）**

```
解析 → ParsedBlock：char_start/end + locations[]（页码/bbox_norm/尺寸/旋转/原点）
   ↓
切 unit → 每个 unit 记住自己的 locator 与组成它的 block 序列
   ↓
模型引用 → reader_goto(path, locator, quote)
   ↓
verify_quote → 三层匹配定位到 block → 原样交出该 block 的 locations[]
   ↓
阅读器 → 翻到 locator → bbox_norm × 渲染尺寸 高亮（对不上则只翻页）
```

**KB 路径（页级）**

```
解析 → 按页构造 Document，页码进 metadata
   ↓
SentenceSplitter 切节点 → metadata 原样复制，页码跟着片段走
   ↓
检索 → KbHit(doc_id, filename, title, page_no, text, score)
   ↓
生成 → 证据编号 [K1]/[S1]，要求句末引用
   ↓
后处理 → 短标签映射回 doc_id + page_no；未知标签或未提供的 doc 判无效，不猜测修复
```

短标签只用于减少 prompt token，**不能成为持久化身份**。消息必须把 `citation_id` 到
`doc_id / page_no / quote` 的完整映射存进 `citations`。

**引用准确率是独立指标**：模型可能引用了一个片段但该片段并不支撑答案（引用幻觉）。
判分方式：给 Judge 看「答案句 + 被引用的原文」，判断是否真的支撑。

## 5. 指标定义

**指标必须分解到组件**，否则无法归因是检索坏了还是生成坏了。

### 检索层

原来的 `span_recall@k` / `alpha_ndcg@k` 口径锚在 `parsed_blocks` 的字符区间上
（[ADR-0006](adr/0006-分块与标注分层.md)），依赖 `documents/versions/blocks/chunks` 四层表。
那套表随 [ADR-0012](adr/0012-退役postgres与redis改用本机文件.md) 退役，**这一组指标目前没有
可跑的实现**，处置见 [06 §4.5](06-评测体系.md)。

ADR-0006 的核心判断本身没有被推翻：gold 标注不能锚 `chunk_id`，因为 chunk 随分块策略而变。
重建这条轨时锚点应该是 **`(文件 content_hash, 页码, 字符区间)`** ——文件哈希跨重建稳定，
页码是新的最小溯源单位。

### 生成层

| 指标 | 判分 |
|---|---|
| `answer_correctness` | Judge 对比 gold_answer |
| `faithfulness` | 每个论断是否被检索上下文支撑 |
| `citation_accuracy` | 引用的片段是否真的支撑对应句子 |
| `refusal_correctness` | 不可答正确拒答 + 可答不误拒 |
| `format_compliance` | 结构化输出字段齐全度（规则轨） |

### 阅读层（新增，尚无跑批）

| 指标 | 判分 |
|---|---|
| `locator_accuracy` | 模型标的 `[p.N]` 是否就是原文所在的那一页 |
| `quote_verifiability` | `reader_goto` 的 quote 有多大比例能逐字回原文（跨语言问答上必然低，要分语言报告） |
| `read_before_claim` | 下论断之前是否真的调过 `read_material`——这是 playbook 的第一条纪律，也是唯一可以纯规则判的一条 |

### 端到端

`latency_p50/p95`、`ttft`、`cost_per_query`
